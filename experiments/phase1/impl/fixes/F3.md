## Decisions and why

**Held-out audit on TRL's own evaluation, not a second sampler (B4-4).** The brief suggested a callback that every N
evaluations samples K completions on a fixed held-out set. TRL's `eval_strategy="steps"` already samples G = 8
completions per held-out prompt at the training temperature, through the training backend (HF or vLLM), and scores
them with the same TRLReward; a second sampler would duplicate generation (the expensive part) through a second code
path. So TRLReward records what it scores (`recorded`, enabled by the Controller), the Controller clears it at
`on_step_end` (transformers runs `on_step_end`, then `_maybe_log_save_evaluate` → `evaluate` → `on_evaluate`, read in
`transformers/trainer.py` 5.20.1, lines 1929–1930 and 2855), so at `on_evaluate` it holds exactly the evaluation's
completions; `gather_object` collects them from every process so all processes take the same decision. "Every N
steps" is `eval_steps`; the held-out set is `eval_dataset`. K = 8 measures every plan §9 alarm; `topology_collapse`
(K ≥ 64) stays "not measured" during training and is measured offline through `sample_eval` + `eval_run`.

**Baseline = the step-0 evaluation.** With `eval_on_start=True` (documented in the Controller and the M7 wiring) the
first evaluation scores the SFT weights; its audit becomes the baseline (components alarm, envelope rises) unless one
is passed (e.g. an `eval_run` report's `audit`). `eval_audit/fired` lists only checks that fire now and did not fire
on the baseline: rolling back to the SFT weights cannot fix a check the SFT checkpoint already fails (I17: honest
small-nodule output reaches the area-tail line), and otherwise every evaluation would roll back forever
(`test_audit_alarms_that_fire_on_the_baseline_do_not_roll_back`). `eval_on_start` is not made a `grpo_config`
default: it would add an evaluation to the B4 end-to-end test and fail runs without an `eval_dataset`.

**B2-2: initial weights instead of "stop training".** Saving the initial trainable parameters as the first best
makes every rollback well defined, needs no `TrainerControl` (the reproducers pass `control=None`), and keeps a
multi-hour run alive; the alarm and the rollback are logged. Cost: one `torch.save` of the trainable parameters at
construction (SmolVLM-256M full fine-tune ≈ 1 GB on disk, LoRA a few MB).

**B2-3: tolerant reader, atomic writer.** `os.replace`: "If successful, the renaming will be an atomic operation (this
is a POSIX requirement)" (https://docs.python.org/3/library/os.html#os.replace), so a writer that writes a temp file
and renames it never exposes a partial file; editors do not all do that, so the reader also tolerates a partial file
by not consuming its mtime. Reading on rank 0 and `broadcast_object_list` (a no-op in one process,
`accelerate/utils/operations.py`) also removes a latent divergence: before, every rank read the file itself and
could see different versions mid-save.

**B2-5: refuse at configuration.** TRL passes reward functions no group size (`_calculate_rewards`' kwargs:
dataset columns, `trainer_state`, `log_extra`, `log_metric`), and 16 equal keys are also what an oversampled item drawn
twice in a row gives, so the reward call cannot detect it; `grpo_config` and the Controller check it once.

**B3-5: verify pixels at row build.** Rows are the only path from `data/prepared/images` to a trainer, so the check
cannot be bypassed there and needs no new record field (the prepared set keeps its hashes). Measured on the real
prepared set (`scratchpad/fix/F3/png_cost.py`, `real_rows.py`): decode + hash 2.9–5.4 ms per image serial, 1.0–1.2 ms
with 3 threads (OpenCV releases the GIL: `PyAllowThreads`,
https://github.com/opencv/opencv/blob/4.x/modules/python/src2/cv2_util.hpp); `grpo_rows` LIDC train (8,552 rows)
16 s, RIGA 1.3 s on the loaded Mac; peak RSS 0.49 GB; every real image matches its record.

**B4-3: what the table holds.** TRL keeps the last `generation_batch_size` completions in deques and writes
`completions_<step>.parquet` at every `log` (`grpo_trainer.py` `log`, `_logs` with `maxlen=generation_batch_size`);
an evaluation's `log` rewrites the same step's file, so at evaluation steps the table holds held-out completions after
(possibly) the step's training ones. `export(paths, keys)` therefore filters by item ids (`sample_eval --completions
--split val` uses the split's ids), checks that rows come in whole groups of one key and one group index, and merges
consecutive groups of one key (oversampled items) into one row.

**Sampler through `GRPOTrainer._generate`.** It reuses TRL's prompt rendering (`prepare_multimodal_messages`, chat
template), generation backend and decoding, and TRL's truncation rule (`ids[-1] not in eos_and_pad`); calls hold
whole groups of 8 identical prompts because TRL's vLLM path requests `n = num_generations` per G-th prompt
(`trl/generation/vllm_generation.py`). `_generate` is private, but TRL is pinned (1.16.0) and the tests exercise it
both scripted and with real HF generation.

## Follow-up: bf16 on CPU-only Linux (CI `train` job, found by F5)

- **Problem.** TRL's configs default to `bf16 = not fp16` (`trl/trainer/base_config.py` `__post_init__`), and
  transformers 5.20 `TrainingArguments.__post_init__` raises "Your setup doesn't support bf16/gpu" when
  `bf16 and not use_cpu and not is_torch_bf16_gpu_available()` (`training_args.py` lines 1741–1746). On a CPU-only
  machine every `sft_config` / `grpo_config` call failed (10 tests in the CI `train` job); the Mac hid it because
  MPS on macOS ≥ 14 counts as bf16-capable.
- **Fix (`src/objdel/train/configs.py`).** Both configs set `bf16 = transformers.utils.is_torch_bf16_gpu_available()
  and not fp16`, the same predicate TrainingArguments checks (CUDA: `torch.cuda.is_bf16_supported()`, so the Vast
  Ampere+ cards keep bf16; MPS on macOS ≥ 14; XPU / NPU / TPU), unless the caller overrides `bf16`. CPU-only runs get
  fp32. The D8 settings are unchanged (`test_grpo_config_is_plan_d8`).
- **Tests.** `test_bf16_only_where_the_hardware_supports_it[True|False]` (the predicate patched; an explicit
  `bf16=False` and `fp16=True` win), `test_configs_build_on_this_machine` (all three models, no overrides, the real
  check decides). `test_a_batch_that_splits_groups_across_processes_is_refused` built a raw `GRPOConfig` with TRL's
  default and now passes `bf16=False` (a test-only issue).
- **Verification in Linux.** `polycore-linux:arm64`, `--memory 3g --cpus 3`, F5's install
  (`uv pip install -e ".[dev,data,train]" --torch-backend cpu`, `scratchpad/fix/F3/ci/job.sh`): torch `2.14.1+cpu`,
  CUDA None, `is_torch_bf16_gpu_available()` False; `tests/test_train_{configs,trl,rewards,dataset}.py` +
  `tests/test_breakit_reward.py`: **82 passed, 2 skipped** (the skips are data-backed). The first container run,
  with the configs fix only, already passed the 10 reported tests; it showed the two test-side issues above, which
  the second run confirms fixed. Locally (Mac): 32 passed in the two edited files; `make lint` clean.
