## B4-1 CI action refs

- **Fix.** `astral-sh/setup-uv@v10` resolved to nothing: setup-uv publishes only immutable full-version tags since
  v8.0.0. Every `uses:` now names a full commit SHA, release tag in a trailing comment:
  - `actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803  # v6.1.0` (latest v6; v7 exists, not adopted here)
  - `astral-sh/setup-uv@1c37ad07a6a961277cf70c0d37d6f313000f5884  # v10.3.0` (v10's only breaking change: cache off
    for `pull_request_target` / `workflow_run` / `release`, events this workflow does not use)
  - `actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9  # v7.0.2`
  - `pypa/cibuildwheel@b3395e271a35f73dad77f21802abe9b986dfe299  # v4.3.1` (annotated tag: the SHA is the peeled
    commit `v4.3.1^{}`, not the tag object `a499b5be…`; matches `make wheels`' `cibuildwheel==4.3.1`)
- **Verification.** `git ls-remote --tags https://github.com/<owner>/<repo>` lists each tag at that SHA; the GitHub
  API `repos/<owner>/<repo>/commits/<sha>` returns each as a commit of the action's own repository (not a fork).
  `docker run rhysd/actionlint:latest -verbose .github/workflows/tests.yml` → "Found total 0 errors".
  actionlint does not check that refs exist (B4), hence the `git ls-remote` check.
- **Trade-off.** Dependabot raises no security alerts for SHA-pinned actions (GitHub's guide); it still opens
  version-update PRs and rewrites the version comment when `.github/dependabot.yml` enables the
  `github-actions` ecosystem. Not added (a repo-config choice for the owner).
- **Sources.**
  - GitHub, Security hardening for GitHub Actions, "Using third-party actions": "Pin references to actions to a commit SHA
    in your workflow files … you should verify it is from the action's repository and not a repository fork";
    "Dependabot only creates alerts for vulnerable actions that use semantic versioning and will not create alerts
    for actions pinned to SHA values."
    https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions#using-third-party-actions
  - setup-uv v8.0.0 release notes (no major/minor tags; use the immutable tag or the commit hash):
    https://github.com/astral-sh/setup-uv/releases/tag/v8.0.0 ; v10.0.0: https://github.com/astral-sh/setup-uv/releases/tag/v10.0.0
  - actionlint: https://github.com/rhysd/actionlint

## B4-8 the training stack in CI, K13 enforced

- **Fix.** A Linux job `train` in `tests.yml`:
  `uv pip install -e ".[dev,data,train]" --torch-backend cpu`, then
  `pytest -q -m "not slow" --cov=objdel --cov-report=term-missing:skip-covered --cov-fail-under=90`.
  The 3-OS `python` job keeps `[dev]` (lint + fast suite; the train tests skip there) and no longer reports coverage.
  `make cov` now also fails below 90 %.
- **CPU torch.** `--torch-backend cpu` makes uv take torch from `https://download.pytorch.org/whl/cpu` (only for the
  PyTorch packages; everything else stays on PyPI). Resolution checked with `uv pip compile --python-platform`:
  - Linux x86-64: `torch==2.14.1+cpu`, 0 `nvidia-*` packages (PyPI's default Linux x86-64 resolution pulls 22);
  - Linux aarch64: `torch==2.14.1+cpu`, 0 `nvidia-*`;
  - macOS arm64: **fails** (the CPU index has no macOS wheels), so the job is Linux only. On macOS, PyPI's torch is
    already CPU/MPS only, so a macOS train job would install without the flag (not added: one job covers K13).
  - `torch==2.14.1` (the `[train]` pin) accepts `2.14.1+cpu`: a pin without a local label matches any local label
    (PEP 440).
- **Verification.** The job's exact commands in `polycore-linux:arm64` (Python 3.12, `uv 0.12.23`, `--memory 3g
  --cpus 3`, script `ci/train_job.sh`): torch `2.14.1+cpu`, `torch.version.cuda` None; 615 passed, 45 skipped; coverage **91.85 %** (2,233 statements, 182 missed; below 90 %:
  `models/medsam.py` 0 % (`models` extra not installed; `src/objdel/models` since deleted, S4), `targets/simplify.py` 24 % (numba-jitted kernels are not
  traced), `train/dataset.py` 80 %). An earlier run in the same wave: 91.83 %.
  `test_b4_8_*` (marker removed).
- **Blocker found (not in my files, F3).** On a CPU-only Linux machine 10 train tests fail with
  `ValueError: Your setup doesn't support bf16/gpu. You need to assign use_cpu ...`:
  `test_train_configs.py::test_grpo_config_is_plan_d8[*]`, `::test_sft_config[*]`,
  `test_train_trl.py::test_every_process_receives_whole_groups[*]`,
  `::test_a_batch_that_splits_groups_across_processes_is_refused`. They build the production configs (TRL default
  `bf16=True`) without `use_cpu=True, bf16=False`; on the Mac transformers accepts bf16 (MPS), so `make test` is

  `test_breakit_wiring`'s chain does) or in `configs` (bf16 only when CUDA is available).

## I19 experiments import `tests.oracles`

- **Decision.** Accept and document (README rules). `tests/oracles/reward_harness.py` (520 lines) and
  `reward_variants.py` are used by four test modules and by `reward_gates` / `eval_demo`, which measure the same
  gates on the full data. One implementation for both is the point: the pytest gate and the data gate cannot
  drift. The alternatives are worse: moving the harness into `src/objdel` ships test-only code (perturbations,
  adversaries, bootstrap CIs) in the wheel; moving it into `experiments/` makes the library's tests depend on
  experiment scripts. Both scripts need data and an editable checkout anyway (`_objdel_repo.pth` puts the repo root
  on `sys.path`, so `tests.oracles` imports under `-I`, which `test_experiment_scripts` checks).
