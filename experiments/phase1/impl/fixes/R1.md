## 1. HIGH: series UID from the XML used as a path and inside the URL (review #1)

**Research.** DICOM PS3.5 §9.1 (https://dicom.nema.org/medical/dicom/current/output/chtml/part05/chapter_9.html):
"UID = <org root>.<suffix>". Components hold only the characters 0-9, "the first digit of each component shall not
be zero unless the component is a single digit", components are separated by ".", and a UID is at most 64
characters including the NULL pad. The NULL pad is a byte-level detail of DICOM encoding. XML text does not carry it,
so the check does not accept it. Python's `\d` also matches digits from other scripts (for example U+0661 Arabic-Indic one).
The grammar therefore uses `[0-9]`: https://docs.python.org/3/library/re.html#regular-expression-syntax.
`urllib.parse.quote(s, safe="")` percent-encodes everything outside the unreserved set:
https://docs.python.org/3/library/urllib.parse.html#urllib.parse.quote.

**Real data check (read-only, `-I`).** All 1,018 series UIDs in pylidc's database and all 1,036 `SeriesInstanceUid`
values in `data/raw/lidc_xml` (1,018 distinct) match the strict grammar. The longest is 64 characters, exactly the
limit. So the stricter rule (no leading zeros, at least two components) costs nothing. The alternative from the
review, `s in lidc.scans()`, would tie the fetch script to pylidc's database. That would make it unusable for
synthetic tests and for any series outside it. The grammar check is enough, because a grammatical UID is a single
path component that cannot be `.` or `..` and needs no URL quoting. A Hypothesis test checks this property.

**Fix.**
- `objdel.data.lidc.uid(s)` checks the grammar: `(0|[1-9][0-9]*)(\.(0|[1-9][0-9]*))+`, `len <= 64`, `fullmatch`.
  It raises `ValueError("not a DICOM UID ...")`.
- `lidc._series(root, path)` is the one place a series UID enters from the XML. It calls `uid` and names the file
  in the error. `parse`, `series_files` and `sop_z` all go through it. One bad XML makes the whole read fail loudly,
  before any disk or network access. It does not skip the file silently.
- `fetch_lidc_pixels`: `--series` values go through the same check, as an argparse `type`. It re-raises as
  `ArgumentTypeError`, because argparse prints a plain `ValueError` only as "invalid value". The URL is now
  `API + urllib.parse.quote(series, safe="")`, which leaves valid UIDs unchanged.

**Tests** (`tests/test_data_lidc.py`, no network; `urlopen` is monkeypatched to fail and to record its calls):
- `test_uid_refuses_everything_outside_the_dicom_grammar`: 18 bad strings. They include relative traversal, an
  absolute path, a query string, a percent-escape, newline and space padding, leading zeros, a NUL, Arabic-Indic
  digits, and 65 characters.
- `test_uid_accepts_dicom_uids`: `0.0`, the transfer syntax UID, and a real 64-character LIDC UID.
- `test_an_accepted_uid_is_one_plain_path_component_and_url_safe`: a Hypothesis property test.
- `test_planted_series_uid_is_refused_by_every_xml_reader`: `sop_z`, `series_files` and `parse`, each with a relative
  and an absolute planted UID.
- `test_fetch_never_touches_a_path_named_by_a_planted_uid`: the review's repro. A victim directory sits where
  `data/lidc_tmp/<uid>` resolves. After the fix, `main` raises, the victim's file survives, `urlopen` is never called,
  and `lidc_tmp` is never created. Before the fix, `main` deleted the victim and printed "FAILED".
- `test_fetch_cli_series_must_be_dicom_uids` and `test_fetch_url_quotes_the_uid`: the uid arrives as one
  `SeriesInstanceUID` query value.

All of these except the URL test failed before the fix. The URL test pins the URL format across the `quote` change.

## 2. LOW: RIGA test "with image" 94 vs 95 (review #4)

**Root cause.** Two places decided "has an image" with different predicates:
- `riga.item` gives an image to every item except `kind == "maxrg6"`. These are the BinRushed1 reconstructions, B3-1.
  The F7 reconstruction of Magrabia Female image48 is clean lossless TIFF and keeps its image, as the riga docstring
  states.
- `build_data` counted `kind == "prime"`, which drops the F7 item (`kind == "maxrg6:prime_is_rater1_copy"`).

The store is correct. A read-only count over `data/store/riga/*.parquet` gives these rows with an image:

| Split | Rows with an image | Rows with `reference == "prime"` |
|---|---|---|
| train | 547 | 547 |
| val | 58 | 58 |
| test | 95 | 94 |

The extra test row is `riga/Magrabia/MagrabiFemale/image048`. The report is what is wrong.

**Fix.** `build_data.riga_item(stats, photo, extracted, split, group, duplicates)` builds the item, then counts
`it.image is not None` on that item, the same way the LIDC counts already work. The predicate now exists in one
place, `riga.item`. **Test:** `tests/test_data_build.py::test_report_counts_the_riga_images_the_store_gets`. It runs
three items (prime, maxrg6, F7) through the helper. Before the fix the helper did not exist. With the old
predicate, it would count 1 instead of 2.

**Consequences, not acted on.**
- A rebuild of `data/store/build_report.json` would change `riga.with_image.test` from 94 to 95. Nothing else
  changes: the parquet files and the manifest do not depend on this counter. I did not rebuild the store.
- Two documents outside my paths repeat the old figure: `experiments/phase1/RESULTS.md:105` and
  `experiments/phase1/impl/fixes/F4.md:56` ("547 / 58 / 94"). RESULTS.md also says "The 51 maxrg6 items have
  `image = None`". The real count is 50: 51 references start with "maxrg6", but the F7 one keeps its image.
  The correct figures are 547 / 58 / 95 (700 images) and 50 items without one.

## 4. LOW: `store.load` did not check that a row matches its file (review #12)

`load` raises `ValueError("<rel>: row <id> belongs to <dataset>/<split>")` when a row's `(dataset, split)` is not
the requested file's. The check runs before `_check`, and its cost is one tuple compare per row.
**Test:** `test_data_store.py::test_load_refuses_a_row_of_another_file`, in two cases:
- a train file moved into the val slot;
- a LIDC file moved into a RIGA slot.

In both cases the manifest was rewritten to agree with the moved file, so the SHA-256 check passes and only the new
check can catch it. Both cases failed before the fix. The data-backed `test_store_verifies` and
`test_store_rewrite_gives_identical_bytes` still pass on the real store.
