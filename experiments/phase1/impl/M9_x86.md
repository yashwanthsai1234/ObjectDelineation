# M9: x86-64 build, tests and cross-architecture determinism (Docker linux/amd64)

Gate: R9 (plan §7: "Wheels + CI per OS; x86-64 tests pass in Docker; pins and target hash"), with K10 (determinism of
reward, targets and splits) checked across CPU architectures. This note covers correctness and determinism only.
x86 timing (K3/K4) is a Phase 2 entry gate on the first Vast box.

**Success criteria, written first:**
- the extension builds from source on linux/amd64 with the repo's flags, and the fast suite, lint, the slow K1/K2
  gates and the ASan/UBSan fuzz pass;
- the cibuildwheel x86_64 wheel is manylinux and abi3 (auditwheel, abi3audit);
- every hashed output (polycore rasters, topology, target texts, caches, reward terms, advantages, eval metrics,
  splits) has the same SHA-256 on the Mac (arm64) and in the container (x86-64), and twice in a row on x86. The
  coordinator later accepted one exception: the raw split scores (see "Coordinator decisions").

## Re-run (one command)

```
experiments/phase1/bench/x86.sh            # full: about 13 min on the Mac (Rosetta), exit 0 only if all pass
experiments/phase1/bench/x86.sh --quick    # no K1/K2 10k gates, 2,000-shape fuzz
experiments/phase1/bench/x86.sh --no-wheels   # no sdist + cibuildwheel (the only step that needs network)
```

Outputs go to `build/x86/` (git-ignored). `summary.txt` has every step's status and time, the failing tests,
lint findings and each hash comparison, with a known-cause line per differing section. The exit status is 0 only
when:
- every gated step passes (`*-info` steps are informational);
- Mac vs x86, both the editable build and the release wheel, differ only in the accepted sections
  (`xarch_hashes.ACCEPTED`, marked `ACPT`);
- x86 run 1 vs run 2 is identical in all 26 sections (`--strict`).

The IPP-off comparison is a diagnostic only. Per-step logs are in
`build/x86/io/*.log`, hashes in `build/x86/hashes-mac.json` and `build/x86/io/hashes-x86*.json`.

On a real x86 box (Phase 2, Vast), the same check runs natively, without Docker:
`.venv/bin/python -I -m experiments.phase1.bench.xarch_hashes --out vast.json`, then
`... xarch_hashes --compare build/x86/hashes-mac.json vast.json`.

Isolation:
- **Source.** A tarball of `git ls-files -co --exclude-standard`, i.e. tracked files plus untracked files that are not
  ignored. `data/`, `.venv/` and `build/` are never copied (the script refuses if they would be). No RIGA data leaves
  the Mac, and no Python in the container reads `data/`.
- **No AppleDouble files.** The archive is made with `COPYFILE_DISABLE=1 --no-mac-metadata --no-xattrs`. The first
  run lacked this: macOS tar added `._*.py` files for `com.apple.provenance`, and ruff failed on them.
- **Container limits.** `--platform linux/amd64 --cpus 3 --memory 4g --memory-swap 4g --network none`. Everything is
  preinstalled and the extension builds with `--no-build-isolation --offline`. The cgroup check in `env.txt` reads
  `cpu.max 300000 100000`, `memory.max 4294967296`.
- **Release wheel.** cibuildwheel runs with `CIBW_CONTAINER_ENGINE="docker; create_args: --cpus 3 --memory 4g"`.

Emulation: Docker Desktop runs amd64 under **Rosetta 2**. `/proc/cpuinfo` reports "VirtualApple @ 2.50GHz" with
sse4_2, avx, avx2 and fma, and no AVX-512. numpy's baseline is X86_V2 and its active dispatch target is X86_V3.

## The hash script

The corpus uses PCG64 integer draws only (platform-independent; no libm, no float sampling):
- 6 RIGA-like items: 6 raters, disc ⊃ cup, RGB;
- 12 LIDC-like items: 2–4 raters, int16 HU, nodules of radius 2–16 with holes, specks, pinches and abstaining raters;
- frame sides 50, 100, 200 and 250; 1,224 holes.

The production path covers:
- `frame` (crop; LIDC: lung window + bicubic upscale to 512);
- 300 random polycore shapes (off-grid vertices, self-crossings): `rasterize`, `validate`, `signed_area2`,
  `score_batch` at 1 and 3 threads;
- `instance_topology`, `signature`, `size_filter`, `betti`, `polygonize` on 147 frame masks;
- `build_target` (75 rater targets, with the reward's size rule and at all rules), `target_set_hash`;
- `ExpertCache.build` (24 caches) and the fingerprint;
- `reward.score_batch` on 16 completions per item (targets, shifts, scales, vertex drops, bow-ties, garbage,
  truncation, empty), `advantages_v4`, `topology_reward`;
- `eval.metrics`;
- `splits`: `lidc_split` (300 patients), `riga_split` (120 images), `riga.descriptor` + `near_duplicates`,
  `riga.keypoints` + `keypoint_duplicates` (8 synthetic fundus photographs, 4 same-eye pairs).

On the completions, 81 % are format-ok and 64 % legal. Floats are hashed exactly (float.hex or raw bytes), with one
digest per record, so `--compare` names the first differing record. The Mac runs it in 6–12 s and x86 under Rosetta
in about 15 s. Two Mac runs give 25/25 identical sections.

## Findings and proposed fixes (no library code edited; owners S2 and S1/S3, coordinator decides)

Each fix was checked in the sandbox by monkeypatching it into the hash script
(scratch `impl/M9/fixes.py`), running it on both architectures and twice on x86, and comparing with the current Mac
output.

**Finding 1: OpenCV's Intel IPP distance transform on x86 (caches, reward, eval).**
- `reward.cache.edt` calls `cv2.distanceTransform(src, DIST_L2, DIST_MASK_PRECISE)`. In the x86 opencv-python wheel
  (Intel IPP 2026.0.0, AVX2 "l9"), OpenCV 5's IPP HAL routes this to `ippiTrueDistanceTransform_8u32f_C1R` whenever
  `cv::getNumThreads() <= 1` **or** the image has fewer than 2^14 px
  ([hal/ipp/src/distancetransform_ipp.cpp](https://github.com/opencv/opencv/blob/5.x/hal/ipp/src/distancetransform_ipp.cpp)).
- The reward calls `cv2.setNumThreads(0)` with thread pools (score.py docstring), and RIGA/LIDC crops are ≤ 250 px,
  so this is the path every x86 cache takes.
- The code's own comment cites [opencv#24082](https://github.com/opencv/opencv/issues/24082) ("a rounding issue
  that leads to non-deterministic behavior between runs"). The issue reproduces it on an AMD Threadripper, so it is
  not a Rosetta effect. The fix, [PR #27432](https://github.com/opencv/opencv/pull/27432) in 4.12/5.x, only snaps
  values within 2^-11 of an integer. Non-integer distances still vary, which I measured: sqrt(45) came out as
  6.708204 and as 6.7082043 for the same input.
- arm64 has no IPP and runs OpenCV's `trueDistTrans`
  ([distransform.cpp](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/distransform.cpp)), whose last
  step is `std::sqrt` of an exact integer, which is correctly rounded.
- Ruled out:
  - Rosetta sqrt (sqrtss, sqrtps and vsqrtps all correctly rounded and repeatable on 2^20 inputs);
  - Rosetta FMA (vfmadd fused and repeatable);
  - input alignment (1 distinct output over 64 offsets).
- **F1 (S2, `src/objdel/reward/cache.py` `edt`):** compute it as
  `scipy.ndimage.distance_transform_edt(src).astype(np.float32)` (keep the all-nonzero guard).
  - scipy computes exact integer squared distances and a double sqrt; rounding that to float32 is the correctly
    rounded float sqrt. It is **bit-identical to OpenCV's non-IPP output on every corpus mask on both
    architectures**, so the Mac goldens and caches do not change.
  - Cost: 0.07 / 1.6 / 6.7 ms against OpenCV's 0.02 / 0.41 / 0.80 ms at 50² / 250² / 500². This is paid only in
    `ExpertCache` build and load (two EDTs per object per load), never per rollout.
  - Fallback, one line but process-global (it also changes `cv2.resize` and others): `cv2.ipp.setUseIPP(False)` at
    import.
  - Either way, add a test that builds the same cache twice and compares `dist_in_core` (it exists:
    `test_pickle_rederives_the_cache`, which is how the failure showed).

**Finding 2: `excursion_moment(m)` differs by 1 ULP for m = 3 and 7 (T5, so caches and reward).**
- S_m comes from `scipy.integrate.quad` over `stats.norm.pdf` / `cdf` / `sf`. `quad` itself is identical on both
  architectures; `np.exp` and the scipy normal functions differ (numpy SIMD exp, platform libm).
- The difference moves T5 by 1 ULP in 4 of 24 caches, and so the cache digests and the reward terms.
- **F2 (S2, `cache.py` / `spec.py`):** freeze S_m for m = 1..k_max as `float.fromhex` constants (the Mac values,
  which are the current goldens; S_1 = `0x1.0000000000001p+1`), with a test that recomputes them with `quad` to
  1e-12. The values are a property of N(0, 1), not data.
- **F1 + F2 together make `caches`, `reward.terms`, `reward.advantages` and `eval` identical across architectures
  and across x86 runs, with the Mac output unchanged (25/25 against the current Mac hashes).**

**Finding 3: the LIDC model image (frame.image; prepared `image_sha256`).**
- `targets.frame` upscales LIDC crops with `cv2.resize(..., INTER_CUBIC)`. On the 12 LIDC images:

  | Path | Pixels that differ (x86 vs Mac) |
  |---|---|
  | x86 with IPP | 413 k of 9.4 M (±1) |
  | x86 without IPP or any optimised path | 30 (±1, 6 images) |
  | PIL `Image.resize(BICUBIC)` | **0** |

  PIL resamples in fixed point
  ([Resample.c](https://github.com/python-pillow/Pillow/blob/main/src/libImaging/Resample.c)).
- Only the model input is affected: targets and caches use the masks, which are identical, and RIGA images are
  exact crops.
- It still matters for two things:
  - re-running `prepare_rl` on x86 gives different `image_sha256` values than the Mac's records;
  - x86 runs would train on slightly different pixels than the Mac's.
- **F3 (S1, `src/objdel/targets/frame.py`):** upscale with PIL BICUBIC. This *is* a behaviour change: the Mac's LIDC
  images change, so LIDC prepared images must be regenerated. Not for the no-behaviour-change sweep.
- Alternative, no code change: build `data/prepared` once (Mac) and ship it with its manifest, never rebuilding on x86.

**Finding 4: splits (decisions identical, raw values not).**
- `riga.descriptor`'s `np.linalg.norm` (float32 BLAS `sdot`; OpenBLAS kernels differ per architecture) changes 2 of
  8 descriptors in the last bit.
- The FFT NCC moves by ≤ 1.2e-7.
- ORB keypoints (CLAHE, INTER_AREA, Harris and angle float paths, with or without IPP) move RANSAC inlier counts by
  ≤ 3. Same-eye pairs give 234–260 inliers and others 2–8, so the same eye is still found at ORB_DUP = 22.
- **F4 (S3, optional):** `hp / (sqrt(sum(float64(hp)²)) + 1e-6)` makes the descriptors identical. It does not make
  FFT/ORB values identical, and the dedup thresholds absorb those (real RIGA: different eyes ≤ 16 inliers, same eye
  ≥ 29).
- Splits are computed once, when the store is built, and stored with a SHA-256 manifest. Do not rebuild the store on
  x86; if it is ever rebuilt, compare the split assignment (identical here), not the raw scores.

**Residual risk: AVX-512 on Vast.** Rosetta exposes no AVX-512, so these runs use numpy's X86_V3 dispatch. On an
AVX512_SKX CPU, numpy switches float64 `exp`/`log` to SVML kernels, whose results differ in the last bits from the
AVX2 kernels and from glibc
([numpy build options](https://numpy.org/doc/stable/reference/simd/build-options.html);
[SVML needs AVX512_SKX](https://git.almalinux.org/rpms/python3.14-numpy/commit/778b2e81a37a166b5879eb8d7f07832431856517)).
- `advantages_v4` uses `np.log` (`_topology`), and F2 removes `np.exp` from the cache path.
- **Phase 2 entry step:** run the hash script natively on the first Vast box and `--compare` it with
  `build/x86/hashes-mac.json`. If `reward.advantages` differs, either set `NPY_DISABLE_CPU_FEATURES="X86_V4"` for
  the reward process or accept bit-level (not decision-level) differences in advantages.
- Summation in numpy itself is implemented identically on every CPU ([FPRev, arXiv:2411.00442](https://arxiv.org/abs/2411.00442));
  BLAS is not, hence finding 4.
