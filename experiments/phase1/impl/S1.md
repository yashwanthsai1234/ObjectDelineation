- `checker/polygonize.py`, `checker/certify.py`:

  - `validate` computed the largest |coordinate| inline (the `M` loop). It now calls `detail::max_abs_coord`, the

  message. The repeat is removed.

  - xgrammar → https://xgrammar.mlc.ai/docs/latest/api/python/grammar.html (`geometry/text.py`).
  - Every other URL in the owned files returns 200, or 403 for bot-blocking hosts (OpenCV docs, SourceForge, World
    Scientific DOI), which was checked by hand.

## F3: LIDC upscale with Pillow bicubic (coordinator-sanctioned behaviour change, after the sweep)

**Finding.** M9 (`impl/M9_x86.md`, finding 3): `cv2.resize(INTER_CUBIC)` gives model images that differ by ±1
between x86 (413 k of 9.4 M pixels with IPP, 30 without) and arm64. Pillow's bicubic gave 0 differing pixels.

**Research.**
- Pillow `Resample.c`: https://github.com/python-pillow/Pillow/blob/main/src/libImaging/Resample.c
  - bicubic `#define a -0.5`;
  - output-pixel centre `center = in0 + (xx + 0.5) * scale`, with the filter evaluated at
    `(x + xmin - center + 0.5)`;
  - 8-bit images use `PRECISION_BITS = 32 - 8 - 2 = 22`: coefficients become integers
    (`(int)(0.5 + k * (1 << 22))`), accumulation is integer with a rounding bias, and the result is clipped.
  - With integer arithmetic there is no FMA or SIMD-width dependence, which is why it is the same on every CPU.
- OpenCV `resize.cpp`: https://github.com/opencv/opencv/blob/4.x/modules/imgproc/src/resize.cpp
  - `interpolateCubic` uses `A = -0.75f`;
  - source coordinate `(dx + 0.5) * scale - 0.5`, i.e. the same half-pixel centres;
  - 11-bit coefficients, with SIMD/IPP paths per architecture.
- Pillow `Image.resize` docs: https://pillow.readthedocs.io/en/stable/reference/Image.html#PIL.Image.Image.resize
- Pillow ≥ 10 is already a core dependency (`pyproject.toml`), and `objdel.data` uses it. Installed: 13.0.0.

**Change** (`src/objdel/targets/frame.py`):
- `np.array(Image.fromarray(image).resize((side, side), Image.Resampling.BICUBIC))`.
- The order is unchanged: int16 HU → lung window → uint8 → crop → upscale. Pillow resizes the same uint8 RGB array,
  so no dtype change is needed.
- `np.array` (a copy) keeps the result writable, as `cv2.resize`'s was. `np.asarray` of a Pillow image is read-only.
- The `cv2` import is gone from `frame.py`.
- The module docstring and References are updated.

**Tests.**
- New: `test_targets_frame.py::test_lidc_upscale_is_pillow_bicubic`. It was run red first, then green. It checks that
  the frame image equals Pillow's bicubic resize of the windowed crop at the frame side.
- S3's `test_breakit_data.py::test_lidc_upscaled_image_lines_up_with_the_mask` passes (image and mask aligned
  within one output pixel), as do all `test_targets_frame.py` and `test_breakit_data.py` tests (35).

**Before and after** (`scratchpad/impl/S1/f3/dump.py`; LIDC val all, LIDC train every 20th, RIGA val all; 1,510
frames):

| | RIGA (58) | LIDC (1,452) |
|---|---|---|
| image bytes identical | 58 | 0 |
| masks, box, scale identical | 58 | 1,452 |

- LIDC image change: max |difference| 33 levels (median per image 9), 48 % of values changed.
- The cause is the kernel (a = −0.5 vs −0.75), not the geometry: the sampling centres are the same.
- Targets are unchanged: `build_targets` rebuilt after F3 gives `manifest.json` byte-identical to `data/targets`
  (`target_set_sha256 1af819f4…`).
- Caches read only the masks, so they are unchanged too.
- **`data/prepared` must be regenerated** (LIDC `images/` and the `image_sha256` of each LIDC record).
- **Cost.** A 512² upscale takes 1.7–2.4 ms with Pillow against 0.2–0.4 ms with OpenCV (8 threads), for crops of
  50–250 px. That is about 15 s more over the 9,000 LIDC items in `prepare_rl`, and it is paid once per item.
