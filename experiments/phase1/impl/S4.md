### The one failure: present before any edit, not caused by the sweep

`test_train_dataset.py::test_r1_round_trip_on_the_prepared_train_set[lidc]` fails on the rebuilt `data/prepared`.
**10 / 23,469** LIDC train targets score `topo_any = 0`, with IoU_tc between 0.0 and 1.0. In every case I inspected
(`scratchpad/impl/S4/r1b.py`), the target comes from a rater whose whole mask is below the item's `min_area`. For
example, rater areas 9 / 36 / 21 px with min_area 5 give filtered signatures `()`, `(0,)`, `(0,)`; 4 vs 41 px gives
voters `(1,)` only; so does 3 vs 59 px. Under F2's B2-4 rule such a rater is not a voter, so its own answer can never
be topo-any.

These targets also go into SFT rows. This is a real mismatch between SFT and RL: SFT teaches answers that the RL
reward scores as having no rater topology. The coordinator / S1 (targets) / S2 (reward) should choose one of:
1. Drop non-voting raters' targets from `sft_rows` / the R1 set. This is a one-line filter in my
   `dataset.py`, but it changes behaviour and the prepared set's counts, so I did not make it in a
   behaviour-preserving sweep.
2. Restrict the R1 assertion to voting raters.
3. Accept the 10 and document them.

`test_breakit_wiring::test_real_lidc_sample_*` passes: its 5 sampled items contain none of these raters.

## Follow-up (coordinator decisions)

### 1. SFT teaches only voting raters (option 1)

- **Test first.** `test_train_dataset.py::test_sft_rows_teach_only_voting_raters` builds a LIDC item whose raters
  are a 12 px disc, an 11 px disc and a 4 px speck, which is below min_area 5. Its preconditions held: the speck's
  target is certified (`targets[2]` is not None) and the cache's `voters == (0, 1)`. It was red for the intended
  reason: `sft_rows` returned raters `['1', '2', '3']`. It is green after the fix. `grpo_rows` still keeps the item.
- **Fix (`src/objdel/train/dataset.py`).** `sft_rows` keeps rater i only if i is in the union of
  `objdel.reward.rater_answers(caches, names).values()`. This is the reward's own joint voting rule (B2-4), so there
  is one implementation; for RIGA it covers disc and cup jointly. The rule also covers the case where every rater
  abstains, in which all of them vote. An item without caches has one rater, and that rater is kept: it is the only
  voter. The caches are loaded with the record digests through a new helper `_caches`, which `cache_loader` now also
  uses, so the digest check has one code path. Measured cost: 7.7 s for 7,341 LIDC train items and 8.3 s for 547
  RIGA items (`scratchpad/impl/S4/loadcost.py`).
- **R1.** The test could not pass completely unchanged, because it scores `records()` targets, not SFT rows, and
  compares the count with the manifest's `rl_targets`. The changes:
  - `round_trip` skips non-voting raters (via `rater_answers`) and counts them.
  - The data test asserts `scored + abstained == rl_targets` and no failures, as before.
  - The data test also asserts that `sft_rows` emits exactly the scored targets for RL items. This new
    end-to-end check ties R1 to what SFT actually teaches.

  Both R1 cases pass: riga and lidc.
- **Rows dropped** (`scratchpad/impl/S4/sftcount.py`, real `data/prepared`):

  | split | targets | SFT rows | dropped |
  |---|---:|---:|---:|
  | riga/train | 3,282 | 3,282 | 0 |
  | riga/val | 348 | 348 | 0 |
  | lidc/train | 23,469 | 23,459 | **10** |
  | lidc/val | 3,444 | 3,444 | 0 |

- **Prepared files unchanged.** `prepare` and `_prepare` are untouched. A second scratch `prepare_rl` run after all
  follow-up edits gave 18,670 files byte-identical to the golden, and `data/prepared` itself is unchanged.
  The manifest's `targets` / `rl_targets` still count every rater's target. `prepare_rl`'s I5 token evidence still
  counts all train targets; the one RIGA answer over budget per model is unaffected, because no RIGA rater abstains.
- **Contract (EXECUTION.md §3, coordinator).** The `sft_rows` line should read "one row per *voting* rater (B2-4)",
  instead of "one row per rater".

### 2. `sample_eval.py` bf16

- **Test first.** `test_experiment_scripts.py::test_sample_eval_uses_bf16_only_on_cuda_cards_that_support_it`
  patches `torch.cuda.is_available` / `is_bf16_supported` and covers three cases: no CUDA (the Mac), CUDA without
  bf16 (pre-Ampere), and CUDA with bf16. It was red (no `bf16` helper), then green.
- **Fix.** `sample_eval.bf16() = torch.cuda.is_available() and torch.cuda.is_bf16_supported()` is passed to
  `grpo_config(bf16=...)`. On CUDA this is exactly transformers' own `is_torch_bf16_gpu_available()`, the predicate
  `TrainingArguments` checks, so a pre-Ampere card gets fp32 instead of an error. The Mac stays on fp32, as today.
  The `configs._bf16` helper is not reused because it enables bf16 on MPS, which the coordinator ruled out for
  sampling. The `is_available()` guard is needed because `is_bf16_supported()` returns True on any ROCm build.
- Sources: transformers 5.20.1 `utils/import_utils.py` `is_torch_bf16_gpu_available` (local `.venv` source, l.635);
  torch 2.14 `torch.cuda.is_bf16_supported(including_emulation=True)`, source in `.venv` `torch/cuda/__init__.py` l.231:
  https://docs.pytorch.org/docs/2.14/generated/torch.cuda.is_bf16_supported.html (cited in the script's docstring).
