## Design choices with evidence

1. **Shell/Python split: everything in Python, shells are shims.** I compared it with a shell-orchestration prototype of
   `launch` (`<scratchpad>/phase2/impl/O/launch_shell_variant.sh`):
   - Shell variant: 33 lines of bash, plus 6 extra policy subcommands (check-offer, check-cost, onstart, record-launch,
     record-destroy, record-ssh), a `jq` dependency and about 7 Python startups per launch. The poll / timeout / destroy
     branches are testable only through subprocesses.
   - Python variant: `cmd_launch` is 43 lines, uses no `jq`, and is unit-testable in-process.
   - The watchdog stays bash: it runs at container start, before any code is synced, so it cannot import `objdel`.
2. **The watchdog travels inside `--onstart-cmd`**, base64-encoded and unpacked to `/root/watchdog.sh`. It is not baked
   into the image, so a watchdog fix needs no rebuild.
   - The onstart string is 2,989 characters. The test bound is 4,000; Vast's onstart length limit is UNVERIFIED.
   - The string carries no secret. `CONTAINER_API_KEY` is injected by Vast and never written to `/etc/environment`.
3. **Idle rule.** The watchdog destroys only when `PULLED_OK` is newer than the start of the GPU idle period, not
   merely present. An older `PULLED_OK` would leave the outputs written after it unpulled.
   - Tested: never pulled → kept; pulled before idle → kept; busy GPU → kept; pulled during idle → destroyed;
     cap reached → destroyed.
4. **Cost guard (G10).** `spend()` = Σ ledger `cost_usd` (dph_total × elapsed at destroy) + live accrual.
   - `launch` refuses when spend + dph × cap > $15. No flag overrides this: passing it means editing `HARD_STOP`.
   - `launch` refuses when spend ≥ $10 unless `--owner-approved` is passed.
   - `sweep` alerts at $10 and destroys every instance at $15.
5. **H-GOV.** Every check runs on the saved offer JSON:
   - RIGA needs `riga_permission.granted == true` with non-empty `evidence` in `.vast-allowlist`, and
     `hosting_type == 1`.
   - `offers --riga` adds `datacenter=True` to the query and also re-filters the returned offers.
   - The snapshot stores bucket counts, not offers, so the test builds one offer per recorded offer: 237 community
     (`hosting_type 0`) and 34 Secure Cloud. Result: 237/237 refused; 34/34 allowed with permission, 0/34 without.
6. **RIGA key.** The identity is read with `security` into Python memory and passed only as the `input=` of
   `ssh … 'age -d -i /dev/stdin bundle-riga.tar.age | tar -x -C /dev/shm/riga'`.
   - The DRY_RUN=0 test with a fake `ssh` checks: the identity is on that command's stdin only; it is in no argv, no
     environment, no file under VAST_HOME and not in the onstart string; the ledger has the public recipient only.
   - DRY_RUN prints `<stdin: age identity from the keychain>` in place of the identity.
   - `age` is added to both images.
7. **Ledger.** Fixed columns. An unknown column raises `KeyError`. Secret-looking values raise `ValueError`: patterns
   `AGE-SECRET-KEY-`, `ghp_`, `github_pat_`, `PRIVATE KEY`, `Bearer `.
   - The GHCR PAT appears only in `create instance --login` (V10 forces that; the test asserts it is nowhere else).
   - The scoped API key reaches vastai as the `VAST_API_KEY` env var, never on argv.
8. **Transfer.**
   - Code goes as `rsync --files-from=<git ls-files -co --exclude-standard>`, incremental, with no tarball. The list
     always contains `tests/` (coordinator request: `k3_harness` → `phase1.reward_gates` → `tests.oracles`).
     `sync_up` then runs `python -I -c "import objdel._polycore, experiments.phase1.reward_gates,
     tests.oracles.reward_harness"` on the box. This works because the editable install's repo-root `.pth`
     (CMakeLists) puts `/workspace/src` on `sys.path`; verified locally under `-I`.
   - Every rsync carries `--exclude=data/raw/`. Any bundle path under `data/raw` (resolved) is refused before any
     command runs.
   - Pull verification relies on rsync's own whole-file checksum of every transferred file. A second `-c` pass would
     race with files the trainer is still writing.
9. **Dockerfile.phase2** = B5's stages (base → sampler `/opt/vllm` → phase2 `/opt/venv`) + `age`. The image-only extras
   `flash-linear-attention`, `kernels` and `causal-conv1d` are installed with `-c /opt/requirements.txt`, so they cannot
   move a pinned version (xarch_hashes unaffected). `causal-conv1d` is allowed to fail and then leaves
   `/opt/causal_conv1d.MISSING`: the slim image has no nvcc, and the `kernels` hub route is the fallback (D15). The
   final freeze is saved to `/opt/venv.freeze.txt`.
10. **image_check.sh** records the following in a JSON file and exits 1 unless the CUDA and matmul checks pass:
    - CUDA availability, and the bf16 8192³ TFLOPS against the A3 §3.1 peak (pass ≥ 0.6 × peak);
    - the GDN route per function (`chunk_gated_delta_rule`, `fused_recurrent_gated_delta_rule`, `causal_conv1d_fn`,
      `causal_conv1d_update`), classified by the bound function's `__module__` as hub / package / reference;
    - the `fla`, `causal_conv1d` and `kernels` specs, the `objdel._polycore` import, and the `/opt/vllm` vLLM import.

## Bundle builder (coordinator follow-up)

- `experiments/phase2/vast/bundle.py` (117 lines). It is a separate module, not a `policy.py` subcommand, because it
  needs only `policy.allowlist` / `die` and keeps `policy.py` from growing.
  - Usage: `python -I -m experiments.phase2.vast.bundle lidc|riga`.
  - Members: `prepared/{manifest.json, <ds>/, images/<ds>/, caches/<ds>/}`, `views/<ds>-*`, `eval_views/<ds>-*`.
    LIDC also requires the four lidc-val-shifted / lidc-val-rescaled / probe-precision / probe-topology dirs.
  - Format: PAX tar with SHA256SUMS as the first member, members sorted, mtime 0, owner 0, mode 0644.
  - Refusals: symlinks, any path whose resolved parts contain `data/raw`, and missing eval views.
  - RIGA: the tar is piped straight into `age -r <riga_recipient>`, so no plaintext touches the disk. The age output
    is not byte-identical (random file key); the tar inside it is.
- Tests (5): byte-identical rebuild after touching every mtime; SHA256SUMS correct per member; no riga or raw members;
  symlink into raw, data root under raw and a missing probe dir all refused; RIGA writes only `.age` + `.sha256` to the
  recorded recipient (fake `age`), and refuses when no recipient is recorded; `--help`; a `data`-marked size check on
  the real dirs.
- The `data` test skips right now: V's `eval_views/lidc-val-{shifted,rescaled}` are being rebuilt (absent at 10:00).
  The parts that exist (prepared LIDC + lidc-train view + both probes) total 1.8 GB on disk.
- On the box, `sync_up` extracts into `/workspace/data/lidc/` and runs `sha256sum -c` on both the `.sha256` sidecar
  and the SHA256SUMS inside. The run configs (R) must point their data roots at `/workspace/data/lidc/{prepared,views,
  eval_views}`; RIGA lives at `/dev/shm/riga/…`.

## What the owner must provide for Vast access (§4.1)

1. Vast account with a verified email, the Mac's ed25519 key added, and $25 prepaid credit with the low-credit alert at
   $10 (card vs no card: §8.3).
2. A scoped API key (`misc`, `instance_read`, `instance_write`, `user_read`; no billing or team scopes) in the keychain:
   `security add-generic-password -s objdel-vast-scoped -a vast -w`. Also `pip install vastai` on the Mac.
3. A private GHCR package and a read-only `read:packages` PAT in the keychain as `objdel-ghcr-read`.
   - Pushing needs `docker login ghcr.io` with a write-scoped token, used only on the Mac.
   - Then `IMAGE_REPO=ghcr.io/<owner>/objdel-vast build_images.sh --push phase2` and record the digest.
4. `experiments/phase2/vast/.vast-allowlist` (JSON):
   `{"image": "ghcr.io/<owner>/objdel-vast:p2-<hash>@sha256:…", "ghcr_user": "<owner>", "riga_permission":
   {"granted": false, "evidence": ""}, "riga_recipient": "age1…"}`.
5. RIGA only after written permission: an age key pair, with the identity in the keychain as `objdel-riga-age` and the
   recipient in the allowlist.
6. Optional: `brew install shellcheck age`.
