## Recommendations

### Adopt now
1. Trackio as the single tracker. Change: configs.py lines 174 and 195, report_to "none" -> "trackio" (via a run-spec key `tracker: trackio|none`, default trackio; tests keep "none"). Set run_name = "<run_id>-<config stem>" and env TRACKIO_PROJECT=objdel-phase-X in the Vast onstart/run chain (policy.chain / cmd_run). Reasons: native in TRL, local SQLite, no account needed, wandb-API so a later switch is a one-line change; our runs are scalar-heavy. Do not adopt W&B (account + SaaS, no gap to fill), MLflow (server + DB to run for one user) or Aim (separate server, thinner TRL support) now.
2. Persistence without hosting: add the trackio DB dir to pull.sh and to the final-pull file list; also copy it into runs/<id>/trackio/. View with `trackio show` on the Mac. Only set TRACKIO_SPACE_ID if the owner approves a Space (Q1). Keep rl.json and controller.jsonl as the source of truth for hashes and gates; Trackio is a view.
3. Structured logs: standardise one JSON-lines file per run, runs/<id>/events.jsonl, with the envelope {ts, run_id, step, phase, kind, trace_id=run_id, payload}. Reuse the existing controller.jsonl (callbacks.py) as the pattern; add kinds: step_time{generate_s,reward_s,update_s,sync_s,wake_s,sleep_s}, gpu{util,mem,power} from nvidia-smi sampler (already in profile.py), cost{usd_accrued} from policy.accrued (policy.py:190). Write async/line-buffered; no per-token labels (low cardinality). Alert rules (checked by watchdog.sh, not paged): GPU util <30 % for 5 min, step time > 1.5x median, spend > cost alarm, heartbeat age > N min. No Prometheus/Grafana/Loki/OTel stack: one box, one user, YAGNI.
4. NVTX ranges now, dashboards later: add a tiny module src/objdel/infra/nvtx.py (`range(name)` context manager using torch.cuda.nvtx.range, no-op when disabled via env OBJDEL_NVTX=1). Wrap: generate, reward, old_logps, update, sync, wake, sleep (the step phases already timed in step_time) and the checker calls. Capture on the box with `nsys profile --capture-range=cudaProfilerApi --capture-range-end=stop --trace=cuda,nvtx,osrt` around steps 3-4 (same steps profile.py traces), then `nsys stats` to a CSV pulled by pull.sh. Nsight view stays local on the Mac (Nsight Systems GUI); no web dashboard. Re-check flags against vllm 0.32.0 on the box (F10). Gate for phase C: GPU busy share from nsys, compared with the torch.profiler "update" busy share.
5. Keep the Vast CLI + policy.py as the GPU orchestrator. Reasons: it already enforces the owner's rules (US/CA, verified, reliability, preflight stamp, ledger, cap, orphan sweep) that SkyPilot/dstack/Modal would need re-implementing; SkyPilot has no documented country filter (F6). Small cleanups under phase CLEAN/E: split policy.py (628 lines) into vast/offers.py, vast/ledger.py, vast/remote.py; typed run spec (dataclass) replacing ad-hoc dicts. Add `resume` support instead (see 7).
6. HF Hub as the only checkpoint store, as today. Add: (a) push LoRA adapter + `run_spec.json` + `events.jsonl` summary per branch; (b) `hf_push` writes the Trackio run_name and git commit into the model card; (c) push at every N steps from the box in the background only if the run cap risk is high (adapter is small), otherwise at end. Keep refusals (private repo, no RIGA).

### Adopt later (with trigger)
7. Resume from checkpoint (not a new tool): save adapter + optimizer + step every K steps to runs/<id>/ckpt and HF branch `<run>-ckpt`; `train_rl --resume`. Trigger for SkyPilot managed jobs / Vast interruptible: only after this exists and the saving is worth ~30-50 % lower price (measure bid prices with offers.sh; do not assume).
8. Queues and async RL: do not add Redis Streams or NATS. If async RL is ever done, use the trainer's own process queue first (torch multiprocessing / TRL async rollouts) on 2 GPUs. Trigger for a broker: more than one rollout box feeding one trainer, or a verifier on another host. Then NATS JetStream (single binary, pull consumers, ack/DLQ) over Redis Streams for lease semantics; require idempotency key = (run_id, step, prompt_id, sample_idx), visibility timeout > p99 rollout time, bounded queue with backpressure, alarm on oldest-message age and consumer lag (messaging-streaming/task-scheduling skills). Not before.
9. Verifier service (phase 3D / after Phase E): decision record. Option A in-process CUDA extension (today): lowest latency, no copies, chosen. Option B gRPC (protobuf, streaming, deadlines, well-typed) for a remote verifier in a separate process, with inputs as shared-memory/CUDA IPC handles, not pixels over the wire. Option C HTTP/JSON: fine for a human-facing demo or a Space, bad for batches. Option D Triton: only if the verifier becomes an ONNX/TensorRT model (the 3D/voxel direction may add a learned model); Ray Serve only if the trainer moves to Ray. Recommend: define the verifier interface now as a Python Protocol `Verifier.score(batch) -> Scores` in src/objdel/verify (phase E layers) so a gRPC server wraps it later without touching the trainer. Trigger for the server: a second consumer (eval farm, 3D asset checker) on a different machine.
10. Hosted tracking: if multi-run comparison across rentals gets painful, publish a Trackio Space (free CPU) after owner approval (Q1); migrate to W&B only if sweeps/alerts are needed (API swap).

### Do not adopt
Airflow/Celery/Prometheus+Grafana+Loki+OTel collector/MLflow server/Aim server/Ray/Triton now: each is a stateful system to run, with no number showing a need (observability and messaging skills: YAGNI).
