### B.3.2 Data flow in words

1. `pool` draws `draws` shifted and `draws` rescaled windows per RL-eligible train item (`rl_eligible(raters)`, 2
   or more doctors), plus the centred view. It reads only geometry (union box, doctor areas). It writes no pixel. It
   counts every dropped item and draw.
2. The target law is the (size x offset) cell shares of the draw-0 shifted windows of the train items. This is the
   test view's generator law, measured on 7,341 train items of 557 patients. No val data shapes training.
3. `schedule` picks exactly `steps x 32` windows. It works in blocks of 20 steps (640 rows). In each block it fills
   centred, shifted and rescaled slots by fixed shares. For each off-centre kind it gives every cell a slot count by
   largest-remainder rounding of the target shares. Then it picks a window in that cell. So every trained prefix of
   whole blocks meets the target. One source item appears at most once in a step. No window repeats in a run.
4. Only the scheduled windows get pixels and caches (the existing `_prepare` path, with the window id as the key).
   9,600 windows is about the size of today's train-shifted view (7,341 windows, 1.2 GB) [measured: SD3 s2].
5. `quality` runs every gate on the store and on the rows root. A hard failure writes no manifest, so `train_rl`
   cannot load the root.
6. `train_rl` reads the rows in file order and checks the manifest hash, the count and the ordered-id hash. Step s
   gets rows 32(s-1) .. 32s-1.
7. Gate B1 uses the whole val (78 patients). The val halves (B1.0) serve only B3: B3.7 tunes on val-shape, Gate B3
   judges on val-select. Test is read once.
