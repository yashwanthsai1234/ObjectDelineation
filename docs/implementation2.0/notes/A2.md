## Findings

### F1. GED and HM-IoU definitions (LIDC protocol)
- GED = 2E[d(p,g)] - E[d(p,p')] - E[d(g,g')] with d = 1 - IoU. HM-IoU = build CxC IoU matrix between predictions and rater masks, Hungarian match, average matched IoU. [web: https://arxiv.org/pdf/2511.06857]
- LIDC set-up commonly: 2D slices centred on nodule (15,096 slices), up to 4 raters; when raters are fewer, ground-truth distribution uniform (1/4 each). [web: https://arxiv.org/pdf/2503.09797, https://arxiv.org/pdf/2407.00295]
- Recent LIDC results are reported in GED (ProSona -17% GED; a CVPR-2026 paper GED 0.1048 vs D-Persona 0.1358). [web: https://arxiv.org/pdf/2511.08046, https://arxiv.org/pdf/2605.08210]. Those methods emit MANY samples per image; ours emits one outline, so GED is a degenerate case (see R2).
- Empty-mask pitfall: IoU of empty vs non-empty = 0, so GED is dominated by detection errors; the authors of "Navigating Uncertainty in Medical Image Segmentation" argue GED is limited for model selection (abstract confirmed by WebFetch) and the search summary says they propose separate detection and segmentation-only distances. [web: https://arxiv.org/abs/2407.16367; the split-metric claim is from a snippet, unverified in full text]
- This matters here: 10.8 % of test images are misses (IoU<0.1) per BRIEF; a single GED number would mix miss rate and shape quality. [BRIEF s2]

### F2. QUBIQ protocol
- Official metric: soft ground truth = mean of raters; GT and prediction binarised at 10 thresholds 0.1..0.9 (organizer page says ten levels; 0.1..0.9 is nine values, so the exact grid is unclear), Dice per threshold averaged, then averaged over tasks. [web: https://qubiq.grand-challenge.org/participation/, https://arxiv.org/pdf/2303.16296]
- CURVAS-PDACVI 2025 uses thresholds 0.1..0.8 and sets Dice=1 when both are empty at a threshold: differs from QUBIQ. [web: https://curvas-pdacvi.grand-challenge.org/metrics-evaluation/]
- Primary paper to check: arXiv 2405.18435. The organizers note Dice has shortcomings for uncertainty. [web]

### F3. Cluster bootstrap for images nested in patients
- Consistent practice: resample patient IDs with replacement, keep ALL images of each drawn patient, recompute the metric, percentile CI; naive image bootstrap gives intervals too narrow. For paired model comparison use the same drawn patients for both models. Replicate counts range 500..50,000; no single standard. Cites Field and Welsh (2007) via one preprint. [web: https://arxiv.org/pdf/2607.02394, https://metricgate.com/docs/cluster-resampling-roc-confidence/ ; low-authority sources, preprints/tool docs]
- Repo status: signal.py already does nodule-cluster bootstrap B=2,000 (item id up to the slice) [code: src/objdel/eval/signal.py:15,103,202]; final_eval.py uses ITEM bootstrap [code: experiments/phase2/final_eval.py:10,34]. So final_eval CIs are too narrow if slices of one nodule/patient are in test. LIDC patient id is available from the DICOM series (not checked here) [estimate].

### F4. Test-time selection without labels
- Self-consistency = MBR decoding with Monte-Carlo risk; selection = pick the sample with max mean utility vs the other samples (medoid in utility space). [web: https://arxiv.org/pdf/2310.01387]
- Sample-based MBR is medoid identification; Correlated Sequential Halving approximates it under a fixed budget with little quality loss and no tuning. [web: https://aclanthology.org/2024.findings-acl.505.pdf (Jinnai and Ariu), snippet-level]
- Label-free best-of-N alternative: self-certainty (model-confidence score, NeurIPS 2025). [web: https://neurips.cc/virtual/2025/poster/120166]
- No source found applying this to segmentation masks; utility = IoU between candidate masks is the natural choice [estimate]. With n=8 samples the full 8x8 IoU matrix is trivial (28 pairs); CSH is unnecessary at this n [estimate].
- Majority vote on masks = per-pixel vote at 0.5 then re-polygonize; it can yield a shape no sample produced (possibly illegal), whereas medoid always returns a legal sample [estimate].

### F5. NVTX / Nsight Systems practice
- Pattern: wrap each step phase in NVTX ranges; run `nsys profile -t cuda,nvtx --capture-range=cudaProfilerApi --capture-range-end=stop` (or `repeat[]` for several windows) and start/stop capture around the steps of interest; narrow windows because traces grow (300 MB/step vs 1.7 GB for 30 steps reported). [web: https://dev-discuss.pytorch.org/t/using-nsight-systems-to-profile-gpu-workload/59, https://docs.nvidia.com/nemo/megatron-bridge/0.1.0/training/profiling.html, https://nvidia.github.io/TensorRT-LLM/0.19.0/performance/perf-analysis.html]
- PyTorch calls: `torch.cuda.nvtx.range_push/range_pop`; that `torch.cuda.profiler.start()/stop()` trigger cudaProfilerApi is my understanding, NOT confirmed by the sources [estimate].
- Repo: no nvtx use in src (grep empty) [code: src].

### F6. How SOTA RL repos measure step phases
- verl: per-step selectable Nsight profiling (list of steps in ppo_trainer.yaml), NVTX markers on role actions via DistProfiler.annotate, `discrete` option to split databases per role action, needs nsys on each node and the nvtx package; rollout shares the actor worker in the hybrid engine so one profiler config covers the step. [web: https://verl.readthedocs.io/en/latest/perf/nsight_profiling.html, https://verl-omni.readthedocs.io/en/latest/perf/profiler.html]
- Not found: a documented per-phase NVTX recipe for vLLM generate / ref logprob / reward / update. verl source would be the next place. [gap]
- Repo already logs wall-clock phases (time/sync_s, wake_s, sleep_s per commit history) [BRIEF/commit log]; NVTX adds GPU-side attribution (idle gaps, host syncs) that wall clocks cannot show.

## Recommendations
1. Bootstrap unit: change experiments/phase2/final_eval.py (lines ~10, 34) to reuse the nodule/patient-cluster draws from src/objdel/eval/signal.py (the function at line ~103). Add key `cluster_id` to saved per-item rows; report both item CI and cluster CI in final_eval.json for one release, then drop the item CI. B = 2,000 (matches signal.py); use paired draws when comparing two checkpoints.
2. Decide the cluster level: nodule vs patient. LIDC slices of different nodules of one patient correlate; use patient id if it can be derived from the series UID, else nodule id as signal.py does. Document the choice in docs/glossary.md. [open question Q1]
3. Metrics module: add src/objdel/eval/multirater.py with (a) per-image IoU vs each rater, (b) HM-IoU via scipy.optimize.linear_sum_assignment on CxC IoU matrix (for single prediction it reduces to max-over-rater matching only if C=1: define it explicitly, see Q2), (c) GED with d=1-IoU and, for a single deterministic prediction, report GED(p repeated) and the n=8 sample version, (d) QUBIQ-style soft Dice with thresholds 0.1..0.9 for comparability. Later port to GPU (phase D).
4. Never report GED alone. Report: miss rate (IoU<0.1), IoU on found images, and a segmentation-only distance computed only where both masks are non-empty/found; this separates detection from shape (supports F1). Define empty-vs-empty convention explicitly (Dice=1 as CURVAS, or exclude).
5. Save all n=8 answers per test image (phase A goal) as polygons plus legality flags, so selection and GED are computed offline without regenerating.
6. Selection: implement `select_medoid(masks)` in src/objdel/eval/select.py: utility = IoU matrix over LEGAL samples, pick argmax of mean off-diagonal IoU; tie-break by shorter token length. Compare against: first sample, majority-vote mask, oracle best-of-8 (upper bound, uses labels, report as ceiling only), and mean-over-samples (no selection). Evaluate with the cluster bootstrap of rec. 1. Skip Correlated Sequential Halving (n=8).
7. NVTX: add `src/objdel/infra/nvtx.py` (or train/ if no infra layer yet) with a context manager `phase(name)` that calls torch.cuda.nvtx.range_push/pop, a no-op unless env OBJDEL_NVTX=1. Wrap: generate, sync_weights, wake, sleep, pixel_build, h2d, ref_logprob, policy_forward_backward, reward_score, optimizer_step. Hook points: src/objdel/train/fast.py patches and callbacks.py. Keep names identical to the existing time/* log keys so Nsight and rl.json agree.
8. Capture recipe (documented in docs/runbooks): `nsys profile -t cuda,nvtx,osrt --capture-range=cudaProfilerApi --capture-range-end=stop -o <name> python -I -m experiments.phase2.train_rl ...` with `torch.cuda.profiler.start()` at step N and `stop()` at N+2 (add config keys `profile_start_step`, `profile_steps`). Verify on first run that the capture starts (see F5 caveat). Profile 2-3 steps only. This runs only on the rented GPU, so folds into the existing $3 budget.
9. Gate for phase C: record from nsys the GPU-idle fraction per step and host-sync count (cudaStreamSynchronize / cudaMemcpy in osrt/cuda API rows), compare to BRIEF numbers (~40 % idle, ~1,250 syncs); use the same NVTX ranges as before/after evidence.
10. Do not copy verl/Ray profiler plumbing (Ray-specific); copy only the idea: step-selectable capture plus named role ranges.
