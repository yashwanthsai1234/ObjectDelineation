## 1. Findings

### 1.1 Where the checker sits on the critical path (read this first)

- F1. RL scoring waits 5 ms per step of 14-23 s. `time/rewards_s` mean 0.0053 s over 771 steps
  [measured: runs/rl/train_rl/rl.json], 0.0046 s in R5 [measured: runs/r5/base/rl.json]; the checker runs on a
  prefetch thread on a lowest-priority stream [code: gpucheck.cpp:66-71, train/rewards.py:112-120]. So no checker
  inefficiency below changes RL step time. The value of fixing them is: (a) owner rule "CUDA for polygonizer",
  (b) 3D voxels (dense slots cannot scale, F12), (c) offline throughput (targets, eval), (d) CI/maintainability.
- F2. `check_masks` (the CUDA polygonizer) has NO production caller. grep over src/, experiments/phase2: only
  experiments/cuda_checker/compare.py:76, tests/test_cuda_checker.py:152, and tests/test_reward_one_checker_call.py:130
  (a monkeypatch that asserts the reward never calls it) [code]. Production polygonization is numpy
  (`checker/polygonize.py`) from `targets/build.py:93`. docs/research/notes/gpu_scoring.md:54 says why the scorer does not
  use rings: the size filter needs component and hole pixel areas, which labeling gives directly [code: docs note].
- F3. Measured speed of `check_masks` is old and pre-fix: RTX 4090, 2026-11-03, code 999969b + CMake fix, before the arena
  work (CK-1..3): LIDC 22x21 masks batch 8192 = 6,389 masks/s (156 us/mask), vs the Python certify path 2,551/s and
  OpenCV findContours 56,581/s; 512x512 noise (huge E) batch 4 = 19 masks/s [measured:
  experiments/cuda_checker/RESULTS.md:149-154]. No measurement exists for the current code. Needs one short rental
  (Recommendation 10).

### 1.2 Kernel inventory, complexity, traffic, launches, syncs

n = shapes/objects, V = vertices of a shape, E = unit boundary edges of a mask, S = 4(W+1)(H+1) slots, L = jump_rounds(S)
= ceil(log2 S) + 1 [code: gpucheck.cpp:958-964], k = raters, wpr = ceil(W/32). All kernels launch with
`for_each` = 128 threads/block, one thread per item, except `raster_kernel` (one warp per row, 4 warps/block) [code:
gpucheck.cpp:100-110, 417-427].

Polygon path (`check_polygons` / start of `score_polygons`, `launch()` [code: gpucheck.cpp:1110-1126]):

| Kernel | Items | Work per item | Notes / traffic (512x512 object, V = 130) |
|---|---|---|---|
| Precision :310 | n | O(V) scan for max |coord| | trivial |
| raster_kernel :388-427 | sum of H warps | each lane tests every 32nd edge: O(V/32) + O(W/32) words; per shape O(H V + HW/32) | Reads all V edges per row from L1/L2 (about 0.5 MB cached per shape), writes 8,192 words = 32 KB. i64 `/` and `%` (floordiv) only on crossing edges. Windows of 1,024 columns re-test all edges per window, so W > 1,024 multiplies edge work. 16 KB shared/block. |
| CleanRings :479 | rings | O(n_ring) | one thread per ring |
| EdgePairs :585 | vertices | O(V_shape) box test, classify on box overlap | whole-shape O(V^2/2); about 8.5 k box tests at V = 130 |
| ShapeTotals :626 | n (ONE THREAD PER SHAPE) | rings^2 pair loops; `any_witness` x `locate2` = O(n_a n_b) per ring pair when rings are not "apart", else O(n) | serial tail, see F8 |
Counts per call: 5 kernels, 1 memset, 1 H2D, 1 D2H, 1 stream sync per lane (two lanes when n >= 64) [code: :1663-1695].

Scorer (`score_words`, after the polygon launch [code: gpucheck.cpp:1548-1643]): 25 kernels.
RowBox (H items, wpr words), ObjBox (1 thread per object, serial over H rows), CropFill (bit to byte on the bbox+1 crop),
LabelInit/LabelMerge/LabelFlatten (3 kernels, one thread per crop row, union-find) run FOUR times (fg, bg, fg, bg: :1611-1617),
Count x2, Filter x2, Holes, Gather, ScoreRows (one thread per frame row: k*wpr popcounts + 3 planes + dist lookups only
at error pixels), ObjTerms (ONE THREAD PER OBJECT: serial loops of H x (1+k) rows, heapsort of the signature), SigScan
(ONE THREAD total), SigCompact.
Totals for `score_polygons`: 30 kernels, 5 memsets, 8 memcpys, 4 host syncs [code: :1784-1806, 1560-1640].
`score_masks`: 25 kernels, 4 syncs; plus a HOST bit-pack loop `pack_plane` over every pixel [code: :1139-1143, 1823-1824]
(512x512 mask = 262 k branchy iterations on one CPU thread; also in `add_tables` for k+3 planes per cache).
Resident table memory per object-cache: k rater planes + 3 planes (bits) + float32 `dist` (H*W*4 B). At 512x512, k = 4:
about 128 KB + 96 KB + 1 MB = 1.2 MB; the dist map dominates [code: :1720-1740; arithmetic].

Mask path (`check_masks` -> `check_mask_chunk` [code: gpucheck.cpp:966-1057]):

| Step | Kernels | Work |
|---|---|---|
| InitSlots :806 | 1, one thread per VERTEX ROW | for every vertex of the row: 4 byte loads for the 2x2 code, for each of 4 directions up to 4 more byte loads for the end vertex code; writes succ/lab/jmp/rkey for ALL 4 slots; bit-quad counts |
| LabelRound :845 | L, one thread per vertex row | `for_row_slots` :795 loops all 4(W+1) slots of its row and reads succ[] of each (4 B) to find the edges; only edge slots do the pointer jump |
| Pred, RankInit :860-881 | 2 | same dense sweep |
| RankRound :883 | L | same dense sweep |
| RingStats :898 | 1 | same sweep, atomics per edge |
| GatherRings, SetBase, ScatterCorners | 3 | rings or dense sweep |
Per chunk: 7 + 2L kernels (L = 22 for a 512x512 mask: 51 kernels; L = 13 for a 24x24 crop: 33), 1 memset of 12 B/slot (12.6 MB
at 512x512), 6 memcpys, 3 host syncs (ring count; ring info + quads; corners) with a host `std::sort` of the rings between
them [code: :1019-1056]. Scratch 64 B per slot (9 i32 arrays, i64 rbase, pts, rcount, i64 rarea, plus rec/info/base): 67 MB per
512x512 mask [code: :986-996; arithmetic]. A chunk holds at most 2^23 slots, so 7 masks of 512x512; chunks run one after another
on lane 0 only (lane 1 idle) [code: :1697-1718].

### 1.3 Why the polygonizer does about 500x more work than needed (and the real range)

Slots in use: E (800 for a r = 100 disc) of S = 1,052,676 at 512x512: 0.08 %. Yet every one of 2L = 44 rounds sweeps all
S slots, with only (H+1) = 513 threads, each walking 2,052 slots sequentially at a stride of 8,208 B between neighbouring
threads (uncoalesced; L1 reuse only within a thread) [code: gpucheck.cpp:795-804]. Bandwidth is not the issue: succ reads are
44 x 4.2 MB = 185 MB per mask [arithmetic]. The issue is work and parallelism: 16 warps on a 170-SM RTX 5090 and 2,052 dependent
branchy loads per thread per round.

[measured: CPU build of the same source on the Mac, 3 runs each, disc masks] time follows S, not E, confirming O(S log S):

| Mask | E | S | rounds (2L) | CPU build of check_masks | numpy polygonize |
|---|---|---|---|---|---|
| 512x512, r = 12 | 100 | 1,052,676 | 44 | 15.3 ms | 2.37 ms |
| 512x512, r = 100 | 804 | 1,052,676 | 44 | 15.1 ms | 2.24 ms |
| 256x256, r = 60 | 484 | 264,196 | 40 | 3.5 ms | 0.64 ms |
| 24x24, r = 10 | 84 | 2,500 | 26 | 0.038 ms | 0.085 ms |
8x more edges at 512x512 cost 0 % more; the work is the grid.

Work ratio S*2L / (E*2*(ceil(log2 E)+1)) [arithmetic from the table]: 28,949x (E = 100, 512x512), 2,619x (E = 804, 512x512),
1,092x (256x256, E = 484), 48x (24x24 crop). So H1's "about 500x" (256x256, E = 1,000) is the right order for its case but
UNDERSTATES a full 512x512 LIDC frame (2,600-29,000x) and OVERSTATES the bbox-cropped case (about 50x), which is what the CPU
target builder feeds (`_rings` crops first, build.py:80-89). `check_masks` itself never crops.
Estimated GPU time, 512x512, one mask [estimate: 44 rounds x ~50 us latency-bound sweep (2,052 L1-hit loads x ~40 cycles at
1.8 GHz) + InitSlots ~0.1 ms]: about 2-4 ms, against about 20-50 us for a bit-sliced one-block-per-mask tracer (H1 estimate
10-30 us per 256x256 mask). Unmeasured; Recommendation 10.
Other overwork: (a) `jump_rounds` uses max slots of the chunk, not the longest ring (a ring has at most the perimeter = n1+n2+n3+2nD
edges, known after InitSlots); (b) 3 host round trips; (c) one chunk at a time, one lane; (d) byte-per-pixel input (8x the bits).

### 1.5 Fingerprint coupling (hidden constraint on moving EDT or labeling)

reward/spec.py:50 folds `np.__version__` and `cv2.__version__` into the reward fingerprint; cache.py's `StaleCacheError` fires when
the fingerprint changes. Changing the EDT or labeling backend does NOT itself change the fingerprint, but if the new backend is not
bit-identical the stored caches (`dist`, tau, T5) differ from rebuilt ones. Any swap must be proven bit-identical on
tests/goldens, or the fingerprint must change and 24k caches be rebuilt (offline, minutes). [code: reward/spec.py:50, cache.py:87-93]

### 1.7 Correctness review of the kernels (no defect found)

Checked: slot index `(y(W+1)+x)*4+d` is i32 and below 67 M for a 4,096 mask; `rmax = S/8+1` (at most 2 outgoing edges per vertex,
at least 4 edges per ring); corner count at most S/2; the zeroed region [o_rcount, end) covers rcount, rarea, quads, nrings; rkey is
initialised for all slots in InitSlots; the mutex covers `views()` and the Registry; W or H = 0 masks give no edges; ring start
always a corner (outer: N then E; hole: W then S), so list ranking indices start at 0; union-find links larger root under smaller
(roots only decrease), so `find` without path compression is correct but can be slow on deep trees. 195,809 of 195,809 CPU-vs-GPU
cases matched [measured: experiments/cuda_checker/RESULTS.md:84-91, RTX 4090, 2026-11-03]. A single mask of 4,096x4,096 needs
about 4.3 GB scratch (64 B x 67 M slots) [arithmetic]: not a bug, but an unbounded-memory path for huge inputs.

### 1.8 Why dense slots cannot be the 3D design

3D crack tracing on a 512x512x100 volume has 513x513x101 = 26.6 M vertices; even 3 slots per vertex at 64 B is about 5 GB, and
the sweeps scale with that, not with the surface [estimate]. The sparse (edge or surfel list) design is therefore mandatory for
the stated future direction, which is the strongest reason to rewrite now rather than patch.

## 2. What is already good (keep)

Exact integer predicates with per-shape i64/i128 tiers; warp-per-row ballot raster with one coalesced store; resident expert
tables and device-only scoring (only per-object numbers return); pinned staging, grow-only arenas, one mutex, lowest-priority
stream; single-source CPU/nvcc build that doubles as the test oracle; `-ffp-contract=off` / `--fmad=false` for IEEE-identical
float64 terms [code: CMakeLists.txt:21-22]; cross-arch build check for sm_80/86/89/90/120 in cuda/docker_check.sh.

## 3. Recommendations (numbered, in order)

R1. Decide the polygonizer's job before coding: it feeds TARGETS (offline, 24.6 k rows, about 160 s of CPU). Treat it as a
   policy and 3D-readiness item. Do not claim an RL step-time gain (F1).

R2. New work-optimal `trace_masks` in cuda/gpucheck.cpp replacing InitSlots..SetBase (:806-956) and `check_mask_chunk`
   (:966-1057). One block per mask (grid-stride over row blocks for masks above about 5 K edges):
   (1) bit-sliced codes from packed rows (outE = s & ~q, outS = r & ~s, outW = p & ~r, outN = q & ~p; per word `popc` + block scan)
   emit edges compacted in (y, x, d) order; (2) successor by the 2x2 table, edge index from word rank, O(1); (3) ring id and rank
   in shared memory: min-label jumping and Wyllie on E edges (E <= about 5 K per block; above that a sparse ruling set), the log factor
   is irrelevant at E ~ 1 K; (4) ring offsets from a device scan, scatter corners; outputs stay on the device (`RingsDev`), D2H optional.
   Zero host sorts, zero mid-call syncs. Input: packed words (the scorer's layout), not bytes. Precedent for a separate CPU path
   exists (`raster()` has an `#ifdef` CPU body, :429-461): make the CPU path a sequential crack-following tracer, O(HW + E),
   which is also the oracle. Use thrust (host and device backends) for scans so the single-source build stays.
R3. Ring identity: derive (component, is_hole) from the scorer's fg-8/bg-4 labels (outer ring = foreground root of the start pixel;
   hole ring = background root, parent = foreground label of the pixel above its root), with the closed-form starts verified in
   section 1.6. Justification is targets (`_rings` needs `comp` and `hole` per ring, build.py:91-96, today from cv2), not speed.
   Fallback without labels: R2(3). ADR note: closed-form start changes ring ORDER only; `canonicalize` sorts parts and holes
   (geometry/shape.py), so target text and hashes should not change [code reasoning; assert with tests/test_targets.py hashes].
R4. Batched certify on device, replacing the per-rung `to_mask` + CPU checks in targets/build.py `_build` (:214-246): new
   `_gpucheck.certify_polygons(polys, src_masks, rules)` returning per object defects, intersection and union popcounts (IoU),
   `array_equal` as XOR popcount, and the size-filtered signature of the rasterized candidate vs the source mask's. Reuse
   `score_words`/labeling; extend `add_tables`/`Tables` to allow k = 1 ("the source mask is the table", gpucheck_py.cpp currently
   requires 2 <= k <= 32). build_views always passes the rule (`ma`), so the `_kept` interval loop (`lo == hi`) collapses to one
   signature compare; keep the CPU `_kept` only for probes with unknown unions. Whole ladder of a batch of rows = one call per rung.
R5. EDT on device: prefer cuCIM `distance_transform_edt` (exact, PBA+, `float64_distances=True`, then `astype(float32)`; sqrt of
   an integer in binary64 rounded to binary32 matches scipy by the repo's own innocuous-double-rounding argument in cache.py)
   for eval NSD (`metrics._surface`) and, optionally, `_band`/`edt` (cache.py:130-135,185-189). Gate: bit-identical to scipy on all
   tests/goldens and on 1,000 real caches, else the fingerprint changes (section 1.5). Alternative if the gate fails: separable
   Meijster with integer squared distances ([H1] section 7), about 100 lines.

## 5. Library check (web)

- OpenCV CUDA `cv::cuda::connectedComponents`: 8-way only (BKE), CV_32S labels, 8-bit single-channel input
  [web: https://docs.opencv.org/4.x/d0/d05/group__cudaimgproc.html]. Cannot do the 4-connected background, one image per call, label
  order is not "min pixel index" (repo's `Holes` rule needs it). Not suitable.
- CuPy `cupyx.scipy.ndimage.label`: arbitrary `structure`, docs state no algorithm or label order, "may synchronize the device"
  [web: https://docs.cupy.dev/en/latest/reference/generated/cupyx.scipy.ndimage.label.html]. One image per call: no batching.
- cuCIM `cucim.skimage.measure.label` has `connectivity` (4 or 8 in 2D), 32-bit labels, docs silent on order (examples raster)
  [web: https://docs.nvidia.com/cucim/latest/api/]. Same per-image call limit; needs a canonicalizing min-pixel pass.
  Conclusion: libraries do not fit a batch of 256 small crops; keep the custom batched labeling.
- cuCIM `distance_transform_edt`: "Exact Euclidean distance transform", PBA+, single precision by default, `float64_distances`
  option, indices may differ from SciPy only on ties [web: same page]. This one fits (R5).
- No library gives crack-edge (8,4) ring tracing with exact integer output (cuCIM `find_contours` is marching squares; not checked
  in detail); R2 stays custom.
