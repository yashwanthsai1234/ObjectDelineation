### 2.4 New findings not in the audit

N1. `Qwen3VLModel.forward` and `Qwen3VLForConditionalGeneration.forward` accept `mm_encoder_outputs` (a dict of precomputed
vision outputs: `pooler_output` list per image, `deepstack_features`), and raise if both it and `pixel_values` are given
(`modeling_qwen3_vl.py:1155-1185, 1323, 1375`). So the trainer's forward never needs `pixel_values` at all once the 32 images
are encoded. This is a supported public argument, not a hook. It makes `VisionCache` hash keys and the 1.61 GB tensor
unnecessary.

N2. All structural metadata that FastForward reads from the device (`window`, `prompt_groups` equality, `lengths`,
`by_length` order, per-image row counts) is derivable on the HOST before any tensor exists: completion lengths and
truncation flags come from vLLM's `completion_ids_list`; prompt lengths and image grids are constants of the prompt;
group membership is `row // G` (TRL's RepeatSampler repeats each prompt G times consecutively, `grpo_trainer.py:1331`,
`:1374`) and the dataset image identity is the OpenOnce object. TRL itself already chunks and shuffles Python lists in
the batch dict (`utils.py:1076-1078, 1114`), and `by_length.move` already reorders lists (`fast.py:383-386`), so a host
list riding in the batch stays aligned with the rows.

N3. Weight push touches ~700 parameters but only the 196 LoRA layers' weights change between steps (LoRA excludes the vision
tower and projector: fast.py module docstring and `VisionCache` rely on it). Everything else is identical after the first push.
Also vLLM's `load_weights` accepts an iterable, so ONE call with the generator replaces ~700 calls (TRL calls it once per
parameter: `vllm_generation.py:520-522`). Whether `load_weights` rebuilds a name map per call is [unverified] (vLLM not
installed); the 1.01 s awake sync [measured: r4 note] for ~0.1 ms of HBM traffic [estimate: 4.3 GB D2D at ~1.8 TB/s ~ 5 ms]
shows the cost is Python/launch overhead.

N4. dr_grpo's normaliser uses `max_completion_length` (`grpo_trainer.py:3289`). Lowering the outline limit (Phase C
"outline limit") rescales the loss by 1536/new_limit unless compensated. Not bit-comparable across limits.

N5. `beta = 1e-3` makes the reference pass mandatory (1.4-1.7 s, [estimate: two-point fit]). With beta 0 TRL skips it
(`grpo_trainer.py:2832`: `if self.beta != 0.0`). That is a training-objective change, not a transparent speedup.

## 3. Design principle for the replacements
"Host knows the structure, device holds the data." Never read a device tensor to learn something the host computed one
call earlier. Never build a tensor on the CPU that the GPU can build from a smaller one.

## 4. Recommendations (numbered, concrete)

Order = saving per risk. All savings [estimate] against R5's 23.4 s unless tagged. Expected total for R-1..R-5: about 3.5-5 s
(15-20 %), to be confirmed by nsys (G0).

### R-1. Pixels: 32 distinct images on the GPU, never 256 rows on the CPU (largest, 2.7-3.0 s of the 3.0-3.2 s CPU phase)
Two levels. Do level A first (small, bit-exact), level B after.

Level A, GPU ImageMemo (keeps TRL's flow):
- File `src/objdel/train/fast.py` `ImageMemo.__call__` (`:458-475`). For each missing image run the processor's own math on
  the device: uint8 HWC -> CHW tensor on `cuda`, call the same fast image processor with `device="cuda"` /
  `return_tensors="pt"` on a tensor input (the torchvision backend honours the input device), or run `rescale_and_normalize`
  + `patchify` directly (`image_processing_qwen2_vl.py:176-210`, `image_processing_backends.py:316-340`). Resize is identity for
  512x512 and image side % 32 == 0: assert it, and fall back to the CPU path for any other size.
- Keep the per-image rows as CUDA fp32 (32 x 1024 x 1,536 x 4 B = 201 MB). Build the 256-row output with one
  `index_select`/`repeat_interleave` on the GPU (1.61 GB D2D ~ 2 ms; transient VRAM +1.61 GB, same as TRL's own resident copy today).
  `Trainer._prepare_input` `.to(device)` then no-ops.
- Pass 1 (prompt ids only): memo the whole processor call by (prompt text, image shape, kwargs) and return `prompt_ids` plus a
  pixel-free `BatchFeature`; or override `_tokenize_prompts` in FastGRPO to tokenize once per distinct prompt (1 distinct
  prompt per step in LIDC [measured: docs/implementation2.0/notes/B_gpu_audit.md]). Keep the `one_pad` vLLM expansion check (`fast.py:680-686`) as the
  guard: it compares vLLM's expanded ids with the trainer's.
- Saving: 2 x 1.61 GB CPU memcpy (~0.3-0.5 s) + pass-1 processing (0.2-0.5 s) + pageable H2D (1.61 GB at ~6-12 GB/s: 0.15-0.3 s) +
  tokenization x2 (0.1-0.3 s).

Level B, row-to-image index + `mm_encoder_outputs` (removes `pixel_values` from the trainer):
- Replace the batch's `pixel_values` by a per-row `int32` image id (stays a tensor: TRL's `split_tensor_dict`, `shuffle`
  and our `by_group_length.move` index it with the rows) and keep `image_grid_thw` per row. Patch `trl_grpo.split_pixel_values_by_grid`
  and `unsplit_pixel_values_by_grid` to identity for these keys (same module-level swap pattern FastGRPO already uses for
  `shuffle_sequence_dict`, `fast.py:561-565`).
- Encode the 32 images ONCE per generation batch before the reference pass, no grad, in one vision call (the tower is frozen
  in RL: `configs.lora`, `fast.py` docstring). Store `BaseModelOutputWithDeepstackFeatures` per distinct image
  (`pooler_output` tuple split by `grid.prod/merge^2`, `deepstack_features` per level). Per chunk call
  `model(..., mm_encoder_outputs={"image": gathered_output})`, with no `pixel_values`/`image_grid_thw` kwargs.
- Delete `VisionCache.keys` hashing (`fast.py:262-272`), `prompt_groups`' pixel compare (`:66-72`), `per_row`, and the
  `pixel_values` plumbing in `packed_chunk` (`:218-222`). Removes S4, S9 (pixel part), S12 (about 380 syncs), frees ~1.6-3.2 GB
  of VRAM (`_buffered_inputs` copies + original), which is the room needed to try larger micro-batches or partial checkpointing.
- Risk: medium. DeepStack indexing and the `masked_scatter` image-embed placement stay HF's own, so the numerics are the
  same op sequence on the same values.
- Saving over level A: ~0.1-0.3 s plus memory; the sync removal is also what makes per-layer CUDA graphs possible later.

Bit-equality proof:
1. Level A: `torch.equal(gpu_pixel_values, hf_cpu_processor(...)["pixel_values"])` on >= 2,000 rendered views (centred, shifted,
   rescaled; the full `--train-views` set once on the box is 24,624 rows, ~40 s) and on all 32 images of 5 recorded steps. The
   ops are IEEE fp32 sub then div (separate kernels, no FMA contraction, `rescale_and_normalize` fused-factor form): expected
   bit-equal [unverified until run]. If not equal, stop: the vLLM-vs-trainer match (B2) and the logprobs would shift.
2. Level B: for one recorded generation batch, `torch.equal` of per-token logprobs and entropies from the old path (pixel_values)
   vs the new path (mm_encoder_outputs) for reference pass and all 16 update chunks; and equal `loss` and `grad` norm for 1 micro-batch.
3. End to end: step-1 reward, legal and IoU and logprob gap identical to R5's step 1 (the standard already used in R4/R5).

### R-2. Host-side metadata: remove every device read of values the host already has (0.3-0.8 s, plus it unblocks graphs)
- In `FastGRPO._generate` (`fast.py:618-627`) capture, from `completion_ids_list`/`prompt_ids_list` (already Python lists), per
  row: prompt length, completion length (0 if truncated and masked, mirroring `mask_truncated_completions`,
  `grpo_trainer.py:2604-2611`), image id. Store `self.meta` as numpy arrays.
- `by_length` / `by_group_length` (`fast.py:375-404`): compute `order` with `np.argsort(kind="stable")` on the host lengths. No
  `.tolist()`. Put a Python list field `host_meta` (row-aligned) in the batch dict so `move`/`split_tensor_dict` carry it with the
  rows (`utils.py:1076-1078`).
- `window` (`:36-47`): take `(first, longest)` from the chunk's `host_meta`; keep the bucket rounding; no device call.
- `prompt_groups` (`:62-78`): runs = rows with the same (image id, prompt length) from `host_meta`; drop the device equality
  compare. Keep a debug `assert` mode that runs the old compare once every 50 steps.
- `packed_chunk` (`:164-239`): build `seg`, `idx` (gi, pi, ri, ci), `lab` offsets from `host_meta` lengths into ONE pinned
  int64 staging tensor (`torch.empty(..., pin_memory=True)`, fill via numpy, `.to(device, non_blocking=True)`), instead of
  Python lists of tensors; build `tok`/`lab`/`mmt`/`posp` with gathers from the row tensors (`index_select` with `idx`), not a
  per-row `torch.cat`/`torch.full` loop. The `allow` mask (`:205-208`) builds on the device already.
- `FastForward` entry (`:108-115`): `rows`, `nimg` come from image ids and a constant per-image row count.
- `_compute_loss` metrics (S15): subclass override of `_compute_loss` for `loss_type == "dr_grpo"` only, copied from TRL
  (`grpo_trainer.py:3141-3400`) with the seven `.item()` calls replaced by device tensors appended to `self.is_stats`-style
  accumulators and read once in `FastGRPO.log` (`fast.py:604-616`). Guard: at start-up compare a hash of
  `inspect.getsource(GRPOTrainer._compute_loss)` with the pinned value and raise on a TRL change (same private-name check as
  Phase A). Alternative with no copy: none found; the `.item()`s sit inside closures (`global_masked_mean`) that cannot be patched.
- Fused-head syncs (S14, S13): feed precomputed indices. In the packed path `idx` (`fast.py:197`) already holds the label
  positions: call the head with `compact=False` style full reshape only if memory allows, or precompute the boolean `nonzero`
  once per forward and pass it. DeepStack: replace the boolean `index_put` in `_deepstack_process` with `index_add_`/`index_copy_`
  on `visual_pos_masks.nonzero()` computed once per chunk on the host (positions of image pads are known: they are the
  prompt's constant image-run). Both need a small patch of HF/TRL code (monkeypatch `Qwen3VLTextModel._deepstack_process`,
  gated by a version check). Do this last; it is the riskiest of R-2.

Bit-equality proof: (a) test mode runs old (device read) and new (host) derivations side by side on 50 recorded batches and
asserts equal `(start, keep)`, runs, `order`, `seg`, `idx` (`torch.equal`, integer data: must match exactly); (b) loss and
metrics: `torch.equal` on `loss`; metrics equal after one flush (same float32 ops; sum order is unchanged because each
accumulator adds the same micro-batch values in the same order); (c) DeepStack: logprobs `torch.equal` on one chunk.

### R-3. Rope positions: closed form on the GPU, keyed by prompt (0.1-0.3 s, removes S5, S6, 9.8 MB H2D)
- File `fast.py` `RopeCache.positions` (`:336-348`). Prompt positions depend only on (prompt tokens, image grid): compute them once per
  distinct prompt with HF's own `get_rope_index` on the 32 distinct prompt rows (or one row per distinct grid + prompt, a constant
  in LIDC), cache the (3, P) tensor on the device. For each row the completion positions are `end + (cumsum(mask) - 1)` on all
  three axes where `end` = last prompt position + 1 (text group continues the last prompt text group:
  `modeling_qwen3_vl.py:994-1003`), and 0 on padding (zeros init: see verdict table). In torch: one `cumsum`, one `where`, one
  `cat` for the whole 256-row batch; no `.cpu()`.
- Keys: use the host `image id`/prompt id from R-2, not row bytes.
- Applies while prompts end with text after the image (LIDC/RIGA chat template: image then text, generation prompt last
  [code: HF loop handles any group order, but this closed form assumes completion follows a text group]). Assert it at start-up with the
  token types of the prompt; fall back to HF `get_rope_index` otherwise.

Bit-equality proof: `torch.equal(new_positions, hf_get_rope_index(...)[0])` for all 256 rows of every recorded batch (50 batches),
including truncated/masked rows, 1-token and 1,536-token completions (property test with random lengths in
`tests/test_train_fast.py`). Integer data: exact. Runtime option `--check-rope` asserts on step 1 and every 50th.

### R-4. Weight sync: one call, LoRA-touched weights only, in place (about 1.0 s measured sync -> ~0.1 s; wake/sleep stays)
- File `fast.py` `sync_without_merge` (`:495-504`) and `lora_merged_params` (`:696-717`).
- Step 0 (and any resume): push everything once as today (vLLM's weights come from the checkpoint; do not assume they equal the
  trainer's base).
- Later steps: yield only the names in `deltas` (the 196 LoRA layers' `.base_layer.weight`), values `p.data + delta.to(p.dtype)`
  exactly as now (so same W + d in bf16). Stacked vLLM params (`qkv_proj`, `gate_up_proj`) still go through vLLM's own weight
  loader, so the mapping stays vLLM's.
- Replace TRL's per-parameter loop: set `vg.sync_weights = fast_sync` that does `empty_cache()` once, `wake_up(["weights"])` if
  sleeping, then ONE `model.load_weights(generator)` call, then `reset_prefix_cache()`. Peak extra VRAM = one delta tensor (generator
  is lazy). Keep the `time/sync_s` timer (`fast.py:652-668`) so G0 can compare.
- Awake variant (optional, separate flag): `vllm_enable_sleep_mode=False`. R4 showed no step-time gain (-0.05 s) [measured] and costs
  11.2 GB (vllm_gpu_memory_utilization 0.35 x 32 GB) of resident memory; ONLY worth it if R-1 level B frees enough VRAM and a
  profile shows wake/sleep (0.37 s) on the critical path.
- Request-level alternative evaluated and rejected for now: vLLM native LoRA serving avoids merging but slows decode
  (docs/implementation2.0/notes/B_gpu_audit.md §4.6 [estimate: 10-30 %]) and changes the numerics versus the trainer's merged W + d.

Bit-equality proof (the strong one, cheap): after sync, compare every vLLM parameter against the old path's: for the old and new
sync run on the same adapter state, copy vLLM's `named_parameters()` to CPU as int16 views and `torch.equal` all ~2.13 B values
(a one-time preflight, ~seconds). Also assert the untouched parameters are unchanged between syncs (hash before/after). Then
step-1 identity as in R4/R5. This also closes audit item B10 (no GPU bit-check after N syncs).
