## Findings

### Sizes (the numbers that decide everything)
F1. LIDC store: 7,341 / 1,084 / 2,200 items (train/val/test), Parquet+zstd 1.96 GB / 0.29 GB / 0.59 GB, int16 HU + bit-packed masks, sorted rows, SHA-256 manifest. [measured: data/store/manifest.json; code: src/objdel/data/store.py:1-40]
F2. RL rows: 24,624 = 8,208 centred + 8,208 shifted + 8,208 rescaled; 8,208 = 7,341 + 289 disagreement items x 3 extra copies (oversample x4). So only 22,023 DISTINCT images (3 x 7,341); 2,601 rows (10.6 %) are repeats of an image. [measured: data/prepared/manifest.json (289 disagreement items, 7,341 items); arithmetic 24,624-22,023 = 2,601 = 289x3x3]
F3. Views on disk today: PNG, mode RGB, three identical channels (R==G==B checked), 512x512, mean 162,772 B each. `data/views`: 51,400 files; `data/prepared`: 18,670 files; `data/lidc_slices`: 1,998 files. Many small files make rsync/HF upload/Vast restore slow. [measured: find/du in REPO/data; t1_bench.py]
F4. As ONE gray uint8 plane a view is 262,144 B. All 22,023 distinct train views = 5.77 GB gray (17.3 GB if stored RGB). All 24,624 rows expanded = 6.46 GB. [measured: t1_bench.py arithmetic]
F5. Decode cost per view on the Mac (single thread): PNG RGB 2.9-3.3 ms; Parquet binary zstd-3 of the gray plane 0.30 ms (100.5 KB each, smaller than the RGB PNG at 162.8 KB); zstd-1 0.47 ms / 118.9 KB; zstd-6 0.29 ms / 92.9 KB. [measured: t1_bench.py]
   -> a one-time preload of all 22,023 views = ~6.6 s (zstd-3) vs ~63 s (PNG). Both are noise against a GPU rental, but PNG decode is per-opened-image inside the step today (the P1 12.96 s/step finding that created OpenOnce). [code: src/objdel/train/dataset.py:253-262]
F6. Hashing: SHA-256 of a gray 512x512 view 0.165 ms; BLAKE2b 0.277 ms; SHA-256 of the RGB view 0.32 ms. Hashing all 22,023 views = 3.6 s. No need for BLAKE3/xxhash. [measured: t1_bench.py]
F7. Per-image patch tensor: Qwen3-VL image at 512 px = 1,024 patches x 1,536 floats; fp32 = 6.29 MB; x 256 rows = 1.61 GB, which equals the "1.61 GB fp32 pixel_values" in the brief. So the heavy object is the processed pixel_values, not the stored image. Precomputing patches for all views (uint8 patch form 1.57 MB x 22,023 = 34.6 GB) does not fit; keep gray uint8 (262 KB) and patchify on device. [estimate: 1,024x1,536 from the 1.61 GB figure; arithmetic exact, patch grid not re-derived from the processor]

### What the code does today
F8. Pixel contract: each record holds `image_sha256 = sha256(repr(shape) + bytes)` of the decoded RGB array; `dataset.py` decodes every PNG and refuses a mismatch. [code: src/objdel/train/dataset.py:86-87,174-175]
F9. The resize is Pillow bicubic on purpose: bit-identical across CPUs, while `cv2.resize` differed by +-1 between x86 builds. [code: src/objdel/targets/frame.py:21,162] -> A GPU re-render of views from int16 HU would change pixels (no bit-identity with Pillow) and shift train vs eval. Reject "render views on the GPU" unless a parity test shows max abs diff 0. 
F10. B1 audit already proved: every built view equals a fresh re-simulation from the store (0 mismatches, 150/150 pixel hashes), splits are leak-free (0 shared sha256 across patients/splits). So views are a pure function of (store item, box, side, window, op, noise seed). [measured: notes/B1.md F1-F3]
F11. TRL 1.17.1 takes images from the prompt messages (`part["image"]`) and runs the image processor on them; our ImageMemo wraps `image_processor` and keys by `id(image)` + kwargs, so any object returned by the data layer must be the SAME Python object for the 8 rows of a view. [code: trl/trainer/grpo_trainer.py:1764-1772 in .venv; src/objdel/train/fast.py:420-480]
F12. vLLM colocated uses `vllm_gpu_memory_utilization` 0.35 with sleep mode (~11 GB of 32 GB). [code: src/objdel/train/configs.py:192-193] Free GPU memory during the trainer phase after model+LoRA+activations is not measured here.

### Candidate formats (verdict for 7,341 images / 22,023 views)
| Option | Evidence | Verdict |
|---|---|---|
| Parquet (current store) | Already deterministic, manifest-hashed, zstd; HF datasets also writes Parquet. Row-group random access is fine because we preload everything (F5). | KEEP for canonical store; ADD one Parquet for views (R1). |
| Arrow IPC / memory-map | Zero-copy mmap of a fixed-width column. Our rows are fixed 262,144 B, so a raw `.npy` memmap does the same with no dependency. Larger on disk (5.77 GB vs ~2.2 GB zstd) so worse to ship to a rented box. | Use only as the in-memory form after decode. Not a file format. |
| Lance | Vendor benchmarks claim large random-access wins, versions per mutation, tags. Independent paper finds Parquet tuned correctly is within range and Lance scan is comparable [paper: arXiv 2504.15247]. No independent 2026 image-versioning benchmark found. [web: https://arxiv.org/abs/2504.15247, https://www.lancedb.com/blog/lance-format-v2-2-benchmarks-half-the-storage-none-of-the-slowdown] Our whole bank fits in RAM, so random access never touches disk. | DO NOT ADOPT now (new dependency, no number forces it). Revisit only if the bank exceeds host RAM. |
| Zarr v3 (+sharding) | Fits chunked N-D volumes; KvikIO gives GPU-direct reads via `GDSStore` with zarr-python 3.x, but GDS needs supported storage and falls back to a bounce buffer with no speed-up otherwise; no official doc found that GDSStore reads sharded v3 directly. [web: https://docs.rapids.ai/api/kvikio/stable/zarr/, https://pypi.org/project/czarr/] | NOT for 2-D crops. PRIME CANDIDATE for the 3D voxel phase (OME-Zarr, sharded). Note as direction, build nothing now. |
| WebDataset (tar shards) | Designed for sequential streaming of TB-scale data; our RepeatSampler needs random index access over 24,624 rows and 6 GB fits RAM. [estimate: known design, not re-verified on the web] | REJECT. |
| GPU-resident uint8 tensors | 5.77 GB gray (F4). Per step only 32 distinct images x 262 KB = 8.4 MB cross PCIe (4.0 ms at ~2 GB/s pageable, ~0.2 ms at ~40 GB/s pinned) [estimate: PCIe rates]. So residency saves <= a few ms of a 23.4 s step. | OPTIONAL via a config switch; default pinned host. Value is only in letting a GPU patchify kernel read the bank directly (phase C). |
| Pinned host cache | 5.77 GB page-locked; `index_select` on a pinned tensor then `.to("cuda", non_blocking=True)`. Cheap, no VRAM pressure beside vLLM (F12). | DEFAULT for `ViewBank`. |
| GPU decode: nvImageCodec | GPU: JPEG (hw+CUDA), lossless JPEG, JPEG2000/HTJ2K, TIFF. PNG: CPU only (OpenCV fallback). v0.10.0 beta, `pip install nvidia-nvimgcodec-cu12/cu13`; Blackwell not mentioned on the README. [web: https://github.com/NVIDIA/nvImageCodec] | REJECT. PNG not GPU-decoded; lossy JPEG changes pixels; JPEG2000-lossless is slower and heavier than raw/zstd for 0.26 MB images. |
| GPU decode: DALI | `fn.decoders.image` uses nvImageCodec; PNG listed as supported, GPU decode documented only for JPEG/JPEG2000; conflicting doc versions. [web: https://docs.nvidia.com/deeplearning/dali/user-guide/docs/operations/nvidia.dali.fn.decoders.image.html] | REJECT (heavy dependency for ~0.3 ms/image problem). |
| GPU decompression: nvCOMP zstd | Real. B200 microbenchmark ~155 GB/s zstd output; Blackwell Decompression Engine up to 600 GB/s peak. [web: https://arxiv.org/pdf/2512.02189, https://docs.nvidia.com/cuda/nvcomp/decompression_engine_faq.html] Whether the RTX 5090 has the DE is not established by the sources. | REJECT for now: CPU preload is 6.6 s once (F5). Keep as a phase-D curiosity only. |
| DVC | Git-native, content-addressed, `dvc repro`; needs a remote and adds `.dvc` files into git. Sources are blogs, not primary docs. [web: https://reintech.io/blog/dvc-vs-git-lfs-vs-lakefs-ml-data-versioning] | NOT NEEDED: we already have manifests with SHA-256 (F1,F10). |
| lakeFS | Server infrastructure for data lakes, multi-team. | REJECT. |
| HF datasets repo + revision | Revisions are git commit SHAs/tags; private repos load with a token. One forum report: `load_dataset(revision=<old commit sha>)` raised FileNotFoundError; so pin via `snapshot_download(revision=sha)`. [web: https://huggingface.co/docs/datasets/main/en/upload_dataset, https://discuss.huggingface.co/t/load-dataset-file-not-found-error-when-specifying-commit-id/89281] | USE as the transport + immutable snapshot (private dataset repo, same free-account pattern as the model repo). |

Content hashing for views, decided from F6/F8/F10: two hashes per view, both SHA-256.
- `view_id` = SHA-256 of canonical JSON of (store_manifest_sha256, item_id, kind, box, side, window, op, noise_seed, renderer_version). Identifies WHAT the view is (spec hash; reproducible without pixels).
- `pixel_sha256` = existing `_pixels_sha` but computed on the gray plane (shape + bytes). Identifies WHAT IT LOOKS LIKE. Dedup key: rows with equal `view_id` share one bank row (2,601 repeats, F2).

## Recommendations (numbered, concrete)

R1. New module `src/objdel/data/viewbank.py` (library, with `tests/test_viewbank.py`): a "view bank" = one Parquet per (dataset, split, kind-set) + a sidecar index.
  - File: `data/views/<name>/bank.parquet`, schema `view_id:string, item_id:string, kind:string(centred|shifted|rescaled), box:list<int32>(4), side:int32, window:list<int32>(2), op:string, noise_seed:int64, gray:binary(262144 B raw uint8, 512x512), pixel_sha256:string`. Settings follow store.py `WRITE_OPTIONS` but `compression_level: 3`, `use_dictionary: False`, `write_statistics: False`, row group ~64 MB (about 640 views at 100 KB), rows sorted by `view_id` (deterministic bytes, same K10 rule as store.py).
  - API: `write_bank(views, out)`, `load_bank(path, device="pinned"|"cuda"|"cpu") -> ViewBank`, `ViewBank.__getitem__(view_id) -> np.ndarray (512,512) uint8` (a cached read-only view, same object on repeat, so ImageMemo's `id(image)` key still hits), `ViewBank.take(view_ids) -> torch.uint8 (n,512,512)` for the phase-C GPU patchifier.
  - `load_bank` verifies every `pixel_sha256` on load (3.6 s for 22,023 views, F6) and the file SHA-256 against `manifest.json`.
  - Size: ~2.2 GB zstd (22,023 x 100.5 KB) vs 2.39 GB PNG shifted+rescaled only, and 3 files instead of 51,400 [measured/estimate: F3,F5].
R2. Channel handling: store gray, expand to 3 channels at the last moment (`np.broadcast_to` / `.expand(3,...)` on device). Gate: a unit test that `np.repeat(gray,3,-1)` equals the current RGB PNG decode for 300 views (R==G==B was checked on 1 view only; test all 22,023 in the migration script before deleting any PNG).
R3. Migration script `experiments/phase2/build_bank.py` (module-run, `-I`): reads `data/views/lidc-train-{shifted,rescaled}` and `data/prepared` (existing PNG + jsonl), asserts each PNG's `image_sha256` (current RGB contract), writes the bank, then asserts every gray plane equals R channel. After it passes once, ARCHIVE the PNG trees to `archive/` (repo rule: no old code/data beside new). Do not change the pixel recipe (F9): the bank stores Pillow-produced pixels; no GPU re-render.
R4. Replace `dataset.OpenOnce` image path: rows carry `view_id` only; `grpo_rows_views` (`dataset.py:240`) builds rows with the bank lookup; keep the "same object per view" guarantee (F11). `datasets.Image(decode=False)` PNG opens go away (the P1 cost). Open check: that TRL `part["image"]` accepts a numpy array (it passes images to `image_processor`, which accepts arrays) and that vLLM's `multi_modal_data` accepts the same object; verify in the C-phase test before deleting OpenOnce.
R5. Config keys in the typed run spec (phase E): `data.bank_path`, `data.bank_sha256`, `data.bank_device: pinned` (allowed: `pinned|cuda|cpu`), `data.verify_pixels: true`. Default `pinned`; allow `cuda` only after phase C measures free VRAM (F12).
R6. Dedup by `view_id`: `rl_shifted.yaml` rows (24,624) index into 22,023 bank rows; the oversample x4 stays a sampling weight in the row table, not extra pixels. Test: 24,624 rows, 22,023 unique `view_id`, 2,601 repeats.
R7. Versioning without a new tool: (a) keep SHA-256 manifests per artifact (store, bank, targets); (b) one private HF DATASET repo (e.g. a second repo beside the model repo, storage only, token already in use) holding `store/*.parquet` (2.84 GB LIDC) + `bank.parquet` + manifests; (c) each run writes into its run spec `data_revision = <HF commit sha>` plus the three manifest SHAs; (d) download with `hf download <repo> --repo-type dataset --revision <sha>` (or `huggingface_hub.snapshot_download(revision=sha)`), not `load_dataset(revision=...)` (forum failure report). Preflight before a rental: download + `verify_manifest` is the data half of the existing preflight rule. Do not adopt DVC, lakeFS or Lance. Uploading is an owner-run command (git/HF write rule): give the command, do not run it.
R8. Keep the canonical Parquet store (`src/objdel/data/store.py`) unchanged. Only addition: expose `store.manifest_sha256(root)` (hash of manifest.json, already done ad hoc in `build_eval_views.py:90`) so `view_id` can include it.
R9. Hash helper: one function `objdel.data.hashing.sha256_json(obj)` (canonical `json.dumps(sort_keys=True, separators=(",",":"))`) and reuse `_pixels_sha` (moved out of `train/dataset.py:86` into `data/hashing.py`, gray shape). Remove the other ad-hoc `hashlib` calls in `build_eval_views.py` and `build_views.py` when touched (CLEAN phase).
R10. Test/eval views get the same bank format (`kind` in `{test-shifted, test-rescaled, val-*}`) so eval and train load pixels the same way; test views were built on a GPU box and are not local (B1 F3), so rebuild them locally once with the same seed and compare to the R5 box's hashes before first use.
R11. Future 3D voxel phase: plan OME-Zarr v3 with sharding, `zarr-python` 3.x, optional KvikIO `GDSStore`; decide only after confirming GDS works on a Vast North-America host (preflight probe `gdscheck`). Build nothing in phase X.
R12. NOT recommended (record in an ADR, `docs/decisions/`): GPU image decode (nvImageCodec/DALI), nvCOMP, Lance, WebDataset, DVC, lakeFS. Each with the reason above; revisit triggers: bank > host RAM (Lance/Zarr), PNG decode back on the hot path (none after R4), multi-node (WebDataset).
