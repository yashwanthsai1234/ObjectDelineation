## Context (what already runs)
- Stack pinned: torch 2.14.1, transformers 5.20.1, trl 1.17.1 [code: pyproject.toml:19-21]. No flash-attn, liger-kernel or kernels package in the venv (listing of .venv site-packages showed none) [measured: venv listing].
- Attention today: SDPA with a 4-D bool mask; flash backend refuses masks so it runs mem-efficient [prior: docs/research/notes/packed_attention_research_2026-11-08.md:17]. fast.py asserts sdpa or eager for shared_prefix [code: src/objdel/train/fast.py:209-216].
- Log-prob head: TRL already has a fused lm-head / chunked Triton log-prob that scores label positions only and never builds (B,T,151,936) logits [prior: B_gpu_audit.md:343, trl/trainer/utils.py:1569-1720]. Remaining waste: 2 boolean-index host syncs (utils.py:1694,1697).
- Compile: `compile_text_layers` compiles each decoder layer (regional), dynamic=False, BUCKETS of 8 widths, recompile_limit raised to 64 [code: fast.py:720-731]. It is OFF in train_rl; only g_probe `--compile` uses it [prior: rl_code_optimality_review_2026-11-08.md:44]. reduce-overhead crashed (cudagraph trees output overwritten in no-grad old-logprob pass) [prior: cuda_streams_graphs_review_2026-11-08.md:54]. DeepStack boolean index sits inside layers 5, 11, 17 and blocks compile of those layers [prior: B_gpu_audit.md:335-336].

- Update phase (16 micro-batches, fwd+recompute+bwd) = 7.67 s of the 23.4 s R5 step; 4.5-5.0 s of it does not scale with tokens (launch/host overhead) [prior: B_gpu_audit.md:92]. So kernel work can win at most a few seconds per step; the fixed overhead matters more than FLOPs.

## Findings

### F1 Liger Kernel
- Qwen3-VL: README now lists `apply_liger_kernel_to_qwen3_vl` (RoPE, RMSNorm, SwiGLU, CE, FusedLinearCE) [web: github.com/linkedin/Liger-Kernel]. An earlier version raised NotImplementedError "Under development" (PR 911); a SwiGLU no-op fix (PR 1175) was open [web: PR 911/1175 search]. First working release version NOT found. [needs check]
- Fused GRPO loss: `LigerFusedLinearGRPOLoss`, variants include dr_grpo; TRL exposes it as `use_liger_loss=True` [prior: G_gpu_techniques.md:215]. Claim: up to 40 % less peak memory on Qwen3-0.6B, no speed claim [prior: huggingface.co/blog/liger-grpo]. It chunks on batch and needs padded [B,L,H], which conflicts with the shared-prefix packed rows [prior: G_gpu_techniques.md:216-218]. Our loss is also customised (sequence_mask IS, cap 3, truncated masking) and would be bypassed or duplicated.
- Liger README: CuTe DSL backend targets SM90/SM100/SM110; sm_120 not mentioned. Triton/cuTile fallbacks exist [web: Liger README]. Speed numbers shown are B200, not 5090.
- Speed evidence for us: none. TRL already avoids full logits, so expected gain ~0 s [estimate, matches G_gpu_techniques.md:39]. Memory is not our limit at 16x16 for the head; checkpointing is for the layers.
- Risk: medium-high (loss path rewrite, fast.py conflicts, version churn).
- Liger model-level patches (RMSNorm, SwiGLU, RoPE Triton kernels): these cut launches per layer. Plausible small gain on the 4.5-5.0 s fixed part, but only if they do not break our RopeCache injection (fast.py:296-300 injects positions via forward pre-hook) [estimate]. Untested.

### F2 FlashAttention 2/3/4 on sm_120
- sm_120 has Ampere-style mma.sync, no WGMMA/tcgen05/TMEM, 99 KB SMEM. FA3 = Hopper only. Official FA4 targets SM100/SM103 (B200/B300) [prior: G_gpu_techniques.md:~205; web: FA issue 1987 says "FA4 B200/B300", blackwell geforce != enterprise].
- FA4 sm_120 port: CuTe-DSL fwd/bwd/varlen PRs are in tag `fa4-v4.0.0.beta5`; PR 2634 (adds public API routing) is OPEN, unmerged, built from a fork branch; no env vars needed. Fwd D128 ~parity to 1.07x FA2; bwd parity to slightly ahead, 0.85-0.95x for causal MHA long seqs; `deterministic=True` backward unsupported; supports GQA, head dims 64/96/128/192/256 [web: github.com/Dao-AILab/flash-attention/pull/2634]. Bundle: huggingface.co/SecondNatureComputing/flash-attn-4-sm120 [prior].
- So even in the best case FA4 on 5090 is about FA2 speed (parity), not the 2x seen on B200. FA2 itself is slow on Blackwell per one unverified comment [web: issue 1987].
- Our real attention problem is the MASK, not the kernel: flash refuses masks, so the model runs mem-efficient [prior: packed_attention_research:17]. Flash varlen avoids the mask: `torch.nn.attention.varlen.varlen_attn` (torch >= 2.12) needs no new dependency; cuDNN is chosen only on sm90/sm100 so sm_120 gets the flash kernel; F.sdpa-flash on a 5090 ~187 TFLOPS fwd [prior: packed_attention_research:19]. Estimated gain 0.7-1.1 s/step [estimate, same note]. Not yet measured on sm_120 backward.
- Hub kernels: `attn_implementation="kernels-community/flash-attn2"` works without compiling; `flash_attention_2` falls back to the Hub kernel if flash-attn is absent; v3 builds fail in GQA backward on CUDA 12.8 [web: huggingface.co/docs/trl/main/en/kernels_hub... page fetched]. Whether a Hub FA2 cubin exists for sm_120 on torch 2.14 is UNVERIFIED (G note says FA2/FA3 cubins do not cover sm_120).
- Risk: FA4 high (open PR, fork build, no deterministic bwd, CUDA-13/CUTLASS-4.4 dependence); varlen_attn medium-low.

### F3 torch.compile regional compile
- Regional compile (compile one repeated block) cuts compile time (67 s -> 9.6 s in a DiT) at the same speedup [web: PyTorch devlog 2026-05-11, inference on H100]. Not a training number.
- In our code it is built but unmeasured in production: no measured result for compile on the R5 path found in notes [measured: none]. The blockers are real: 8 widths x grad/no-grad x adapter on/off recompiles; DeepStream bool index in 3 layers; reduce-overhead conflict with vLLM cumem allocator [prior].
- FA4 entry points are excluded from Dynamo (run eager) so a compile plus FA4 mix works [web: PR 2634].
- Gain estimate: small. Fixed overhead in update is 4.5-5.0 s of launch cost; fusing RMSNorm/SwiGLU/rotary elementwise ops could cut it by ~1 s [estimate]. High risk of recompile storms because the widths change with every batch.

### F4 Chunked logprob
- Already in TRL 1.17.1 (fused head + Triton `_ChunkedLogProbFunction`, `_use_triton`) [code: trl/trainer/utils.py:61, 1569-1720]. Nothing to adopt. Only improvement: pass precomputed label indices to avoid 2 host syncs per chunk (~1,250 syncs per step overall, brief section 2) [prior: B_gpu_audit.md:343-345].
- Unsloth's newer approach: one sample at a time plus sequence chunking via `unsloth_logit_chunk_multiplier` (default max(4, ctx//4096)); logits memory example 3.3 GB -> 0.207 GB at batch 4, ctx 8192, 128K vocab [web: unsloth.ai/docs grpo-long-context]. Same idea as TRL's fused head; our vocab is 151,936 and chunks ~430 tokens, so no gain.

### F5 Activation offload vs checkpointing
- Checkpointing is mandatory at 16x16 (OOM without) and costs a recompute pass [code: configs.py:186]. Partial checkpointing (off on k of 28 layers via `GradientCheckpointingLayer.gradient_checkpointing`) estimated -1 to -2.5 s/step; needs box memory headroom data [prior: B_gpu_audit.md:299-304, 428].
- Activation CPU offload (PyTorch `torch.autograd.graph.save_on_cpu`, or `torch.distributed.algorithms._checkpoint` offload): PCIe 5 x16 ~ 50-60 GB/s real; offload cost scales with activation bytes and would add stalls while the host is already the bottleneck (40 % GPU idle). [estimate] No evidence it helps; reject.
- Selective checkpointing (`torch.utils.checkpoint` with `create_selective_checkpoint_contexts`, save matmul outputs, recompute pointwise): saves recompute FLOPs at some memory. Candidate but no measured data for this model [estimate].

### F6 Unsloth GRPO internals
- Memory tricks: linear cross-entropy chunking, sharing GPU memory with vLLM (saves ~16 GB in their Llama 3.1 8B 20K ctx setup) [web: unsloth.ai/blog/grpo]. "90 % less VRAM" is vs TRL+FA2 in one setup, Unsloth's own benchmark [web].
- We already share memory with vLLM (colocate + sleep mode, util 0.35) [code: configs.py:189-190]. Unsloth replaces model classes and patches TRL; it conflicts with fast.py's overrides of `_get_per_token_logps_and_entropies` and our pinned stack. Qwen3-VL GRPO support in Unsloth: not verified here. Reject as a dependency; steal ideas only.

### F7 TRL native options (v1.17.1 installed)
- Kernels Hub: `attn_implementation` accepts hub kernel ids, pinnable via `@v2` [web: TRL docs kernels_hub page].
- `use_liger_kernel` (HF Trainer arg: applies model-level Liger patches) and `use_liger_loss` (GRPO loss) exist [web: TRL liger docs; prior G note]. Model patch is the lower-risk of the two, but the GRPOTrainer path with vision models and our FastForward is untested.
- Native async/tree attention in TRL uses Hub FlashAttention [prior: D_rl_infra.md:110]; not for our colocated single-GPU loop.

## Recommendations (numbered)
1. ADOPT NOTHING that touches the loss. Keep TRL's fused log-prob head; reject `use_liger_loss` and Unsloth. Reason: expected ~0 s gain, conflicts with packed rows and custom IS/loss. Reuse existing code instead.
2. Remove the 2 host syncs in the log-prob path: in `FastForward.packed_chunk` (fast.py:~197, `idx` already known) pass precomputed label indices to the TRL entropy/logprob helper (override or thin wrapper of `selected_log_softmax` call). Gate: NVTX shows fewer cudaStreamSynchronize; logprob tensors identical (tests/ parity test) .
3. TEST (30-s micro-benchmark, then decide): `torch.nn.attention.varlen.varlen_attn` as a custom `AttentionInterface` function for trunk+branch packed rows, replacing SDPA-with-mask. Compare fwd+bwd against (a) SDPA 4-D mask, (b) FA4 sm120 bundle at head_dim 128, GQA, widths 430-1536. Adopt varlen_attn if bwd works on sm_120 and parity tests (current packed tests) pass; est. 0.7-1.1 s/step [estimate].
4. DO NOT adopt FA4 in the trainer now. Revisit only if PR 2634 merges to main and a wheel exists; require `deterministic=True` is not needed. Re-check at the next rental planning.
5. Liger MODEL patches (`use_liger_kernel=True` or `apply_liger_kernel_to_qwen3_vl(rms_norm=True, swiglu=True, rope=False, fused_linear_cross_entropy=False, cross_entropy=False)`): TEST in one 15-step g_probe arm after item 3, with rope=False so RopeCache injection stays valid and loss kernels off. Pin the version that ships a working Qwen3-VL patch (verify on PyPI/GitHub releases). Gate: step-1 logprobs equal to eager within bf16 tolerance; s/step gain >= 3 %.
6. torch.compile: keep `compile_text_layers` off by default (train_rl has no flag). Make it a later arm only after (a) the DeepStack index fix in layers 5/11/17, (b) a single width bucket policy (or `dynamic=True` for the sequence dim with `mark_dynamic`), (c) `TORCH_LOGS=recompiles` shows <= 8 recompiles over 20 steps. Never use reduce-overhead while vLLM sleep mode (cumem) is active.
7. Checkpointing: run one rental arm "partial checkpointing" (turn checkpointing off for k layers, k = 4, 8) with memory print after update; keep micro-batch 16x16. Reject CPU offload. Gate: no OOM, >= 1 s/step gain.
8. Add a startup guard (phase A item "TRL private-name check") for every private name used here: `_get_per_token_logps_and_entropies`, `selected_log_softmax`, `_use_triton`, `add_fused_lm_head`. A silent TRL rename would drop the fused head.
