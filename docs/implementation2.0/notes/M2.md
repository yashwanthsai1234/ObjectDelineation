### 1.2 Tokens per image at 512x512

GDN layers keep a per-sequence recurrent state not in this number: 32 value heads x 128 x 128 = 524,288 values per layer, x 24 layers = 12.6 M values = 25 MB (bf16) or 50 MB (fp32) per sequence; 256 live sequences = 6.4 or 12.9 GB [estimate; state dtype in vLLM not verified]. vLLM also pads hybrid pages; the real figure needs a GPU run.

Card is 31.84 GiB (32,607 MiB) [measured: REPO/runs/r5/box.txt:160].

Colocate plan for Qwen3-VL-4B (arithmetic):
- Today (2B): util 0.35 x 31.84 = 11.1 GiB; weights 3.96 GiB; assume ~1.2 GiB activation + graphs; KV about 5.9 GiB = ~55k tokens [estimate; the 1.2 GiB overhead is assumed, not measured].
- 4B at util 0.35: weights 8.27 GiB + 1.2 = 9.5 GiB leaves 1.6 GiB KV = **~11k tokens**. One step holds 32 prompts x 256 image tokens shared via prefix cache (~10k) plus 256 answers (mean outline 131 tokens, tails to 1,536): ~44k tokens needed on average. 0.35 is too small.
- To match the 2B's ~55k tokens: 8.27 + 1.2 + 7.55 (55k x 147,456 B) = ~17.0 GiB = **util ~0.53-0.55**.
- Trainer while vLLM awake: bf16 weights 8.27 GiB + LoRA r16 all-linear: 36 layers x 917,504 = 33.0 M params (2B: 28 x 622,592 = 17.4 M); fp32 weights+grads+Adam = 16 B each = 0.53 GB [estimate]. Total awake ~17.0 + 8.3 + 0.6 = ~26 GiB of 31.8: fits, ~5 GiB headroom for the GPU scorer and CUDA context.
- Update phase (vLLM asleep): gradient checkpointing is on for RL [code: configs.py:186]. 16 rows x ~1.8k = ~29k tokens; layer inputs saved 36 x 29k x 2560 x 2 B = 5.3 GB (2B: 3.3 GB) + one recomputed layer ~3 GB + weights 8.3 + LoRA 0.6 = ~17-19 GiB [estimate]. Fits without changing 16x16 micro-batches.
- vLLM sleep offloads weights to host RAM: ~8.3 GiB pinned per run (2B: ~4 GiB). Check host RAM on the rented box in preflight [estimate].
- Full fine-tune is out: weights + grads + Adam for 4B = ~16 B x 4.4 B = 71 GB. LoRA only [estimate].

### 1.4 vLLM and TRL support
- Our pins: vLLM 0.32.0, torch 2.13.0, transformers 5.19.0 in the vLLM venv; train venv torch 2.14.1, transformers 5.20.1, TRL 1.17.1, PEFT 0.21.2 [code: experiments/phase2/docker/locks/vllm.txt, train.txt, pyproject.toml:19-23].
- TRL 1.17.1 accepts vLLM 0.22.0 <= v < 0.33.0 [code: .venv/.../trl/import_utils.py:107], so 0.32.0 is in range.
- Qwen3-VL-4B: same architecture class as the 2B already running under vLLM 0.32 and TRL 1.17.1 colocate. No new vLLM or TRL code path. Supported.
- Qwen3.5: "Full support for the Qwen3.5 model family", GDN, FP8, MTP landed in vLLM v0.17.0 [web: https://github.com/vllm-project/vllm/releases/tag/v0.17.0]. 0.32.0 is newer, so inference works. Prefix caching for hybrid (Mamba-style) layers is described as "currently experimental" in the vLLM Qwen3.5 recipe; a CUDA-graph capture size above the Mamba cache size triggers `assert num_cache_lines >= batch` (lower `max_cudagraph_capture_size`, default 512) [web: https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3.5.html; the page covers the 397B/35B models, not the 4B dense, so applicability to 4B is inferred].
- TRL source has no qwen3_5 / linear_attention / hybrid special-casing [code: grep of .venv/.../trl returned nothing]. TRL has no known Qwen3.5 GRPO+colocate+LoRA bug report that I could find (one search, no hit); Unsloth's page says GRPO for Qwen3.5 needs its own inference "because vLLM does not yet support Qwen3.5" (stale page vs. vLLM 0.17 notes) [web: https://unsloth.ai/docs/models/qwen3.5/fine-tune]. Treat Qwen3.5+TRL as untested.
- Our weight sync (`lora_merged_params`, merged W+delta pushed by HF name) never uses vLLM LoRA, so vLLM's LoRA coverage of GDN projections is irrelevant [code: src/objdel/train/fast.py:696-717]. Open risk: HF names `in_proj_qkv`, `in_proj_z`, `in_proj_b`, `in_proj_a` must map onto vLLM's fused GDN projections inside `load_weights` (not verified).

### 1.5 Attention type and the FastGRPO patches
Qwen3-VL-4B (full attention): every patch applies unchanged.
- `RopeCache` hooks `get_rope_index` + `compute_3d_position_ids`: same model_type `qwen3_vl`.
- `VisionCache`: same visual tower (frozen, excluded from LoRA).
- `packed_chunk` (shared prefix): needs a 4-D mask via SDPA/eager, valid for full attention.
- `packing_wins` PAIR = 12,000 (linear FLOP per token / attention FLOP per pair). 4B: linear 2 x 3.63 B = 7.26 GFLOP/token; attention 4 x 36 x 4096 = 0.59 MFLOP/pair; ratio 12,300. 2B: 2.82 GFLOP / 0.229 MFLOP = 12,300 [estimate]. PAIR needs no retune.
- Compute per token is 2.6x the 2B (7.26 vs 2.82 GFLOP) [estimate].

Qwen3.5 (hybrid): what breaks, from transformers 5.20.1 source [code: .venv/.../models/qwen3_5/modeling_qwen3_5.py, masking_utils.py:1443-1470]:
1. **Shared-prefix packing breaks.** The model builds `linear_attention` masks with `create_recurrent_attention_mask`, which returns `None` when the mask is not 2-D ("already a custom 4D attention mask"). `packed_chunk` passes a 4-D mask, so GDN layers get no mask and run one causal recurrence over `[prompt, answer1, answer2, ...]`: answer k sees answers 1..k-1 through the state. The tree mask only works on the 8 softmax layers. Result: wrong log-probs, silently. Required guard: disable `shared_prefix` when any layer_type is `linear_attention`. A correct version needs state forking per answer block (a custom kernel) or one row per answer.
2. Cost of losing it: R5 token ratio was 0.36 (packed tokens / row tokens) and the shared-prefix step went 31.0 -> 23.6 s [measured: runs/r5/shared_rl.json `shared/token_ratio` mean 0.36; step_time mean 23.2 s over 15 steps]. Without it the trainer forward processes ~2.8x the tokens (the TRL window path also pads to the longest answer).
3. `RopeCache` still works: Qwen3_5 has `get_rope_index` (line 1364) and `compute_3d_position_ids` (line 1526). GDN layers ignore positions.
4. `VisionCache` works (deepstack list is empty; simpler).
5. Left padding is handled: `apply_mask_to_padding_states` zeros padded hidden states for GDN layers given a 2-D mask (line 223/543), so the `window()` column-cut path is valid.
6. **Kernels.** The GDN forward uses `chunk_gated_delta_rule` from `fla` and `causal_conv1d` via the hub-kernel mechanism, else the pure-torch fallback `torch_chunk_gated_delta_rule` (Python loop over chunks) [code: modeling_qwen3_5.py:235-290, 423]. Our train lock has no flash-linear-attention, causal-conv1d or kernels package (grep count 0 in locks/train.txt). One source puts the fallback at about 10x slower [web: search summary, single source, unverified]. Installing fla/causal-conv1d on sm_120 (Blackwell) with torch 2.14.1 is unverified.
7. `compile_text_layers` assumes one code object for all layers; hybrid layers give two layer types (variants x BUCKETS widths) and Triton kernels inside compile are unverified.
8. Trainer-vLLM mismatch (IS ratio min = 0 in 98.1 % of 770 steps, median per-token |logp diff| 0.018 [measured: runs/rl/train_rl/rl.json per the brief]): GDN carries a recurrent state across up to ~1,900 tokens, with different kernels in vLLM (its own fla ops) and HF (fla or torch). Expect the mismatch to be no better and probably worse; unmeasured.
9. Thinking mode is on by default in the chat template; the generation prompt must pass `enable_thinking=False` (template line 149) in both TRL and the vLLM bridge (`sample.py` export_prompts), and the SFT format must match.
10. Vocab 248,320 vs 151,936: logits and lm-head cost 1.63x per token; fused head helps but this adds step time.
- Benefit side: KV cache 4.5x smaller per token (32,768 vs 147,456 B), so more concurrent sequences at a given util (before the GDN state is counted).

### 1.6 Step time and budget
Baseline 2B R5 shared-prefix: 23.2 s/step mean; generate 11.0 s, sync 1.25 s, wake 0.1, sleep 0.29 [measured: runs/r5/shared_rl.json, 15 steps]. RL is 770 steps for 3 epochs, a 4.9 h run (~$2.2 at $0.440/h, the R3 RTX 5090 rate) [estimate: 770 x 23.4 s].

Qwen3-VL-4B (patches intact), per component [estimate]:
- Trainer forward/backward and old-logp: ~2.6x FLOPs per token => 2.6x of the non-generation part (~12 s) = ~31 s.
- vLLM decode: memory-bound, weights 2.1x bigger, 36 vs 28 layers => 1.3-2.1x of 11.0 s = 14-23 s.
- Sync (bytes) ~2.6 s.
- Total ~**45-55 s/step** (about 2x the 2B). With 770 steps: 9.6-11.8 h = $4.2-5.2.
- **$3 buys about 6.8 h = ~450-540 steps at that speed**, i.e. 60-70 % of a 3-epoch run. The $3 cap (BRIEF 3) and the 4B choice conflict. SFT for a new base model costs extra on top (the 2B adapters do not transfer).

Qwen3.5-4B: forward ~2.6x tokens x 2.8 (no shared prefix) minus the full-attention savings; with the torch fallback an additional unknown multiple. Not estimable to better than "well over 2x the Qwen3-VL-4B step" until fla is confirmed.

## 2. Recommendations (numbered)
1. Keep Qwen3-VL-2B for the data-fix run (`rl_shifted.yaml`); evaluate 4B only after the shifted-views result. Decision gate: 2B shifted-view test IoU. If misses stay > ~6 % of images at the same training mix, try 4B.
2. If 4B is run: add `"qwen3-vl-4b": "Qwen/Qwen3-VL-4B-Instruct"` to `MODELS` in `src/objdel/train/configs.py:70-73` and to `_LORA` (line ~95 uses `lora(model)`); set `vllm_gpu_memory_utilization` 0.55 for it in the RL config (configs.py:192), keep `vllm_max_model_length` 4096, `per_device_train_batch_size` 16 x 16 accumulation, gradient checkpointing on. Make the util a per-model value, not a constant.
3. Cap the 4B run by money, not epochs: configure steps so wall time <= ~6.5 h ($2.9 at $0.44/h); log `time/*` every step; stop at the budget and save the checkpoint (`train_rl` resume exists via `resumed_from`).
4. Before any 4B spend: 10-step dry run on the 5090 reading `torch.cuda.max_memory_allocated()` during awake and update phases, vLLM `Maximum concurrency` log line, and `shared/token_ratio`. Replace my assumed 1.2 GiB vLLM overhead with the measured number. Add peak memory to `runs/*/rl.json` (not logged today: no peak-memory field in shared_rl.json).
5. Guard in `FastForward._get_per_token_logps_and_entropies` (`src/objdel/train/fast.py`, the `self.shared_prefix and pos is not None ...` condition): refuse shared_prefix when `any(t == "linear_attention" for t in getattr(model.config.get_text_config(), "layer_types", []))`, raise `NotImplementedError` in `packed_chunk` for the same case. Add a test in `tests/` with a tiny random `Qwen3_5` config (24 layers not needed; 4 layers, 1 attention) that asserts packed and unpacked log-probs differ without the guard and the guard routes to the window path. This protects the repo even if nobody runs Qwen3.5 soon.
6. Qwen3.5 only if a later phase needs it: first (a) add `flash-linear-attention` and `causal-conv1d` (or the `kernels` package) to a separate lock and check sm_120 import and speed in a CPU-free GPU micro-test (one forward/backward at 29k tokens); (b) implement GDN state forking for shared-prefix: run the prompt once, then expand the final recurrent + conv state to 8 answer blocks (batch of 8 rows reusing `initial_state`), which fla's `chunk_gated_delta_rule(initial_state=...)` supports; (c) measure trainer-vLLM per-token |logp diff| on 64 prompts before any RL. Estimated effort: new kernel glue + tests, not a library swap.
7. Template: if Qwen3.5 ever runs, set `chat_template_kwargs={"enable_thinking": False}` in `processor_kwargs`/the generation prompt and in `sample.py` `export_prompts`.
8. Keep `PAIR = 12_000` in `packing_wins` (4B ratio 12,300 computed); update its comment to name both models.
9. `hf-mem` into the preflight (`experiments/phase2/preflight.py`): print weights + KV for the chosen model and the implied minimum util, fail if util x card < weights + 4 GiB.
