## Findings

### F1. vLLM version landscape
- Docs exist up to vLLM 0.33.0 (LoRA page links point at v0.33.0, footer 21 Oct 2026) [docs: https://docs.vllm.ai/en/stable/features/lora/].
- TRL main docs: "TRL currently only supports vLLM versions from 0.23.0 to 0.33.x" [docs: https://huggingface.co/docs/trl/main/en/vllm_integration]. Our TRL is 1.17.1 [brief]; whether it equals that docs line is unchecked (Open Q1).
- Prefix-cache hash default is sha256 since v0.11; options `--prefix-caching-hash-algo sha256|sha256_cbor|xxhash|xxhash_cbor` [docs: https://docs.vllm.ai/en/latest/design/prefix_caching/].

### F2. Sleep mode (colocate sleep vs awake)
- Levels [docs: https://docs.vllm.ai/en/latest/features/sleep_mode/]: level 0 = scheduler pause only (not a CUDA checkpoint); level 1 = weights to CPU RAM, KV cache dropped; level 2 = params + KV dropped, other GPU allocations (RoPE tensors) backed up to CPU. Sleep frees "over 90 %" of GPU memory depending on workload.
- Documented RL update order: `sleep(level=2)`, `wake_up(tags=["weights"])`, load new weights, `collective_rpc("reload_weights")`, `wake_up(tags=["kv_cache"])`. Waking weights first avoids OOM from allocating KV early. Level 2 requires sending every parameter except those in `sleep_preserve_parameter_names`.
- CUDA graphs stay on GPU by default; `sleep_mode_offload_cudagraph=True` backs them up to CPU and restores them in place (no recapture), costs pinned host RAM and ~3 % decode latency at batch 1 (doc text; needs `cumem` backend).
- `release_kv_cache_memory()` drops KV but keeps weights; needs a completed pause and `cumem`. Partial wake does not resume scheduling; serialize sleep/wake/pause/resume calls.
- KV connector: block hashes ignore weights, so use a per-version `cache_salt` if weights change [docs: sleep_mode page]. Relevance: prefix cache must be reset/salted after each LoRA sync or stale-policy KV is reused.
- Known bug class: a buffer tagged kv_cache (FlashInfer block_table_arange) was discarded on sleep and not recreated, giving wrong rollouts in verl [search: https://www.goodfirstissue.org/vllm-project/vllm/issues/31016]. Check on our pinned version if FlashInfer is used.
- Our measurement: wake/sleep/sync is 1.7 s of 23.4 s [brief]; R4 found "vLLM sleep costs 1.6 s per step, awake gains nothing" (R4 speed test, memory notes, not re-read). So sleep is NOT the main gap; decode tail (4-5 s) and CPU phase (3.0-3.2 s) are bigger [brief].
- verl default is sleep mode (needs vLLM > 0.11), `free_cache_engine=True`, `sleep_level=2` on vLLM >= 0.8.5 per a community write-up [search: https://xinnuoxu.github.io/blogs/verl_memory_management.html; https://verl.readthedocs.io/en/latest/amd_tutorial/amd_vllm_page.html]. An old verl README used `free_cache_engine=False` + `enforce_eager=False` to keep CUDA graphs [search: verl v0.2.x README].

### F3. Weight transfer on the same GPU
- vLLM now has a weight-transfer layer: server flag `--weight-transfer-config '{"backend": "nccl"}'`, and `"ipc"` "when the trainer and the server share a GPU" [docs: https://huggingface.co/docs/trl/main/en/vllm_integration]. Python: `WeightTransferConfig(backend="ipc")`; trainer sends an iterator over parameters, packed mode with 1 GB buffer in FSDP2 example; needs `VLLM_SERVER_DEV_MODE=1` and `VLLM_ALLOW_INSECURE_SERIALIZATION` (pickled IPC handles) [search: https://docs.vllm.ai/en/latest/examples/rl/rlhf_ipc/ and rlhf_ipc_fsdp_ep]. Examples are full-parameter, not LoRA (not found for LoRA).
- TRL server flow: `/start_weight_update`, `/update_weights`, `/finish_weight_update`; TRL also needs `--logprobs-mode processed_logprobs` for the importance-sampling correction [docs: TRL vllm_integration]. This matters for our trainer-vLLM mismatch (B2): logprobs must be taken after temperature and logits processing, or the IS ratio is wrong by construction.
- `trl vllm-serve` is deprecated in main docs [docs: same].

### F4. LoRA hot-swap and in-place delta update
- Runtime LoRA: env `VLLM_ALLOW_RUNTIME_LORA_UPDATING=True`; endpoints `/v1/load_lora_adapter`, `/v1/unload_lora_adapter`; "`load_inplace=True`: vLLM will replace the existing adapter with the new one" keeping the same name; docs say this "commonly occurs in asynchronous reinforcement learning setups ... swapped in without interrupting ongoing inference". `max_lora_rank` must be >= largest rank. Security warning: trusted environment only [docs: https://docs.vllm.ai/en/stable/features/lora/].
- Cost note: load_inplace takes an adapter PATH (disk) in the documented form; offline `LoRARequest(lora_name, lora_int_id, lora_path)` also path-based. In-memory (tensor) LoRA load is not documented in what I read (Open Q2).
- In-place pattern with no recapture: adapter params live at stable addresses, so next graph replay sees new weights [paper: arXiv 2605.14217 appendix, via search snippet; non-vLLM-native, design reference only].
- verl LoRA: peft + FSDP + vLLM only; `layered_summon=True` gathers shards layer by layer when syncing the adapter [search: https://verl.readthedocs.io/en/v0.5.x/advance/ppo_lora.html]. AReaL has two LoRA modes (vLLM loads adapter dynamically, or adapter merged before sync) [search: besthub AReaL article].
- Prefix-cache keys include LoRA id, so after an in-place swap the cached blocks for that id are stale unless the cache is reset [docs: prefix_caching page lists LoRA IDs as extra hash; the swap-time invalidation behavior is NOT documented, Open Q3].
- Our current path: "no-merge LoRA sync" [brief]. Delta sync = send only A/B matrices (rank r) instead of merged full weights; no cheaper dtype/size claim measured here.

### F5. n>1 sampling for shared prompts
- vLLM prefix cache is on by default in V1 (hash = parent hash + block tokens + extras). The prefix-caching page does NOT cover parallel sampling n>1 [docs: prefix_caching]. With `SamplingParams(n=8)` one request carries 8 samples; whether prefill is computed once is not confirmed by a doc I read (Open Q4). Safe fact: with prefix caching, 8 identical prompts submitted separately share all full blocks after the first prefill, only the last partial block recomputes [docs: prefix_caching "Only full blocks are cached"].
- For multimodal, one image hash is the extra key for every placeholder block, so identical (image, text) prompts hit the cache; a different image gives different keys [docs: prefix_caching]. Forum reports of wrong results with prefix cache on Qwen3-VL (mRoPE) are unverified user posts [search: https://discuss.huggingface.co/t/multimodal-prefix-caching-with-qwen3-vl/170849]. Must be tested: logprobs with and without prefix cache must match.

### F6. Prefix and processor caches for images
- Processor cache: vLLM caches HF-processor output so an identical image is not processed again; motivated by slow processors like Qwen2-VL [docs: https://docs.vllm.ai/en/latest/design/mm_processing/]. Flags `mm_processor_cache_gb` (non-zero enables) and a type option exist per Dynamo docs [search: https://docs.dynamo.nvidia.com/dynamo/dev/knowledge-base/modular-components/backends/v-llm/vllm-multimodal]; exact `lru|shm` names unconfirmed.
- `multi_modal_uuids`: pass stable ids so vLLM skips rehashing; entry `None` falls back to content hashing. Online: `"uuid"` key per media item. With a cached uuid, the media entry may be `None` (request fails if uuid is not in cache). If both processor cache and prefix cache are off, uuids are ignored [docs: https://docs.vllm.ai/en/latest/features/multimodal_inputs/].
- Precomputed embeddings: `LLM(enable_mm_embeds=True)`, tensor `(num_images, image_feature_size, hidden)`; Qwen2-VL family takes a dict with `image_grid_thw`; engine "may crash" on wrong shape [docs: multimodal_inputs].
- Encoder cache is tracked by `mm_hash` in V1 (`EncoderCacheManager`) [search: https://docs.vllm.ai/en/v0.19.1/api/vllm/v1/core/encoder_cache_manager/]. Cross-request sharing is not confirmed.
- GPU normalization knob: `mm_device_do_normalize` in multimodal config (names only; semantics not read) [docs: mm_processing page].
- Per-request `mm_processor_kwargs` (min/max pixels) are rejected unless `--trust-request-mm-kwargs`; set pixel limits at engine start instead [docs: multimodal_inputs].
- Vision encoder CUDA graphs: `cudagraph_mm_encoder` (bool, default False), `encoder_cudagraph_token_budgets` (power-of-2 auto if empty); Qwen3-VL supported; docs benchmark on GB200, Qwen3-VL-32B: ~18 % lower mean latency (FLASH_ATTN) and ~44 % (FLASHINFER) [docs: https://docs.vllm.ai/en/stable/design/cuda_graphs_multimodal/]. Not measured on 2B / RTX 5090; images with more tokens than all budgets fall back to eager.

### F7. Stop criteria for runaway generations
- Our facts: 38 % of R5 steps hit 1,536 tokens; mean outline 131 tokens; longest in step avg 1,271; 0 of 23,469 train targets exceed 1,536; count above 1,200 unknown [brief].
- vLLM v1 custom logits processors: subclass `LogitsProcessor` with `update_state(batch_update)` and `apply(logits)`; `is_argmax_invariant`; register via `LLM(logits_processors=[...])`; per-request args via `SamplingParams.extra_args`; `AdapterLogitsProcessor`/`RequestLogitsProcessor` for per-request wrapping [docs: https://docs.vllm.ai/en/v0.23.0/examples/features/logits_processor/]. A processor can force EOS (set all logits to -inf except EOS) once a repetition rule fires, so the sequence ends at the next step instead of at 1,536. Logits processors run on the batch, so a Python loop over the batch is a host cost (Open Q5).
- Structured outputs: xgrammar/outlines backends; JSON schema in V1; a compiled grammar is cached per schema, per-request backend choice not supported in V1; overhead reports are mixed and one thread reports CPU-GPU sync cost on RTX 4090 [search: vLLM forum thread 1444; XGrammar paper arXiv 2411.15100]. A grammar for "array of [x,y] ints 0-1000" would bound runaway to well-formed JSON but is not documented for `maxItems`; must benchmark.
- Schedules and partial rollouts: APRIL buffers unfinished rollouts across steps to kill long-tail stalls [paper: arXiv 2509.18521]; NeMo-RL async keeps trajectories up to `max_trajectory_age_steps`. Both change on-policy-ness (IS needed).
- No paper found that does n-gram repeat detection with truncation for RL rollouts (search result, none confirmed). One snippet said RL itself suppresses duplicated mask outputs through negative group advantage [paper: arXiv 2608.18881, snippet only].
- Mechanism is cheap in principle: stop when the last K points repeat, or when the polygon closes (first point re-emitted), or when token count > 3 x (max true length in the audit). The correct limit needs the A-phase true-length count first [brief].

### F8. CUDA graphs and speculative decoding
- Decoder graph modes via `CompilationConfig.cudagraph_mode`: NONE, PIECEWISE, FULL, FULL_DECODE_ONLY, FULL_AND_PIECEWISE. Default in V1 with piecewise compilation = FULL_AND_PIECEWISE ("usually fastest, most memory, longest capture"); FULL suits small models/small prompts [docs: https://docs.vllm.ai/en/latest/design/cuda_graphs/]. Capture-size keys (`cudagraph_capture_sizes`, `max_cudagraph_capture_size`) not confirmed in docs I read.
- Interaction with sleep: graphs stay on GPU unless `sleep_mode_offload_cudagraph=True` (F2). Our `enforce_eager` state in the code was not checked here (Open Q6).
- Speculative decoding: vLLM docs frame it for medium/low query rates and short-to-medium outputs; avoid at max throughput [search: https://docs.vllm.ai/en/v0.21.0/features/speculative_decoding/ via mintlify mirror]. N-gram (prompt-lookup) needs no draft model, bounds `prompt_lookup_min/max` default 5/5 [search]. Speedup shrinks as batch grows (our decode batch is 128 sequences per step: 16x8? not verified) [paper: arXiv 2601.11580]. Polygon text has few repeats of earlier text except the runaway case, so n-gram acceptance is expected to be low for good outputs [estimate]. Recommendation: do not adopt before measuring.

### F9. GPU image preprocessing for Qwen3-VL
- Transformers fast image processors are torchvision-based, `use_fast=True`, accept `device="cuda"`; default device = input device (tensor inputs) else CPU [docs: https://huggingface.co/docs/transformers/v4.57.1/en/main_classes/image_processor]. Video processor docs show `device="cuda"` and optional compile [search: https://huggingface.co/docs/transformers/v5.14.0/video_processors]. Qwen2VLImageProcessorFast exists [search: transformers qwen2_vl docs]; whether Qwen3-VL uses it and honors `device` was NOT confirmed (Open Q7). Note: slow vs fast path give "minor differences in outputs" [search: vLLM forum 1607]; any switch needs a numerical equivalence test on pixel_values and then on logprobs.
- torchvision `decode_jpeg(device="cuda")` uses nvJPEG, input bytes stay on CPU, batch lists are faster; docs mark device as Beta [docs: https://docs.pytorch.org/vision/stable/generated/torchvision.io.decode_jpeg.html]. Our CT images are 512x512 crops, probably already decoded arrays, so decode is likely not the cost; resize/normalize/patchify is [estimate].
- nvImageCodec: batch decode in one call to avoid per-image sync; avoid `torch.cuda.is_available()` before fork [docs: https://docs.nvidia.com/cuda/nvimagecodec/samples/torch_dataloader.html]. Resize with CV-CUDA in the NVIDIA sample [docs: nvimagecodec cvcuda_sample].
- DALI >= 2.1 has an experimental Torchvision-compatible API with GPU replacements for torchvision v2 ops [search: https://docs.nvidia.com/deeplearning/dali/archives/dali_2_1_1/user-guide/examples/getting_started/torchvision_api.html]. No head-to-head benchmark vs torchvision v2 or nvImageCodec was found. DALI adds a pipeline, graph and build dependency, which is heavy for one resize + normalize.
- Our CPU phase 3.0-3.2 s includes 1.61 GB fp32 pixel_values built twice, blocking H2D [brief]. A GPU-side processor removes the fp32 CPU build and PCIe copy, but the Qwen patch layout (temporal 2 x patch 16, merge 2x2, per Qwen3-VL) must be reproduced exactly [estimate, check against HF processor].

### F10. How other frameworks avoid idle gaps
- OpenRLHF: hybrid engine colocates and time-slices with sleep mode; NCCL broadcast to vLLM; `--vllm.enable_sleep` CANNOT combine with `--train.async_enable`; async mode keeps vLLM on its own GPU group; partial rollout pauses in-flight requests during sync, then resumes (samples mix old and new weights); start `--train.async_queue_size 1` (~1 step lag) [search: https://openrlhf.readthedocs.io/en/latest/hybrid_engine.html; async_training.rst].
- NeMo-RL async GRPO: `policy.generation.colocated.enabled: false` is required for async with vLLM; `grpo.async_grpo.enabled`, `max_trajectory_age_steps: 1` (buffer = `num_prompts_per_step x max_trajectory_age_steps x 2`), `in_flight_weight_updates` (needs `vllm_cfg.async_engine: true`; refit without waiting for the longest generation), `recompute_kv_cache_after_weight_updates` (default false: in-flight requests keep pre-update KV), `loss_fn.use_importance_sampling_correction: true` is mandatory [docs: https://docs.nvidia.com/nemo/rl/latest/guides/async-grpo.html]. Takeaway: NeMo-RL does not close the gap on ONE GPU; it needs a second pool.
- slime: sync mode with GPU co-location for limited GPUs and uniform lengths; async mode needs decoupled GPUs; APRIL mixes in unfinished rollouts [search: AMD slime blog, slime skill pages (third-party)]. Not official docs.
- TRL: colocate default; `AsyncGRPOTrainer` (experimental) decouples via vLLM server [skill text: trl-training]. Single GPU cannot host both pools, so only the in-flight partial-update style can apply, and it is moot at 32 GB with a 2B model + trainer.
- Common pattern: the only single-GPU levers are (a) shorter tail (stop rules, partial rollout), (b) cheaper sync (adapter-only, IPC), (c) less CPU/host work, (d) overlap CPU work with GPU decode (pipelining preprocessing of next batch while vLLM decodes the tail) [estimate, not found as a documented framework feature].

## Recommendations (numbered; each ends with a gate)

1. Keep sleep mode, but replace the sync with the documented tag sequence if not already: `sleep(level=2)` -> `wake_up(tags=["weights"])` -> adapter load -> `wake_up(tags=["kv_cache"])`; also use level 1 only if CPU RAM allows and merged weights are not re-sent (level 1 keeps base weights in CPU, so only LoRA delta needs sending). Place: wherever fast.py wraps TRL's vLLM handover (src/objdel/train/fast.py). Gate: NVTX range around sync/wake/sleep; target < 1.0 s (from 1.7 s [brief]); rewards of step 1 identical.
2. Delta LoRA sync, not merge: after each optimizer step, push only LoRA A/B for the language-model layers into the vLLM-held adapter. Preferred order: (a) vLLM `load_inplace=True` with `VLLM_ALLOW_RUNTIME_LORA_UPDATING=True` if an in-memory path exists in pinned version; (b) otherwise `collective_rpc` that `copy_` into the stable adapter tensors (pattern from arXiv 2605.14217). Gate: logprob equality vs merged path within the measured 0.018 median |dlogp| [brief]; prefix cache reset or `cache_salt = step` after each swap (F2, F4).
3. Fix the logprob match cause first (B2 coupling): serve with processed logprobs (`--logprobs-mode processed_logprobs` in server form; the same `logprobs_mode` engine arg for colocate) and compute trainer logprobs with identical temperature. Gate: ratio min = 0 rate drops from 98.1 % of steps [brief].
4. Test `n=8` as ONE request per prompt vs 8 separate requests, with prefix caching on, measuring prefill tokens and wall time via vLLM metrics. Keep whichever has fewer prefill tokens; add equality test of logprobs with prefix cache on and off for Qwen3-VL (mRoPE report, F5). Gate: identical logprobs within tolerance.
5. Images: give each image a stable `multi_modal_uuids` entry (e.g. sha1 of cropped array + window), enable the processor cache (`mm_processor_cache_gb` > 0) and keep prefix caching on, so the 8 samples and later epochs skip HF processing. Set pixel limits at engine start (not per request). Gate: vLLM processor time per step; images across epochs hit cache.
6. Cap runaways with a vLLM V1 logits processor (new module under src/objdel/train/, with a test in tests/): force EOS when the last K=3 emitted (x,y) pairs equal an earlier window, or when the first point repeats (polygon closed), or when length > L_cap. Pass per-request via `SamplingParams.extra_args`. Set L_cap from the A-phase true-length count (e.g. 99.9th percentile x 1.5), not a guess. Keep `max_tokens` as the backstop. Gate: fraction of steps hitting max < 38 % [brief]; decode tail from 4-5 s down; the reward of stopped samples must still be masked/penalized consistently (they are currently masked).
7. Benchmark a JSON-grammar constraint (xgrammar) for the outline array only as a secondary option; reject if overhead > 5 % of decode time or CPU sync appears in NVTX [search: vLLM forum 1444]. Only try after item 6.
8. CUDA graphs: confirm `enforce_eager` is False and `cudagraph_mode` = `FULL_AND_PIECEWISE` (V1 default with piecewise compile); decode batch is fixed small, so capture sizes should include the real decode batch (check key names in pinned source). If sleep recaptures graphs, test `sleep_mode_offload_cudagraph=True` (~3 % decode cost at batch 1 vs recapture). Try `cudagraph_mm_encoder=True` for the vision tower; Qwen3-VL supported. Gate: step time with and without, same rewards.
9. Do NOT adopt speculative decoding now (batch is large, outputs are novel numbers). Run one 10-step ngram test (`speculative_config={"method":"ngram"}`) only if decode tail still dominates after item 6. Gate: acceptance rate > ~30 % needed, [estimate].
10. Training-side image path (the 3.0-3.2 s CPU phase [brief]): build pixel_values once, on GPU, in bf16/fp16 where the model uses it. Use transformers fast processor with `device="cuda"` if Qwen3-VL's class supports it (test), else write the resize+normalize+patchify in torch/torchvision v2 on device. Do not add DALI; nvImageCodec only if decode appears in a profile. Gate: numerical equality with the HF CPU processor on 100 images (max abs diff on pixel_values) and equal grid_thw.
11. Overlap: run the CPU part of the next micro-batch (prompt tokenization, rope position table) in a thread while vLLM decodes the long tail, using the Python loop-free precomputed tables already in RopeCache/ImageMemo [brief]. Gate: NVTX shows no gap between decode end and the first training forward.
12. Do not go async/decoupled. NeMo-RL requires non-colocated pools for vLLM async; OpenRLHF forbids sleep + async; one 32 GB GPU cannot host two pools. If a later run uses 2 GPUs, use NeMo-RL-style `max_trajectory_age_steps=1` plus `use_importance_sampling_correction` (we already use IS with cap 3 [brief]).
13. TRL/vLLM version: record the exact vLLM and TRL versions in the run spec; if upgrading TRL to a version supporting vLLM 0.23-0.33, move to `--weight-transfer-config '{"backend":"ipc"}'` for same-GPU sync. Gate: start-up check (A-phase "TRL private-name check" [brief]).
