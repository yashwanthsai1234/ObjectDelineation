# torch.compile and CUDA Graphs for the training step (forward + backward) of a LoRA fine-tune of Qwen3-VL-2B (PyTorch 2.13/2.14, TRL, PEFT)

Scope note: research done 2026-11-06. PyTorch 2.14.0/2.14.1 and 2.15.0 exist as tags; config values below were read from the v2.13.0 / v2.14.0 source files unless stated. Several PyTorch docs pages served from "main" now correspond to 2.15 and are flagged where used. I found NO published, measured compile or CUDA-graph speedup for Qwen-VL training or for GRPO update steps; see Gaps in each section.

## 1. torch.compile modes for training (default vs reduce-overhead vs max-autotune-no-cudagraphs); does reduce-overhead capture backward; CUDAGraph Trees mechanics

### Takeaway
`mode="reduce-overhead"` turns on CUDAGraph Trees, which record the Inductor-compiled forward and backward graphs into one shared memory pool, but only for graphs that are free of CPU ops, input mutation on eager inputs, and (by default) it re-records for every distinct input shape. For a variable-length VLM batch it therefore only pays off if shapes are padded to a few fixed buckets and graph breaks are removed; the default mode (Inductor fusion, no graphs) is the lower-risk first step.

### Cited Findings
- Modes (HF Trainer table): default = balanced compile time vs runtime; reduce-overhead = reduces Python/CPU overhead using CUDA graphs at the cost of some extra memory; max-autotune benchmarks kernel implementations at compile time; max-autotune-no-cudagraphs is the same without CUDA graphs. For training, compile traces forward and backward together; compilation happens on the first training step. — [HF transformers: torch.compile for training](https://huggingface.co/docs/transformers/en/torch_compile.md)
- Old "separate CUDA graphs" integration (`cudagraph_trees=False`): forward and backward are separate graph captures with separate memory pools, so memory for activations saved in the forward cannot be reclaimed in the backward. CUDAGraph Trees fix this with a single memory pool across all captures, built as trees of recordings rather than one fixed invocation sequence. — [PyTorch docs: CUDAGraph Trees (source md)](https://github.com/pytorch/pytorch/blob/main/docs/source/user_guide/torch_compiler/torch.compiler_cudagraph_trees.md); [dev-discuss: CUDAGraphs in PyTorch 2.0](https://dev-discuss.pytorch.org/t/cudagraphs-in-pytorch-2-0/1428)
- Warmup/record/replay lifecycle: the first run of each graph is a warmup (cuBLAS/Triton benchmarking, memory addresses not fixed, falls back to non-cudagraph Inductor execution); the second run records; the third onwards replays. When a path is newly hit after replays, the pool is checkpointed back to the state at the end of the last common graph. — same CUDAGraph Trees doc
- Training iteration heuristic: "in inference we start a new iteration on each invocation for torch.compile, and in training we do the same so long as there is not a pending backward that has not been invoked. If those heuristics are wrong, you can mark the start of a new iteration with `torch.compiler.cudagraph_mark_step_begin()`, or clone tensors of a prior iteration (outside of torch.compile) before you begin the next run." Footgun: you cannot persist memory between separate runs through your model (one training loop / one inference run). Accessing a tensor output of a previous run raises "accessing tensor output of CUDAGraphs that has been overwritten by a subsequent run". — same doc
- Inputs are of three kinds: eager inputs are copied to static-address tensors before recording/replay; parameters and buffers are assumed (and runtime-checked) to have the same addresses every time and are not copied; outputs of earlier CUDAGraph-Trees graphs are not copied but are checked and trigger a re-record if unstable. — same doc
- Input mutation: mutating an input that comes from eager makes the function run without CUDAGraph and logs "skipping due to mutated inputs"; mutation of parameters/buffers and of prior CUDAGraph outputs is supported (`torch._inductor.config.triton.cudagraph_support_input_mutation`, default `not is_fbcode()` in 2.13 source, i.e. on for OSS). — same doc; [inductor config.py v2.13.0](https://github.com/pytorch/pytorch/blob/v2.13.0/torch/_inductor/config.py)
- Dynamic shapes: "CUDAGraph Trees re-record CUDAGraph for every unique shape of an input tensor." NVIDIA uses 64 KB of device memory per kernel launch in a CUDAGraph up to CUDA 12.4 / driver 550+, so many re-recordings are costly. Doc advice: pad input tensors to a few fixed shapes, and/or set `torch._inductor.config.triton.cudagraph_skip_dynamic_graphs=True` to cudagraph only functions with static input shapes. — same doc
- Reasons CUDAGraph is skipped: input mutation of eager inputs, CPU operators, multi-device operators, free unbacked symbols, cudagraph-unsafe custom ops, and incompatible ops, including `aten._local_scalar_dense` (i.e. `.item()`) and `aten._assert_scalar`, `aten.multinomial`, `run_and_save_rng_state`, `run_with_rng_state`. — same doc
- CUDAGraph partition: `torch._inductor.config.graph_partition=True` splits off CPU ops, device copies, control flow, unsafe custom ops and unbacked symints, and cudagraphs the remaining GPU partitions separately. In the v2.13.0 and v2.14.0 source, the default is `os.environ.get("TORCHINDUCTOR_GRAPH_PARTITION", "1" if not is_fbcode() else "0") == "1"`, i.e. ON by default for OSS builds. (Verify empirically; the docs text still describes it as opt-in.) — same doc; [inductor config.py v2.14.0](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_inductor/config.py)
- Inductor cudagraph knobs present in 2.14.0 source: `triton.cudagraph_trees=True`, `triton.cudagraph_skip_dynamic_graphs=False`, `triton.cudagraph_capture_sizes` (None = capture all shapes), `triton.cudagraph_unexpected_rerecord_limit=128`, `triton.cudagraph_trees_generation_cloning` ("user_visible" or None). In main (2.15-era) there are additionally `cudagraph_dynamic_shape_warn_limit=8` and `cudagraph_dynamic_shape_rerecord_limit=None` ("stop re-recording after N distinct dynamic shapes; shapes already recorded keep replaying; further new shapes run eager") — I did NOT find the latter two in the v2.13.0/v2.14.0 greps, so treat them as 2.15 features. — [config.py v2.14.0](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_inductor/config.py); [config.py main](https://github.com/pytorch/pytorch/blob/main/torch/_inductor/config.py)
- Third-party observation consistent with the above: HF's compile docs say `cudagraphs` backend is for "fixed-shape inputs". — [HF torch.compile for training](https://huggingface.co/docs/transformers/en/torch_compile.md)

### Inferences
- "reduce-overhead captures backward" is true in the sense that AOTAutograd's compiled backward graph is a separate graph recorded into the same CUDAGraph Tree pool as the forward (docs describe forward and backward as separate captures sharing one pool). The docs do not have a sentence that says exactly this for backward; confirm with `TORCH_LOGS=cudagraphs` that backward graphs are recorded and not skipped.
- With micro-batches of 16-32 sequences x 600-1900 tokens, each distinct (batch, seq) shape means one record + 64 KB/kernel of graph memory. Buckets (e.g. 4-6 sequence lengths x 1-2 batch sizes) are the only workable regime; free-running lengths with `dynamic=True` would either skip cudagraphs or re-record constantly.
- Because lora weights are parameters (stable addresses) and the optimizer step is outside the compiled region, the "parameters are not copied" path applies; gradients written by backward into `.grad` are outside the pool unless they come from graphs — confirm no "pending backward / overwritten output" errors with gradient accumulation (call `cudagraph_mark_step_begin()` at the start of each micro-batch if that happens, but see the warning that this releases the previous generation's tensors, so it must be after backward of the previous micro-batch).

### Gaps
- No source found measuring reduce-overhead on a LoRA fine-tune or GRPO update; no source on how gradient accumulation interacts with `cudagraph_mark_step_begin` beyond the docs' generic heuristic.
- I could not fetch the `torch.compile` API page for the exact current wording of `max-autotune-no-cudagraphs`; only the HF table above is cited.

## 2. Regional compilation (per-layer compile), PEFT LoRA, gradient checkpointing, autocast, fp32 adapters

### Takeaway
Compile each decoder layer (or `nested_compile_region`) rather than the whole model: it cuts cold compile time by an order of magnitude with similar steady-state speed, is what torchtune does by default, and PEFT officially lists LoRA training under torch.compile as working. The main documented hazards are LoRA dropout combined with activation checkpointing (Inductor error) and graph breaks inside the HF modeling code.

### Cited Findings
- PyTorch regional-compilation recipe (requires PyTorch 2.5+; on 2.4 set `torch._dynamo.config.inline_inbuilt_nn_modules=True`): compile the repeated layer and reuse it. Recipe numbers, forward only: full-model compile 10.02 s vs regional 0.37 s (another page version quotes 29.71 s vs 1.75 s). Parts outside the region (e.g. a final `Linear`) are not compiled. The recipe covers only a forward call, not training/backward. Page states many cases show minimal speedup difference vs full compile. — [PyTorch regional compilation recipe](https://docs.pytorch.org/tutorials/recipes/regional_compilation.html)
- `@torch.compiler.nested_compile_region` on a repeated unit inside a single full-model `torch.compile`: compiled on first appearance, reused for later occurrences; recompiles automatically if shape/dtype/device/stride/globals change. — [PyTorch: reducing compile time](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/compile/programming_model.reducing_compile_time.html)
- Diffusion model guide: regional compile gives the same speedup as full compile with ~8x smaller compile latency; `compile_repeated_blocks`; cold 9.6 s vs warm-cache 2.4 s. Accelerate offers `use_regional_compilation=True` in `TorchDynamoPlugin`. — [PyTorch blog: torch.compile and diffusers](https://pytorch.org/blog/torch-compile-and-diffusers-a-hands-on-guide-to-peak-performance/); [HF Accelerate compilation guide](https://huggingface.co/docs/accelerate/main/en/usage_guides/compilation.md)
- torchtune `compile_model`: loops over modules and calls `m.compile(backend=backend)` on each `TransformerSelfAttentionLayer` / `TransformerCrossAttentionLayer` ("per-layer compile to reduce compile times"), default backend inductor, default mode (not reduce-overhead); `compile_loss` separately compiles the loss. — [torchtune/training/_compile.py](https://github.com/pytorch/torchtune/blob/main/torchtune/training/_compile.py)
- PEFT docs: torch.compile "works for some but not all features"; tested with a causal LM and default compile settings: training with HF `Trainer`, training with a custom loop, inference, generation; LoRA (plus DoRA, LoRA on embeddings, modules_to_save, merging, disable_adapter, bnb quantization) listed as working. Warns that no error does not guarantee correct output; test on the latest PyTorch; tests live in `peft/tests/test_torch_compile.py`. Not stated: VLMs, gradient checkpointing, reduce-overhead mode. — [PEFT torch.compile guide](https://huggingface.co/docs/peft/en/developer_guides/torch_compile)
- Known bug: PEFT issue #3020 (closed as stale, 2026-04): LoRA + activation checkpointing + torch.compile gives an Inductor `BackendCompilerFailed` error on LLaVA models when `lora_dropout != 0` (works with 0). Torch 2.8.0, peft 0.18.2.dev0, transformers 5.0.1.dev0, regional compile, `use_reentrant=False`. Workaround from a commenter: `torch._inductor.config.fallback_random = True` (dropout falls back to eager; the config comment says "slow but useful for debugging"). PEFT maintainer judged it a torch.compile bug, not PEFT. A second, separate IndexError without GC was mentioned but not detailed in what I read. — [peft#3020](https://github.com/huggingface/peft/issues/3020)
- torch.utils.checkpoint source note: Dynamo does not step inside `utils.checkpoint`; it tries to wrap it in a higher-order op if the forward is safe to trace, else it graph-breaks and falls back to eager (the `checkpoint` function is `@torch._disable_dynamo`). A doc comment says that under torch.compile, recomputation selecting a different compiled graph than the original (automatic dynamic shapes) can raise an error. — [torch/utils/checkpoint.py](https://github.com/pytorch/pytorch/blob/main/torch/utils/checkpoint.py)
- Megatron-Bridge docs: TE-scoped per-layer CUDA graphs cannot be combined with full activation recompute; only the `local` full-iteration graphs support `recompute_granularity=full`. (Megatron-specific, not PyTorch eager.) — [NeMo Megatron-Bridge CUDA Graphs](https://docs.nvidia.com/nemo/megatron-bridge/0.6.2/training/cuda-graphs.html)

### Inferences
- For this project: `lora_dropout=0` (if acceptable for the experiment) removes the one documented compile+GC+LoRA failure; otherwise test `fallback_random`.
- Whether to keep gradient checkpointing at all: with 24-32 GB and micro-batches of 16-32 x up to 1900 tokens it is probably required; compile + non-reentrant checkpoint is supported in principle via the higher-order op, but the cudagraph path with checkpoint is untested in anything I found. Treat "reduce-overhead + gradient checkpointing + LoRA" as unproven and test first.
- No source addressed bf16 autocast vs fp32 LoRA adapters under compile specifically. Dtype mismatch causes guards/recompiles only when dtypes change between calls; fixed dtypes should compile once. This is reasoning, not a cited fact.

### Gaps
- No source on fp32 LoRA adapters + bf16 base under compile (extra casts are fused by Inductor in principle; not verified).
- No measured compile-time or step-time numbers for per-layer compile of Qwen3-VL-2B (28 decoder layers? not verified here).

## 3. Dynamic shapes, bucketing and recompile limits

### Takeaway
Dynamo's default is to recompile once as dynamic on the second distinct shape; default `recompile_limit=8` per code object means a handful of fixed buckets is safe, and beyond that compiled code is skipped (runs eagerly). With cudagraphs, each distinct shape additionally costs a graph recording, so padding to a small fixed set is strongly recommended by both PyTorch and NVIDIA.

### Cited Findings
- `torch._dynamo.config.recompile_limit = 8` and `accumulated_recompile_limit = 256` in both v2.13.0 and v2.14.0; `cache_size_limit` is an alias. `fail_on_recompile_limit_hit` raises a hard error instead (works best with limit=1). — [dynamo config.py v2.14.0](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_dynamo/config.py)
- On hitting the limit "all future compilation attempts will result in the function being skipped (run eagerly)"; existing compiled code is still used if its guards pass; nested calls are skipped too. Raise the limit if the number of recompiles has a known bound. `dynamic=None` (default) only goes dynamic after the first recompile; `dynamic=True` compiles dynamic from the start; `dynamic=False` recompiles for every shape. Find recompiles with `TORCH_LOGS=recompiles` or tlparse. Wrapping changing Python scalars (e.g. LR) in tensors avoids guard failures; `allow_unspec_int_on_nn_module=True` for changing int attributes. — [PyTorch: recompilation](https://docs.pytorch.org/docs/2.14/user_guide/torch_compiler/compile/programming_model.recompilation.html)
- `torch._dynamo.mark_dynamic(tensor, dim)` for a dimension expected to vary (dynamic-shapes docs, core concepts). — [PyTorch dynamic shapes core concepts (source)](https://github.com/pytorch/pytorch/blob/main/docs/source/user_guide/torch_compiler/compile/dynamic_shapes_core_concepts.md)
- NVIDIA CUDA Graph best-practice page on dynamic patterns: start with padding to one fixed max length (e.g. 2048; one graph; a 128-token sequence padded to 2048 wastes ~93% of attention compute); use bucketing (example 128/256/512/1024/2048 = 5 graphs, ~5x memory vs a single graph) only if profiling shows large padding waste and memory allows; hybrid = graph only the most frequent buckets (~95% of data) and run rare shapes eagerly. — [NVIDIA CUDA Graph Best Practice: handling dynamic patterns](https://docs.nvidia.com/dl-cuda-graph/latest/torch-cuda-graph/handling-dynamic-patterns.html)
- NVIDIA MLPerf RNN-T example used bucketing (audio 400-1600, text 150-600) with 8 graphs (4 per network x 2 networks) and captured partial graphs. — [NVIDIA CUDA Graph examples](https://docs.nvidia.com/dl-cuda-graph/latest/examples/introduction.html)
- Megatron-Bridge: sequence length and micro-batch size must not change between steps for CUDA graphs; packed-sequence SFT/LoRA fails with TE-scoped graphs (non-Tensor inputs). — [Megatron-Bridge CUDA Graphs](https://docs.nvidia.com/nemo/megatron-bridge/0.6.2/training/cuda-graphs.html)
- Unsloth's recent PR (closed/merged-type, 2026-11-01) makes packed mRoPE attention work under `torch.compile(fullgraph=True)` by caching a shape-only meta tensor so the compiled wrapper reads symbolic lengths. Evidence that packed/varlen + mRoPE is a recognised graph-break source. — [unsloth#16416](https://github.com/unslothai/unsloth/pull/16416)

### Inferences
- A practical plan: pad sequence length to multiples of e.g. 256 with a cap, giving ~6-8 buckets for 600-1900 tokens (600->768 ... 1900->2048), fix micro-batch size (drop or pad the last short micro-batch), and raise `recompile_limit` above the bucket count. Eight buckets is exactly the default limit, so raise it to e.g. 16-32. Under cudagraphs, memory for 6-8 recordings of 16-32 x 2048 token activations may not fit in 24 GB; per-bucket graph memory is shared via the Trees pool only along the same path, so measure. 
- Padding waste: padding 600 to 768 is cheap; padding to a single 2048 would waste >2x compute for the short end, so single-shape capture is a poor fit here. Sorting/grouping rollouts by length before forming micro-batches would shrink waste.
- No source gives "how many buckets is practical"; the 5-8 range comes from the NVIDIA example (5), RNN-T (8) and the default dynamo limit (8).

### Gaps
- I did not read the dynamic-shapes pages enough to cite `mark_unbacked` / `maybe_mark_dynamic` semantics; the fetch of the rendered dynamic-shapes page only returned a redirect stub.
- No source on `pad_to_multiple_of` interplay with Qwen3-VL's processor (visual token counts vary per image regardless of padding).

## 4. Graph breaks in Qwen2-VL / Qwen2.5-VL / Qwen3-VL HF modeling code

### Takeaway
The Qwen-VL modeling code has data-dependent ops in `get_rope_index`, in vision attention (`cu_seqlens`/`lengths.tolist()`), in `get_image_features` split sizes and in the deepstack boolean-mask scatter; they cause D2H syncs and graph breaks. Because your vision tower is frozen and the language decoder layers are the hot path, the cleanest fix is to compile only the text decoder layers, run the vision encoder eagerly under `no_grad`, and pass precomputed `position_ids` so `get_rope_index` is never called in the training forward.

### Cited Findings
- Reading current `modeling_qwen3_vl.py` (main, transformers v5.x): `.tolist()` in `Qwen3VLVisionAttention.forward` non-flash path (`torch.split(tensor, lengths.tolist(), dim=2)`), in `get_rope_index` (`input_token_type.tolist()` fed to `itertools.groupby`), and in `get_image_features` (`split_sizes ... .tolist()`); `.item()` in `get_vision_position_ids`; `get_rope_index` loops over the batch in Python and appends `llm_positions.max()+1-len(...)` per item; `masked_scatter(image_mask, image_embeds)` in `Qwen3VLModel.forward`; boolean-mask indexing and `.sum()`-sized allocations in `_deepstack_process` and the joint image+video embed path. `_can_compile_fullgraph = True` is set on `Qwen3VLPreTrainedModel`, and `get_placeholder_mask` uses `torch_compilable_check`. `get_rope_index` only runs when `position_ids` is None. (Summarised by a fetch-and-extract tool run over the raw file; I did not read the file line by line, so confirm in your installed version.) — [modeling_qwen3_vl.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_vl/modeling_qwen3_vl.py)
- Issue #47649 (closed 2026-07-30): `lengths.tolist()` in Qwen3-VL vision attention creates a D2H pageable->host copy costing more than 250 ms and leaves the GPU waiting on a CPU that is already ahead; also flags `get_rope_index` (`mrope_position_deltas = torch.tensor(...)`, `position_ids[:, batch_idx] = ...`). — [transformers#47649](https://github.com/huggingface/transformers/issues/47649)
- Open PR #47703 (2026-08-01): moves `cu_seqlens`/`grid_thw` control tensors to CPU, replaces `.item()` with `int()` on CPU tensors, replaces `itertools.groupby` with tensor boundary detection in `get_rope_index`; states it "prevents torch.compile from capturing the whole thing as one graph". GPU verification listed as still pending. — [transformers#47703](https://github.com/huggingface/transformers/pull/47703)
- Open PR #49893 (2026-10-23): for Qwen2-VL/Qwen2.5-VL, precompute `cu_seqlens`, vision `position_ids`, `max_seqlen`, window index tensors on CPU from `grid_thw` and inject them through the existing `accepts_precomputed_kwargs` channel in `vision_utils`; "break `torch.compile` graphs — see #33289"; numerically exact (integer indices); tested on CPU tiny models, XLA TPU validation in progress. — [transformers#49893](https://github.com/huggingface/transformers/pull/49893); umbrella issue [transformers#33289](https://github.com/huggingface/transformers/issues/33289)
- Closed PR #44973: on released transformers (4.52.4) `torch.compile` + `flash_attention_2` crashes because `max_seqlen` is a 0-d tensor and `flash_attn_varlen_func` expects int; main handles it downstream via `.item()` when tracing. Affects Qwen2-VL, Qwen2.5-VL, Qwen3-VL, Qwen3.5, GLM-4V and others. Repro used `max-autotune-no-cudagraphs`. — [transformers#44973](https://github.com/huggingface/transformers/pull/44973)
- `TrainingArguments(torch_compile=True)` wraps the whole model via `torch.compile`; HF docs for training only describe the flags (backend, mode) and say first step is slow; no VLM guidance. — [HF torch.compile for training](https://huggingface.co/docs/transformers/en/torch_compile.md)
- General PyTorch guidance for these break types: `.item()`/data-dependent control flow cause graph breaks; workarounds are to avoid them, hoist them out of the compiled region, use `torch.cond`, set `torch._dynamo.config.capture_scalar_outputs = True`, or wrap in a custom op; `torch.compiler.set_stance("force_eager")` to rule out your own bugs. — [PyTorch: common graph breaks](https://github.com/pytorch/pytorch/blob/main/docs/source/user_guide/torch_compiler/compile/programming_model.common_graph_breaks.md)
- vLLM's multimodal compile design doc also states vision encoder ops can cause graph breaks and recommends `TORCH_LOGS="+dynamo"` and tlparse to find them. — [vLLM torch.compile multimodal](https://docs.vllm.ai/en/stable/design/torch_compile_multimodal/)

### Inferences
- The only parts of the Qwen3-VL forward that matter for a compiled training step are: (a) the language-model decoder layers, (b) `_deepstack_process` (boolean-mask `hidden_states[visual_pos_masks] = ...`, applied in the first few text layers — data-dependent output shape, so likely a break or an unbacked symint if the first 3 layers are compiled), (c) `masked_scatter` of image embeds into `inputs_embeds` (outside the layers). Compile layers 3..N-1 as regional blocks and leave layers 0-2, the embedding merge and `get_rope_index` eager; or precompute a static index form of the visual mask.
- Precomputing `position_ids` (3 x B x S for mRoPE) and passing them in avoids the `get_rope_index` Python loop entirely; the code path only runs when `position_ids` is None, so this is a safe hook (per the file). This also removes CPU time per micro-batch even without compile.
- Because the vision tower is frozen, running it under `torch.no_grad()` eagerly (or caching vision features per prompt, since GRPO re-uses prompts across completions and epochs) removes both the `cu_seqlens` `.tolist()` syncs and any need to compile it.
- The 250 ms D2H stall in #47649 was measured on inference profiling of a large image; with a CPU already at 100%, a stall like this directly matches "GPU ~60% busy, one core at 100%". Checking `set_sync_debug_mode("warn")` on your forward is the fastest way to confirm which of these sites fire in your setup.

### Gaps
- No published successful end-to-end `torch.compile` training of Qwen3-VL (fullgraph or regional) found; `_can_compile_fullgraph = True` is a flag in the code, but I found no test or issue demonstrating training under it with images.
- Status of #47703 / #49893 (both open at time of research) and whether they are in your pinned transformers version is unknown.

## 5. Manual CUDA Graph capture of a training step (torch.cuda.graph, make_graphed_callables)

### Takeaway
Whole-iteration capture (forward, backward, optimizer) is supported by PyTorch and gives the largest launch-overhead removal, but needs static shapes, no host syncs, static input buffers, a side-stream warmup, and a capturable optimizer; `make_graphed_callables` is the middle path for graph-safe sub-modules while the rest stays eager.

### Cited Findings
- Constraints (PyTorch CUDA notes): capture on non-default stream; CPU-GPU sync ops such as `.item()` prohibited; dynamic control flow prohibited (except GPU-data `torch.cond`); dynamic shapes prohibited; CPU work is elided on replay (silent bug); every replay uses the same addresses; only one capture at a time and no non-captured CUDA work on any thread during capture; CUDA RNG permitted (use `graphsafe_set_state` for multiple generators). — [PyTorch CUDA semantics: CUDA Graphs](https://github.com/pytorch/pytorch/blob/main/docs/source/notes/cuda.md)
- Whole-network recipe: warm up 3 iterations on a side stream with real batches (warmup includes `optimizer.step()`), `optimizer.zero_grad(set_to_none=True)` before capture so `.grad` is allocated from the graph's private pool, capture forward+loss+`backward()`+`optimizer.step()` inside `torch.cuda.graph(g)`, then per step copy new data into static input tensors and `g.replay()`; no `zero_grad` needed between replays. Pattern is the PyTorch docs' SGD example. — same doc; [PyTorch blog: Accelerating PyTorch with CUDA Graphs](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/)
- `make_graphed_callables`: creates separate forward and backward graphs per callable, runs warmup, maintains static inputs/outputs; usable inside a normal autograd loop; `requires_grad` of sample inputs must match real inputs; lets you graph only capture-safe sections while data-dependent parts run eagerly. — same doc and blog
- Optimizer capture: the NVIDIA Stable Diffusion v2 MLPerf example lists "capturable optimizer (noop flag)" as the technique for a conditional optimizer step; I did not retrieve the PyTorch `capturable=True` doc text for AdamW directly (the claim that AdamW needs `capturable=True` is standard PyTorch usage but is NOT sourced here). — [NVIDIA CUDA Graph examples](https://docs.nvidia.com/dl-cuda-graph/latest/examples/introduction.html)
- Why/when: replay skips Python, C++ dispatch and driver overhead via one `cudaGraphLaunch`; try it "if all or part of your network is graph-safe ... and you suspect its runtime is at least somewhat CPU-limited". Mask R-CNN: graphed backbone went from 31 ms to 6 ms (5x) but whole-model gain was ~1.7x because only part was graphed; BERT at 4096 GPUs 1.12x after removing syncs and making shapes static (using masks instead of data-dependent gathers). — [PyTorch blog](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/)
- Megatron-Bridge reports: neutral to ~25-30% step-time gain depending on launch-boundness; a short Qwen3-30B-A3B H100 run was slightly slower with graphs (42.00 s vs 41.36 s); graph buffers stay resident (memory neutral to several GB higher); compare replay iterations only; optimizer-graph is experimental and fails with conditional logic. — [Megatron-Bridge CUDA Graphs](https://docs.nvidia.com/nemo/megatron-bridge/0.6.2/training/cuda-graphs.html)
- NVIDIA table: Stable Diffusion v2 full-iteration capture "up to 1.58x cumulative"; GPT-3 175B per-layer 2.2-3.0%; Llama 2 70B LoRA (MLPerf, Megatron-LM per-layer graphs) "variable (depends on LoRA config)"; Llama 3.1 405B full-iteration ~15-25% at large scale (preliminary). — [NVIDIA CUDA Graph examples](https://docs.nvidia.com/dl-cuda-graph/latest/examples/introduction.html)

### Inferences
- A hand-captured whole step for Qwen3-VL needs: fixed (B, S) per graph, static `input_ids/attention_mask/position_ids/labels/pixel inputs` buffers, precomputed position ids, no `masked_scatter` with data-dependent counts (could be replaced with `torch.where`/index_put with fixed-size index tensors), no `.item()` in loss normalisation, LoRA grads accumulating in static `.grad`. With vision frozen and run outside the graph, only the text path is captured.
- Hand capture costs one graph per bucket and nothing is shared across buckets unless a common `pool=` handle is used (`torch.cuda.graph(g, pool=...)` — not verified in the sources I read), which is what CUDAGraph Trees automate.
- For a GRPO loop, captured graphs also fix the advantages/old-logprob input shapes; those become static input buffers.

### Gaps
- No source retrieved on `AdamW(capturable=True)` specifics, `fused=True` + capture, or on `torch.cuda.graph(pool=...)` sharing.
- No example of a captured VLM/LoRA training step found.

## 6. Published measured speedups for compile / CUDA graphs on LLM/VLM LoRA fine-tuning and RL, small models

### Takeaway
Reported gains from default-mode torch.compile on single-GPU LoRA are modest and hardware-dependent (about 10-35%, and negative on an RTX 5090 in one test); I found no measured reduce-overhead or CUDA-graph training number for a <=3B model, and none for GRPO update steps or any VLM.

### Cited Findings
- RTX 5090, 468M Llama from config, bf16, batch 4x2048, torch.compile default mode, SDPA attention, single run: eager 196 ms/step (41,870 tok/s) vs compiled 215 ms (38,040 tok/s), i.e. compile 9% slower on the 5090; L40S 244 -> 236 ms (+3%); A6000 457 -> 455 ms; H100 152 -> 160 ms (5% slower). First step with compile 21.6 s (5090) to 47 s. Peak memory 17.3 GB -> 13.3 GB with compile. With naive attention on H100, compile was 2.6x faster (435 -> 169 ms). Full fine-tune (not LoRA), pure bf16, fused AdamW, transformers 4.57.1, one run per setup. — [Runcrate GPU benchmarks](https://www.runcrate.ai/benchmarks/training) (vendor benchmark page, single run; treat as indicative)
- torchtune on RTX 4090 (LoRA, ~20M trainable params, alpaca_cleaned, 1 epoch): compile gave +15.3% throughput and -11.7% runtime; RTX 3090 +12.8% / -10.7%; W7900 +19.6% / -16%; author notes unsloth was 24% faster than torchtune+compile on a 4090. — [W&B train-bench report](https://forge.coreweave.com/wandb/augmxnt/train-bench/reports/torchtune-vs-axolotl-vs-unsloth-Trainer-Comparison--Vmlldzo4MzU3NTAx) (2024-era torchtune, Llama 3 8B class; older material)
- Original torchtune compile PR (llama-7b, 2024): LoRA 3.05 -> 4.12 (+35%), full fine-tune +61%, QLoRA +201% (units tokens-per-second-like metric as reported); first iteration 108-123 s for full/LoRA, ~300 s QLoRA. — [torchtune PR #596](https://github.com/pytorch/torchtune/pull/596) (old, pre-2.5 era)
- torchtune FSDP2 PR: Qwen2 0.5B LoRA, with compile about 250% toks/sec increase over the old baseline and ~70% lower peak reserved memory (this combines the FSDP2 migration with compile, so it does not isolate compile). — [torchtune PR #1517](https://github.com/pytorch/torchtune/pull/1517)
- PyTorch blog (A100, Llama-3.2-1B, torchtune): compile beat eager at every batch size and, mainly by cutting peak memory >50% at batch 128, allowed batch 256 giving 36% higher throughput; Liger kernels added only 1-2% throughput on top of compile. — [PyTorch blog: Peak Performance, Minimized Memory](https://pytorch.org/blog/peak-performance-minimized-memory/)
- LoRAFusion (arXiv 2510.00206): in a LoRA linear layer (4096x4096, r16, 8192 tokens), torch.compile gave zero forward benefit and negligible backward improvement. — [LoRAFusion](https://arxiv.org/pdf/2510.00206) (snippet-level; not read in full)
- A preprint ablation (low authority, Qwen2.5-0.5B, A100): HF baseline 8,000 tok/s -> +FlashAttention 15,200 -> +torch.compile 22,800 -> +Liger 31,500; authors' stacking, not an isolated compile measurement; the same paper accuses Unsloth of reporting zero-gradient runs. Treat with caution. — [Chronicals, arXiv 2601.02609](https://arxiv.org/html/2601.02609v1)
- NVIDIA: CUDA-graph gains are "neutral to ~25-30%" in Megatron-Bridge docs; MLPerf Mask R-CNN 1.7x, BERT 1.12x (PyTorch blog); see Section 5. — sources cited there
- GRPO update-step acceleration found in the literature came from kernel/data-layout changes (DualKV shared-prompt FlashAttention: 1.63-2.09x policy-update speedup on Qwen3-8B, 8xH100) rather than compile or graphs; the same source reports rollout generation (~240 s/step) dominates the step time. — [DualKV, arXiv 2605.15422](https://arxiv.org/pdf/2605.15422v2/__stdout.txt)
- RL.cu (hand-written CUDA RL stack, Qwen3-0.6B on RTX PRO 6000) credits CUDA graphs, among other things, for 15% faster *generation* and 1.37x wall-clock vs TRL+vLLM; that is inference graphs plus a different architecture, not training-step graphs. — [RL.cu README](https://github.com/KJLdefeated/RL.cu) (hobby project, self-reported)
- Unsloth: no official compile benchmark retrieved; web snippets with "2-5x" figures are third-party and low quality. Unsloth PRs show active work to keep packed mRoPE attention fullgraph-compilable (see Section 3). — [unsloth#16416](https://github.com/unslothai/unsloth/pull/16416)

### Inferences
- Because your GPU is ~60% busy with one CPU core pegged, you are in the launch-bound regime where graphs help most, so the best-case recoverable fraction is bounded by the idle 40% (about 1.6x step speed if overhead were driven to zero; realistically less).
- The Runcrate 5090 result (default compile slower with SDPA) suggests Inductor fusion alone is not a win for this class of GPU when you are already GPU-bound; the gain you want comes from removing launch/sync overhead (either graphs or removing syncs), not from fusion.
- Cheapest first wins likely come from eliminating syncs and precomputing position ids (Section 4) and measuring again before investing in graphs.

### Gaps
- No measured numbers for: reduce-overhead on any LoRA training; compile on Qwen-VL training; compile or graphs inside TRL GRPO update steps; Liger/Unsloth compile on RTX 4090/5090 at 2B scale with 600-1900 token sequences.
- Could not retrieve torchtune's own paper (arXiv 2605.21442, PDF unreadable via fetch) for official compile numbers.

## 7. Finding sync points and graph breaks

### Takeaway
Use `torch.cuda.set_sync_debug_mode("warn")` for eager sync sites, `TORCH_LOGS="graph_breaks,recompiles,cudagraphs"` (or tlparse) for compile issues, and `fullgraph=True` / `torch.compiler.set_stance("force_eager")` for isolation.

### Cited Findings
- `torch.cuda.set_sync_debug_mode(debug_mode)`: "default"/0 no action, "warn"/1 warns on synchronizing operations, "error"/2 raises; experimental, not every sync op is covered (torch.distributed and torch.sparse not covered). — [torch/cuda/__init__.py v2.14.0](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/cuda/__init__.py)
- `TORCH_LOGS="graph_breaks"`, `"recompiles"`, `"guards"`, `"dynamic,recompiles"` examples; `tlparse` / `TORCH_TRACE` produce an HTML compilation report (`pip install tlparse; tlparse /tmp/tracedir`); docs recommend starting with tlparse. — [PyTorch troubleshooting (source)](https://github.com/pytorch/pytorch/blob/main/docs/source/user_guide/torch_compiler/torch.compiler_troubleshooting.md)
- Use `torch.compile(fullgraph=True)` to guarantee a single graph or an error at a graph break; `TORCH_LOGS="graph_breaks"` or tlparse to see the remaining breaks; refactor unsupported code out of the compiled region. — [PyTorch: fullgraph=True](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/compile/programming_model.fullgraph_true.html)
- Cudagraph skip reasons are logged (e.g. "skipping cudagraphs due to mutated inputs") — [CUDAGraph Trees doc (source)](https://github.com/pytorch/pytorch/blob/main/docs/source/user_guide/torch_compiler/torch.compiler_cudagraph_trees.md). The `cudagraphs` TORCH_LOGS artifact name is standard but I did not fetch its documentation page; verify the option with `TORCH_LOGS=help`-style listing in your torch build.
- `torch._dynamo.config.fail_on_recompile_limit_hit=True` converts a silent fallback into an error. — [dynamo config.py v2.14.0](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_dynamo/config.py)
- `torch._dynamo.explain` is mentioned in the troubleshooting page (grep hit) but I did not read the passage; usage not cited here.
- Matches your repo's own profiling work: there is already `experiments/phase2/profile_sft.py` (untracked) and `docs/research/reports/Code performance audit 2026-11-06.md` in the working tree; not read for this note.

### Inferences
- Suggested diagnostic ladder: (1) eager forward+backward under `set_sync_debug_mode("warn")` to list `.item()/.tolist()/boolean-index` sync sites; (2) per-layer `layer.compile(fullgraph=True)` to prove the decoder layer is break-free; (3) `TORCH_LOGS=graph_breaks,recompiles` on the whole step across the bucket set; (4) only then `mode="reduce-overhead"` with `TORCH_LOGS=cudagraphs` to see skips and re-records, setting `torch._inductor.config.triton.cudagraph_skip_dynamic_graphs=True` if dynamic graphs appear.
