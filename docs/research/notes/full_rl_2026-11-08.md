- GPU use (1 Hz nvidia-smi, three 60-70 s windows): mean 67-73 %, peak memory 17 of 32 GB. The idle seconds are the

  topology 0.66 -> 0.93, legal 0.91 -> 0.99. Most of the gain is in the first 50 steps; IoU then rises slowly.
- KL: median per step 0.19 (steps 41-50), 0.25-0.36 after. Single-token spikes appear in the logged mean (step 156:
  1020; step 160: 5.9): a token vLLM sampled that the trainer's policy gives near-zero probability. Gradient norm and
  rewards were unchanged at those steps. Judge drift by the median.
- A `CUDA Error: invalid argument at cumem_allocator.cpp:249` line prints at exit, after the final model is written.
  It is vLLM's sleep-mode allocator shutting down; the exit code is 0 and the model loads.

## Known issue found after the run: base-weight drift in TRL's weight sync

TRL 1.17.1 `VLLMGeneration` merges the LoRA adapter into the bf16 base weights in place, pushes them to vLLM, then
unmerges (`trl/generation/vllm_generation.py:459, 480`). In bf16, W + d - d is not W. Checked on the Mac: a 2048 x
2048 bf16 matrix (|W| ~ 1.6e-2) after 770 merge/unmerge cycles with a fixed rank-16 delta had 6.4 % of entries
changed, max change 4.9e-4. TRL issue #6688 (maintainer-confirmed), tracking #7423, fix PR #7427 open
(`grpo_utilization_research_2026-11-08.md`). The trainer and vLLM both see the drifted weights, so the IS ratio does
not flag it. The held-out numbers above measure the saved model as it is, drift included.

Fixed after the run: `fast.lora_merged_params` yields W + delta as a new tensor (same values PEFT's merge computes)
and never writes a parameter; `FastGRPO.sync_without_merge` routes TRL's colocate sync through it on one process
(FSDP / ZeRO-3 keep TRL's path). Tests in `tests/test_train_fast.py`: the pushed weights equal TRL's merge exactly,
20 syncs leave every parameter bit-identical while TRL's path changes them, and FastGRPO installs the route. Not yet
run on a GPU.
