# Fixing the GRPO stack before renting

The fast, safe path for GRPO on Qwen3-VL-2B with a LoRA adapter on one RTX 5090 (or 4090) is to remove host-side overhead first and to treat every version pairing as unproven until a short smoke run passes. No published measurement covers `torch.compile` or CUDA Graphs on a Qwen-VL training step or on a GRPO update, so the expected gains below are bounded by reasoning and by launch-bound results on other models, not by direct evidence. The most concrete finding is a version problem. TRL 1.16.0 declares vLLM support only up to 0.31.0, and 0.32 support arrived in TRL 1.17.0, so our pin set sits outside TRL's tested range ([TRL v1.16.0 pyproject](https://raw.githubusercontent.com/huggingface/trl/v1.16.0/pyproject.toml); [TRL releases](https://api.github.com/repos/huggingface/trl/releases?per_page=8)). Compile is a modest lever: default-mode `torch.compile` was 9% slower on an RTX 5090 in one full fine-tune test ([Runcrate](https://www.runcrate.ai/benchmarks/training)). The larger recoverable cost is launch and sync overhead, which comes from data-dependent code in the Qwen3-VL forward and which per-layer compile can remove only if we compile the text decoder, precompute `position_ids`, and bucket shapes. On the environment side, sm_120 needs CUDA 12.8 or newer and cu13 wheels need driver 580 or newer, but the arch list of the torch 2.13 cu130 wheel and vLLM 0.32 behaviour on sm_120 are unverified. For the custom checker, the rule is one persistent arena, one pinned staging buffer, one batched launch, one GPU-owning process and a copy on return. The final section lists the measurements that decide the open choices.

## The version range is the first risk, and importance sampling is the second

Cited facts first. TRL v1.16.0 declares `vllm>=0.22.0,<=0.31.0` with `transformers>=4.56.2` and `peft>=0.13.0`. v1.17.0 (2026-10-29) "adds support for vLLM 0.32.0", and raises minimums to torch 2.6, accelerate 1.11 and peft 0.17 ([TRL releases](https://api.github.com/repos/huggingface/trl/releases?per_page=8)). The docs on main say TRL supports vLLM 0.23 to 0.33.x, which conflicts with the 1.16 pyproject and reflects that main is newer ([TRL vLLM integration](https://huggingface.co/docs/trl/main/en/vllm_integration)). v1.17.1 (2026-10-30) is the latest patch seen. v1.17.0 also contains two behaviour changes: with vLLM and importance-sampling (IS) correction on, which is the default, `GRPOConfig` raises when `top_p < 1.0` or `min_p > 0.0` is set without `top_k > 0`, and in colocate mode (vLLM 0.28 or newer) log-probs are renormalized over the top-k/top-p candidate set ([TRL releases](https://api.github.com/repos/huggingface/trl/releases?per_page=8)). vLLM's own 0.32 docs describe a `sampling_mask` feature for the same reason, because training on a full-vocabulary softmax while rollouts sample from a truncated set "violates the principles of importance sampling and destabilizes training" ([vLLM 0.32 sampling mask](https://docs.vllm.ai/en/v0.32.0/training/sampling_mask/)).

My inference is that the image pin of TRL 1.16 with vLLM 0.32 is a deliberate override of the pip constraint, with no evidence of failure and none of success. The notes found no source on torch 2.13 or transformers 5.19 against TRL either. The safest options are to move to TRL 1.17.x, setting `top_p=1` and `min_p=0` (or an explicit `top_k`, where the error text suggests e.g. 512), or to keep 1.16 and make a two-step smoke run a hard preflight gate. Either way the preflight should import-check both packages and run two optimizer steps end to end.

The IS correction itself is on by default (`vllm_importance_sampling_correction=True`, mode `sequence_mask`, `clip_max=3.0`). It forces TRL to compute `old_per_token_logps` with the trainer model, which adds a forward pass ([TRL v1.17.0 grpo_config.py](https://raw.githubusercontent.com/huggingface/trl/v1.17.0/trl/trainer/grpo_config.py); [TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)). In mask modes a ratio outside the range is set to zero, and the sequence-level variants act on whole completions. The metrics `sampling/importance_sampling_ratio/{min,mean,max}` and `sampling/sampling_logp_difference/{mean,max}` are logged ([TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)). The motivation is the paper "Your Efficient RL Framework Secretly Brings You Off-Policy RL Training", which argues that separate rollout and training implementations make "on-policy" RL implicitly off-policy ([paper page](https://liyuanlucasliu.github.io/publication/feng-off-2025)). I did not verify the paper's magnitude numbers.

Inferences follow. In `sequence_mask` mode a whole completion gets zero weight if its sequence ratio exceeds 3.0, and our 1,536-token tail completions are the likeliest to be masked, because errors accumulate over many tokens. TRL logs no masked-fraction metric that the notes found, so we should log it ourselves from the ratio distribution. Merging LoRA into bf16 vLLM weights can add rounding mismatch on top of the engine difference. This is plausible but unsourced.

## Colocate mechanics: sizing the engine for 256 completions

In colocate mode (the default for `use_vllm=True`) TRL builds a vLLM `LLM` inside the trainer process with `distributed_executor_backend="external_launcher"`, `max_num_batched_tokens=4096`, `logprobs_mode="processed_logprobs"`, and `enable_sleep_mode` from config ([TRL vllm_generation.py](https://raw.githubusercontent.com/huggingface/trl/main/trl/generation/vllm_generation.py)). The comment on the 4096 value says the "latest vLLM v1 memory profiler is misled by the high default value (i.e., 32768)". The trainer passes `max_num_seqs = per_device_train_batch_size * vllm_tensor_parallel_size * steps_per_generation` and `gpu_memory_utilization` from `vllm_gpu_memory_utilization`, default **0.3** ([TRL v1.16.0 grpo_trainer.py](https://raw.githubusercontent.com/huggingface/trl/v1.16.0/trl/trainer/grpo_trainer.py); [TRL v1.17.0 grpo_config.py](https://raw.githubusercontent.com/huggingface/trl/v1.17.0/trl/trainer/grpo_config.py)). `vllm_max_model_length` defaults to `None`, and its help text says to set it to at least the prompt plus `max_completion_length`. The fetched source did not show `enforce_eager`, `limit_mm_per_prompt`, a processor cache option or `enable_prefix_caching` being set. This absence was reported on the portion read, not by a full-file grep. `reset_prefix_cache()` is called after each weight sync, so prefix caching helps only within one generation batch, which is where the eight samples per prompt share their prefix.

One generation batch equals `per_device_train_batch_size * num_processes * steps_per_generation`, with `steps_per_generation` defaulting to `gradient_accumulation_steps` ([TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)). Generation runs every `steps_per_generation * num_iterations` micro-steps and the batch is split into buffered chunks. `beta` defaults to 0, in which case no reference model is used. With PEFT and beta above 0, reference log-probs come from the base model by disabling adapters ([TRL v1.16.0 grpo_trainer.py](https://raw.githubusercontent.com/huggingface/trl/v1.16.0/trl/trainer/grpo_trainer.py)).

Our arithmetic, not a TRL statement: to get 256 completions per step on one GPU, set `per_device_train_batch_size * gradient_accumulation_steps = 256` with `steps_per_generation` equal to `gradient_accumulation_steps` and `num_generations=8`. Then `max_num_seqs` is 256 regardless of the micro-batch split, and the micro-batch size only affects training memory. Keeping `steps_per_generation` equal to `gradient_accumulation_steps` keeps one rollout per optimizer step, inferred from the code shape. `vllm_max_model_length` should be at least about 1,900 (330 prompt tokens plus 1,536). With beta above 0 and IS correction on, one step costs three forwards (old log-probs, reference log-probs, training) and one backward over 256 sequences. Setting beta to 0 would drop the reference forward, but that is the owner's decision.

For KV memory, using the 112 KB per token figure from the task, the worst case is 256 x (330 + 1,536) tokens, about 478k tokens or about 53 GB. A typical case of 330 + ~300 tokens is about 161k tokens or about 18 GB. All of this is my estimate. The KV pool will bind and vLLM will queue the long tail, not fail, so generation wall time is set by the 1,536-token stragglers, and shortening `max_completion_length` is the largest generation-speed lever. On 24 GB, 0.3 utilization is 7.2 GB and leaves about 16.8 GB for training. On 32 GB it is 9.6 GB.

### Sleep mode and LoRA weight sync

TRL's sleep mode always uses vLLM level 2. It calls `llm.sleep(level=2)` after init and after each generation, wakes `kv_cache` before generation and `weights` at the start of `sync_weights()`, and re-pushes weights from the trainer because "vLLM's reload_weights would reload the initial checkpoint from disk" ([TRL vllm_generation.py](https://raw.githubusercontent.com/huggingface/trl/main/trl/generation/vllm_generation.py)). vLLM's docs define level 2 as discarding both weights and KV cache and say sleep can release "up to 90%+ of GPU memory" ([vLLM sleep mode](https://docs.vllm.ai/en/latest/features/sleep_mode/)). The TRL memory docs say "offload to CPU RAM", which contradicts the source code, so I follow the code ([TRL reducing memory usage](https://huggingface.co/docs/trl/main/en/reducing_memory_usage)). With sleep mode, `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` must be set under that exact name, since vLLM reads only that variable ([TRL reducing memory usage](https://huggingface.co/docs/trl/main/en/reducing_memory_usage)). Sleep defaults to off, and the docs advise enabling it after out-of-memory errors. Level-2 buffer restoration and a shutdown segfault were known in vLLM 0.8-era releases ([HF blog](https://huggingface.co/blog/vllm-colocate)). Their status on 0.32 is unchecked.

TRL does not use vLLM LoRA adapters in colocate. For PEFT it runs `merge_adapter()`, loads each non-adapter tensor through `model.load_weights([(name, param)])`, calls `unmerge_adapter()`, and resets the prefix cache. This happens once per global step (`if self.state.global_step != self._last_loaded_step`) ([TRL vllm_generation.py](https://raw.githubusercontent.com/huggingface/trl/main/trl/generation/vllm_generation.py); [TRL v1.16.0 grpo_trainer.py](https://raw.githubusercontent.com/huggingface/trl/v1.16.0/trl/trainer/grpo_trainer.py)).

Inferences: sync cost is set by full model size, not LoRA rank, since merged weights are bf16 copies of base plus delta. It is probably sub-second to a few seconds for roughly 4.4 GB, but no published number exists and our smoke run must time it. With sleep mode, utilization could rise to something like 0.5 to 0.6 for a bigger KV pool, at the price of an extra weights push per generation. Whether TRL's init-time memory profiling accounts for the resident training model correctly is unverified, and TRL points to the HF Space `trl-lib/recommend-vllm-memory` as the sizing aid ([TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)). Whether the frozen vision tower reaches vLLM through this loop is also unverified.

### VLM support risk

The documented VLM list for GRPO with vLLM is Gemma3-4B, LLaVA-NeXT, Qwen2-VL-2B, Qwen2.5-VL-3B and SmolVLM2-2.2B. **Qwen3-VL is not listed**, and the research found no Qwen3-VL GRPO colocate report ([TRL GRPO docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)). In colocate each prompt row gets `multi_modal_data = {"image": ...}` ([TRL vllm_generation.py](https://raw.githubusercontent.com/huggingface/trl/main/trl/generation/vllm_generation.py)). TRL issue #6294 documents a real failure for SmolVLM (Idefics3). TRL sends processor-expanded prompt IDs (855 tokens instead of 38) to vLLM, which expands the placeholders again, giving corrupted colocate rollouts and a hard error in server mode. It was seen on TRL 1.5.0.dev0 with vLLM 0.23 and transformers 5.13, with fix PR #6718 of unknown merge status ([TRL issue 6294](https://github.com/huggingface/trl/issues/6294)). v1.16.0 and v1.17.0 also stop VLM policies from generating the image placeholder token ([TRL releases](https://api.github.com/repos/huggingface/trl/releases?per_page=8)). Our inference is that Qwen processors also expand placeholders, so the risk transfers, though vLLM's Qwen-VL path may accept expanded IDs. The smoke gate should compare vLLM completions (non-empty and parse rates) against an HF-generate baseline on a few prompts, as the issue does.

## Compile and graphs: remove syncs first, compile decoder layers second

PyTorch's CUDAGraph Trees record Inductor graphs into one shared pool. They skip functions with input mutation on eager inputs, CPU ops, `.item()` (`aten._local_scalar_dense`) and unsafe custom ops, and they **re-record for every unique input shape** ([CUDAGraph Trees doc](https://github.com/pytorch/pytorch/blob/main/docs/source/user_guide/torch_compiler/torch.compiler_cudagraph_trees.md)). The doc advises padding to a few fixed shapes or setting `triton.cudagraph_skip_dynamic_graphs=True`. In the v2.13/v2.14 source `graph_partition` defaults to on for non-fbcode builds, although the docs still describe it as opt-in ([inductor config.py v2.14.0](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_inductor/config.py)). The default Dynamo `recompile_limit` is 8, after which new shapes run eagerly, and `fail_on_recompile_limit_hit` turns that silent fallback into an error ([dynamo config.py v2.14.0](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_dynamo/config.py); [PyTorch recompilation guide](https://docs.pytorch.org/docs/2.14/user_guide/torch_compiler/compile/programming_model.recompilation.html)). NVIDIA's guidance is to start with padding to one fixed length, use bucketing (e.g. 5 buckets, about 5x graph memory) only if padding waste is large, and graph only the most frequent buckets while running rare shapes eagerly ([NVIDIA handling dynamic patterns](https://docs.nvidia.com/dl-cuda-graph/latest/torch-cuda-graph/handling-dynamic-patterns.html)).

### What breaks in Qwen3-VL and PEFT

Current `modeling_qwen3_vl.py` has data-dependent code: `.tolist()` in vision attention and `get_image_features`, `itertools.groupby` and a per-item Python loop in `get_rope_index`, `.item()` in `get_vision_position_ids`, and boolean-mask scatter in `_deepstack_process` and `masked_scatter`. This was summarized by a fetch tool, so verify it in the installed version ([modeling_qwen3_vl.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_vl/modeling_qwen3_vl.py)). `get_rope_index` only runs when `position_ids` is `None`. Issue #47649 measured a `lengths.tolist()` device-to-host stall above 250 ms in Qwen3-VL vision attention ([transformers#47649](https://github.com/huggingface/transformers/issues/47649)). PRs #47703 and #49893 move control tensors to CPU and were open at research time ([transformers#47703](https://github.com/huggingface/transformers/pull/47703); [transformers#49893](https://github.com/huggingface/transformers/pull/49893)). No published successful Qwen3-VL training under compile was found.

PEFT lists LoRA training under `torch.compile` as working for a causal LM with default settings, without mention of VLMs, gradient checkpointing or reduce-overhead ([PEFT torch.compile guide](https://huggingface.co/docs/peft/en/developer_guides/torch_compile)). A known bug, peft#3020, gives an Inductor `BackendCompilerFailed` on LLaVA with LoRA, activation checkpointing and `lora_dropout != 0`. It works at dropout 0, and a commenter's workaround is `torch._inductor.config.fallback_random = True` ([peft#3020](https://github.com/huggingface/peft/issues/3020)). Dynamo does not trace inside `torch.utils.checkpoint` unless it can wrap it as a higher-order op, otherwise it graph-breaks ([torch/utils/checkpoint.py](https://github.com/pytorch/pytorch/blob/main/torch/utils/checkpoint.py)).

Regional compilation is the documented way to cut compile cost. The recipe shows forward-only compile of 10.02 s full against 0.37 s regional ([PyTorch regional compilation recipe](https://docs.pytorch.org/tutorials/recipes/regional_compilation.html)), and torchtune compiles each transformer layer separately with default mode ([torchtune _compile.py](https://github.com/pytorch/torchtune/blob/main/torchtune/training/_compile.py)).

### Expected gains

| Evidence | Result | Source |
|---|---|---|
| RTX 5090, 468M Llama, full fine-tune, default compile | 196 ms eager vs 215 ms compiled (9% slower); first step 21.6 s | [Runcrate](https://www.runcrate.ai/benchmarks/training) |
| torchtune LoRA on RTX 4090 (2024-era, Llama 3 8B class) | +15.3% throughput | [W&B report](https://forge.coreweave.com/wandb/augmxnt/train-bench/reports/torchtune-vs-axolotl-vs-unsloth-Trainer-Comparison--Vmlldzo4MzU3NTAx) |
| LoRA linear layer (4096x4096, r16) | no forward benefit from compile | [LoRAFusion](https://arxiv.org/pdf/2510.00206) |
| Megatron-Bridge CUDA graphs | neutral to about 25-30%; one short run slightly slower | [Megatron-Bridge](https://docs.nvidia.com/nemo/megatron-bridge/0.6.2/training/cuda-graphs.html) |
| Mask R-CNN (graphs, part of model) | 1.7x overall | [PyTorch blog](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/) |

No measured reduce-overhead or CUDA-graph number exists for any LoRA fine-tune at this scale, any VLM, or any GRPO update step. In the GRPO literature, update-step gains came from kernel and data-layout changes (shared-prompt attention, 1.63 to 2.09x on Qwen3-8B), and rollout generation dominated step time ([DualKV, arXiv 2605.15422](https://arxiv.org/pdf/2605.15422v2/__stdout.txt)).

My reading: an RTX 5090 is likelier to be GPU-bound on fusion than launch-bound, and the one 5090 data point says Inductor fusion alone does not win. The earlier project report found about 60% GPU utilization with a pegged CPU core on the 4090, which is launch-bound and caps the upside at about 1.6x if overhead went to zero (realistically far less). Evidence for the earlier hypothesis that checkpointing should be switched off first still stands, since it removes an extra forward pass at the cost of memory ([TRL reducing memory usage](https://huggingface.co/docs/trl/main/en/reducing_memory_usage)). The recommended ladder is below. It is inference from the cited constraints, not a tested recipe.

1. Run the eager forward and backward under `torch.cuda.set_sync_debug_mode("warn")` to list sync sites, which the docs flag as experimental and incomplete ([torch/cuda/__init__.py v2.14.0](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/cuda/__init__.py)).
2. Pass precomputed `position_ids` (3 x B x S) so `get_rope_index` never runs, and run the frozen vision tower eagerly under `no_grad`, or cache its features per prompt since eight completions share an image.
3. Compile decoder layers with `layer.compile(fullgraph=True)`, leaving the first deepstack layers, the `masked_scatter` merge and the vision tower eager, with `lora_dropout=0` if the experiment allows.
4. Pad sequence length to multiples of 256 with a cap (about 6 to 8 buckets), fix the micro-batch size, and raise `recompile_limit` above the bucket count.
5. Only then try `mode="reduce-overhead"` with `TORCH_LOGS=graph_breaks,recompiles,cudagraphs` and `cudagraph_mark_step_begin()` per micro-batch if overwritten-output errors appear.

Manual whole-step capture needs static shapes, no `.item()`, static input buffers and a capturable optimizer ([PyTorch CUDA notes](https://github.com/pytorch/pytorch/blob/main/docs/source/notes/cuda.md)). It is the last resort for a VLM, and the notes found no example of a captured VLM LoRA step.

## The sm_120 environment: wheels and the vLLM backend need verifying

The RTX 5090 is compute capability 12.0. Its streaming multiprocessor has up to 100 KB shared memory (99 KB opt-in per block), against 228 KB on sm_100, and the guide lists 12.x targets `compute_120a` and the family target `compute_120f` ([NVIDIA CUDA compute capabilities](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)). A single community source claims ptxas rejects `tcgen05` for sm_120a ([gist](https://gist.github.com/solatticus/aab6ec3a0436748b021cbbdd12e8c739)). I treat it as plausible but unconfirmed. CUDA 12.8 GA needs Linux driver 570.26 or newer and CUDA 13.x needs driver 580 or newer ([CUDA release notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html)). Blackwell needs a PyTorch build made with CUDA 12.8 or newer ([PyTorch forum](https://discuss.pytorch.org/t/is-there-a-pytorch-build-that-supports-nvidia-rtx-5090-compute-capability-12-0-sm-120/223536.md)). PyTorch 2.13.0 (2026-07-08) keeps CUDA 13.0 as the default, removes the 12.8 and 12.9 builds, no longer bundles ptxas in the cu13 binary and pins Triton 3.7.1 ([PyTorch 2.13 release blog](https://pytorch.org/blog/pytorch-2-13-release-blog/)). The blog does not state the arch list, so whether sm_120 SASS or PTX ships in the cu130 wheel is unconfirmed. A cuBLAS known issue affecting CC 12.0/12.1 arrived in CUDA 13.0 Update 2, with details unread ([CUDA release notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html)).

For vLLM, prebuilt wheels failed on RTX 50-series ("no kernel image") in issue #35432 until it closed on 2026-05-15 ([vLLM #35432](https://github.com/vllm-project/vllm/issues/35432)). The attention backend page has no sm_120 priority list: FA2 needs compute capability 8.0 or newer, FA4 needs 10.0 or newer, TRITON_ATTN works anywhere, and a B12X backend targets SM120/121 ([vLLM attention backends](https://docs.vllm.ai/en/latest/design/attention_backends/)). Reports cover a CUDA-graph-capture segfault and deadlock on a 5090 with vLLM 0.11.2 ([vLLM forum](https://discuss.vllm.ai/t/bug-segfault-in-pythonsymnodeimpl-and-deadlock-on-rtx-5090-blackwell-with-vllm-0-11-2/2688)). They also cover a whole-host lock on an RTX PRO 6000 during graph capture that clock locking avoided ([NVIDIA forum](https://forums.developer.nvidia.com/t/rtx-pro-6000-blackwell-ws-whole-host-hard-lock-during-vllm-cuda-graph/379239)). An explicit `FLASH_ATTN` backend with fp8 KV cache crashes at engine start on a 5090 ([vLLM #37714](https://github.com/vllm-project/vllm/issues/37714)). All found issues predate 0.32, and nothing confirms 0.32 behaviour on sm_120.

Inferences: stay with bf16 weights and bf16 KV, which sidesteps the NVFP4, fp8-KV and int8 bugs. Pin the attention backend explicitly if the image has no nvcc, because FlashInfer may JIT-compile, and keep `enforce_eager=True` as the fallback if graph capture hangs. TRL does not expose `enforce_eager` in the fields the notes found, so that fallback may need a patch, which is an open question. For our own extension, `-DCMAKE_CUDA_ARCHITECTURES=120` is the plain choice, with `120-virtual` adding PTX. I did not verify CMake's handling of the `120a` suffix or the behaviour of pip `nvidia-cuda-nvcc` wheels (include paths, headers), so the image build should compile a trivial kernel with `-gencode arch=compute_120,code=sm_120`. Our checker should not assume more than 99 KB dynamic shared memory per block, and for the 4090 the target would be sm_89, which the notes did not cover.

On Vast, `vastai search offers` accepts `cuda_vers`, `driver_version`, `geolocation` (with `in`/`notin`), `reliability`, `pcie_bw`, `inet_down`, `disk_space` and `gpu_ram` ([Vast CLI reference](https://docs.vast.ai/cli/reference/search-offers.md)). Unverified machines are filtered by default, and new machines start at 60% reliability ([Vast search docs](https://docs.vast.ai/documentation/instances/search)). Prices are aggregator-reported at about $0.45 to $0.75 per hour, with a median near $0.60 and some hosts on older Xeons ([DeployBase](https://deploybase.ai/articles/rtx-5090-on-vastai-pricing-specs-how-to-rent)). Other trackers disagree widely. My proposed filter, untested, is `gpu_name=RTX_5090 num_gpus=1 geolocation in [US,CA] driver_version>=580 reliability>0.98 pcie_bw>=20 verified=true`, matching the owner's US/CA rule. The 5090 runs about 1.3 to 1.4x faster than the 4090 on small-model inference in vendor numbers ([Spheron](https://www.spheron.network/blog/rtx-5090-vs-rtx-4090/); [Trooper](https://www.trooper.ai/benchmarks-compare-RTX-5090-with-RTX-4090-Pro)), so it only pays if its hourly premium stays under about 30%, and this needs live 4090 prices.

The start-of-rental checks, proposed from these constraints and run before the bundle download, are as follows. Query `nvidia-smi` for name, driver at 580 or newer, about 32 GB, compute_cap 12.0, PCIe generation and width, and max clocks. Print `torch.cuda.get_arch_list()` and fail if sm_120 or compute_120 is missing. Time an 8192 bf16 matmul and record TFLOPS against a stored baseline, since no official dense roofline was found. Compile a small function with `torch.compile` to prove Triton 3.7.1 works. Compile and run the trivial nvcc kernel. Start a tiny vLLM engine with `enforce_eager=True`, then with graphs, logging the chosen backend. Record `lscpu` and reject old low-clock Xeons for launch-bound jobs. Check profiling permissions (`nsys status -e`, `perf_event_paranoid`) as in the earlier report, where `ncu` should be assumed unavailable without privileges.

## Checker host design: one GPU owner, one arena, one pinned buffer, one launch

Cited facts. `cudaFree` on a non-stream-ordered pointer can implicitly synchronize the device, and "any CUDA API call may block or synchronize" ([NVIDIA stream-ordered allocator blog](https://developer.nvidia.com/blog/using-cuda-stream-ordered-memory-allocator-part-1/); [API synchronization behavior](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html)). On P100/V100-era hardware on-demand unified-memory migration reached about 5.4 GB/s against 10.9 for prefetch and 11.4 for explicit `cudaMemcpyAsync` ([NVIDIA unified memory blog](https://developer.nvidia.com/blog/maximizing-unified-memory-performance-cuda/)). Batching many small transfers into one large one performs significantly better ([CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)). `cudaMallocAsync` has a default pool release threshold of 0, so unused memory is returned at every sync unless the threshold is raised ([NVIDIA stream-ordered allocator blog](https://developer.nvidia.com/blog/using-cuda-stream-ordered-memory-allocator-part-1/)). `cudaMemcpyAsync` is only truly asynchronous with pinned host memory, and pageable copies may synchronize ([API synchronization behavior](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html)). Forum anecdotes put pinned allocation near 1.3 ms and free near 18 ms ([NVIDIA forum](https://forums.developer.nvidia.com/t/cudafreehost-consistently-20x-slower-than-free-cudafree-full-runnable-example-code-available/217706)). They are not official, but they support allocating once.

My design from these facts follows. Replace the roughly 20 per-call managed allocations with one `cudaMalloc` arena sized to the high-water mark, grown geometrically only after a sync, with sub-buffers aligned to 256 bytes and an offset reset per call. A single zeroing kernel or `cudaMemsetAsync` replaces per-buffer memsets. If a pool is preferred, set the release threshold high at init. Pack all inputs (vertices, offsets, parameters) into one pinned input buffer for one H2D copy, and use a separate small pinned output buffer without write-combining, because write-combined memory cannot be read efficiently by the CPU ([Runtime API memory management](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html)). Registering numpy arrays per call page-locks each time and is probably slower for small payloads, which is my inference. Each call then does one H2D copy, one batched launch with a block per polygon, one D2H copy and one sync. Launch errors are caught with `cudaGetLastError` after each kernel, and execution errors surface at the final sync. After a sticky error the module should mark itself failed. Arena sub-allocation hides out-of-bounds writes between buffers from `compute-sanitizer memcheck`, so a debug mode with separate allocations or guard bands is needed.

For the mask output, `numpy.unpackbits` with `bitorder="little"` reads each byte LSB-first, and `__ballot_sync` returns a 32-bit mask over the warp's lanes, with all named threads required to reach it ([NumPy unpackbits](https://numpy.org/doc/stable/reference/generated/numpy.unpackbits.html); [NVIDIA warp-level primitives](https://developer.nvidia.com/blog/using-cuda-warp-level-primitives/)). A layout of `(N, H, ceil(W/32))` uint32, with pixel x at bit `x & 31` of word `x >> 5` and written by lane 0 of each warp, is my inference. It round-trips through `view(uint8)` and `unpackbits(..., bitorder="little")` on little-endian hosts. The lane-to-bit rule (bit i is lane i) is not stated on the page the notes fetched, so a unit test against a known pattern is required.

For nanobind, `nb::ndarray` records metadata only, and ownership comes from an owner object or an `nb::capsule` deleter. With `rv_policy::reference` and no owner it assumes the memory lives forever, and creating or casting a return array needs the GIL ([nanobind ndarray docs](https://nanobind.readthedocs.io/en/latest/ndarray.html)). The notes did not retrieve the `gil_scoped_release` and `call_guard` pages, so those APIs need confirming. My pattern: take the input as a read-only contiguous CPU ndarray, release the GIL around the GPU section under a `std::mutex` taken after the release, then reacquire the GIL and return a fresh capsule-owned copy of the packed mask. Copying is cheap at one-eighth of the raster bytes and avoids handing Python a view that the next call overwrites. Returning pinned memory directly is unsafe for the same reason.

Fork pools are the largest hazard for this project. A CUDA context created before `fork()` is unusable in the child, and PyTorch raises "Cannot re-initialize CUDA in forked subprocess" ([PyTorch forum](https://discuss.pytorch.org/t/cannot-re-initialize-cuda-in-forked-subprocess-on-network-to-device-operation/138090); [pytorch/pytorch#68861](https://github.com/pytorch/pytorch/issues/68861)). Each GPU process holds its own context, measured at about 600 MB on one GPU, and without MPS the processes time-slice and never run kernels concurrently ([arXiv 2604.08451](https://arxiv.org/pdf/2604.08451)). My inference is that the current fork-based pool of 4 is safe only if nothing touches CUDA in the parent first, including a build check, and that even then four children cost about 2.4 GB and serialize on the GPU. The architecture to prefer is a single GPU-owning process with lazy initialization on first call, fed by CPU workers over a queue or shared memory, with a pid check that raises a clear error when a forked child calls it. Colocate raises one more concern, since vLLM and the trainer already share the same GPU process. MPS needs a daemon and may not be available on rented hosts, which is unverified.

CUDA Graphs for a handful of kernels are probably not worth it. NVIDIA's dynamic-graph example gained 16% and 26% for 504 and 2,520 kernels of 2 to 8 microseconds, with update cost roughly proportional to changed nodes ([NVIDIA CUDA graphs in a dynamic environment](https://developer.nvidia.com/blog/employing-cuda-graphs-in-a-dynamic-environment/)). Per-launch cost of a few microseconds is small against a megabyte-scale PCIe copy, which is unsourced general knowledge. The earlier project report reached the same conclusion, that batching comes first and a graph over the build, check and score chain comes after.

## Open questions that only the GPU can answer

The first group decides whether the stack runs at all. Does TRL 1.16 import and complete two steps against vLLM 0.32 with Qwen3-VL-2B, and does TRL 1.17.x change the answer? Do vLLM completions match an HF-generate baseline in non-empty and parse rates, which tests the #6294-style double expansion? Which attention backend does vLLM 0.32 pick on compute capability 12.0, does it need nvcc to JIT, and does CUDA-graph capture complete without a hang? Does `torch.get_arch_list()` for the 2.13 cu130 wheel include sm_120, does a Triton kernel compile there, and does a trivial nvcc kernel built for compute_120 run? Does the pip nvcc toolchain include the headers and libraries our extension needs?

The second group sizes and times the step. What is the measured per-step time split among generation, reward scoring, old and reference log-probs, backward and weight sync? How long do merge, per-tensor load and unmerge take, and how long do sleep and wake take with and without level-2 sleep? What `vllm_gpu_memory_utilization` leaves room for training on 24 and 32 GB, and what fraction of 256 sequences is queued by the KV pool at 1,536 tokens? Does training fit with checkpointing off, and what is the activation memory? What fraction of completions does `sequence_mask` zero, and does it concentrate in long completions?

The third group decides the compile work. Which `set_sync_debug_mode` sites fire in the Qwen3-VL forward, and how much do precomputed `position_ids` and cached vision features save? Is a per-layer `fullgraph=True` compile break-free on layers 3 onward, how many recompiles occur across the bucket set, and does LoRA dropout need `fallback_random`? Does reduce-overhead record the backward graphs under gradient accumulation, and does its memory fit with 6 to 8 buckets? Is the host CPU fast enough that the run is GPU-bound, making compile pointless on a 5090? A 5-step `torch.profiler` trace answers most of these cheaply.

The fourth group concerns the checker. What are the break-even batch size and the per-call split between kernel and overhead? Do `cudaMalloc`, `cudaMallocHost` and `cudaFree` costs match forum anecdotes on Ada and Blackwell? Does the little-endian ballot layout round-trip in a unit test? How much would a single GPU-owner process save over four forked children?

## Conclusion

The research changes the order of work. The expensive-sounding ideas (CUDA Graphs, whole-step capture, reduce-overhead) have no published evidence at our scale and a long chain of preconditions in Qwen3-VL, whereas the cheap ones (pin the TRL and vLLM pairing, precompute `position_ids`, cache the frozen vision features, shorten `max_completion_length`, batch the checker) cost hours and attack the measured symptom. A 5090 makes this ordering stricter: it is faster, so a fixed per-step host cost is a larger share, and the one 5090 benchmark found fusion alone was a net loss.

The second implication is that most of the risk is in integration rather than in raw speed. The unlisted Qwen3-VL, the unverified TRL 1.16 plus vLLM 0.32 pairing, the unconfirmed sm_120 arch list and the placeholder-expansion bug are all binary go or no-go checks that a few minutes of rental can settle. They should be settled in the preflight, before any longer run is paid for.
